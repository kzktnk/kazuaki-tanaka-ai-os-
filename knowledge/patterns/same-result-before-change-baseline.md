# Pattern: Same Result before a Change Baseline

**Status:** Active  
**Origin:** Anonymized internal reviews of a buyer-side change-control design (Program Line AL, 2026-09 to 2026-10). Client names, yen, dates, and the worked example are **not** stored here.

## Pattern statement

> **変更管理は、方針を説明した時点では回っていない。基準は、経験者と新人が同じ結論になるまで基準ではない。ベースラインがベースラインでないものを、変更票で救済しない。**

方針・チェックリスト・「合意した」は、運用の開始ではない。回るとは、変更が1件来たときに、受付、影響の分解、採否が、担当が替わっても同じ結果になることである。

## What a running process is

3点が揃って初めて回る。

| 点 | 仕事 |
|---|---|
| プロセス | 受付 → 影響 → 採否。誰がどの列を埋めるか |
| 台帳 | その判断の記録。後の追加発注の根拠になる |
| 手引き | 各列に何を書くか |

方針のページだけでは回らない。影響は一欄にまとめない。業務影響と業務日程は発注側、コストと開発日程はベンダー、採否と理由は発注側。ベンダーの変更管理が別に動いていても、発注側の記録は残す。既存取引先との口約束は、新しいベンダーには引き継がれない。

コンサルタントが作るのは仕組みである。回すのは顧客である。

「合意した」は、誰が、どの粒度で、を名指す。概念にうなずいたのか、項目まで見たのか、自分で回せるのかは別である。チェックの管理票は成果物ごとの着手／完了までにする。中身の再採点はしない。抜き取りの支援で足りる。

ベースラインを固定する前に、回す人と1件を机上で通す。初回の本番で崩れた段だけ直す。

## What a criterion is

Must と Want の仕分けだけでも、総論賛成・各論反対が起きる。Want の中に勾配（改善効果、他施策との整合）を足すと、要件定義の間は基準にならない。確定見積のあとで Want を拾うなら、費用対効果で切る。効果の期間を伸ばして比率を1以上にしない。

次は基準ではない。

- 「システムが止まると業務ができない」。停止しても業務が続くのが前提なら、この試験はほぼ全部を Must にする。
- 「現場が、新しいやり方では回らないと言う」。習熟で一時的に生産性が落ちる変更は、現場からそう返る。それは定着の問題であり、スコープの Must ではない。

Must は、承認された目的（法令、安全、投資を通したときの目的）に照らして要るもの。Want はそれ以外。

## Baseline is not a rescue channel

年度予算のための概算見積と、発注に使う確定見積は別である（`knowledge/patterns/estimate-target-commitment.md`）。確定見積のあとで、ロックしたベースラインに対する変更管理が始まる。概算を制御線にするなら、その選択を名指す。

現場に確認していない To-Be は、まだベースラインではない。変更票で「改善も拾う」通路を開けると、ベンダーはベースラインを既得として増分しか見ない。見積に入っていなかった切片は外し、To-Be が描けてから見積もる。すでに消えた業務を見積に残すと、水増しに見える。減額は、行を指せなければ交渉にならない。

## Written role vs practice

体制図の持ち主と、実際にやっている人が違うときは、図を実体に直すか、実体を図に合わせる。ずれている段だけを直す。図が空に見えるから新しい横断 PMO を足さない。

不具合の最終責任が、試験や稼働の前に名前がないまま進むのは、すでにトラブルの匂いである。書面には書いてあるが動いていない、も同じである。いま協力的に回っていても、試験の前に合わせる。騒ぎを起こす話ではなく、後で「このやり方でやってきた」にならないための話である。親会社の人が説明に行く側だと、その指摘は柔らかくなりやすい。反対されること自体は失敗ではない。

月次は、新しい問題を見つける場ではない。名前の付いたリスクは、顕在化するまでリスクのまま置く。予見できた問題が突然の課題として出るのは、リスクの見落としである。本当に予見できないものは、そのままでよい。

新しい分析を、別の運用を覚えた直後の人に載せない。害が出る日を言い、いまできることと、動かしてはいけないマイルストーンを分ける。足元の着手は、全体のチェンジ計画の中の位置を示したうえで始めてよい。計画の完成を待って着手を止めない。

## Signals

- 「合意した」「運用開始」が、誰がどの粒度でかを言わない  
- 影響が1欄で、採否の材料が担当によって変わる  
- Want に改善効果や他施策との整合の勾配がある  
- Must の定義が「止まると業務ができない」または「現場が回らないと言う」  
- 現場未確認の To-Be を、変更管理で救済しようとしている  
- 概算見積と確定見積が同じ「ベースライン」になっている  
- 体制図と実務がずれているのに、新しい横断役を足そうとしている  
- 月次のために、新しい問題を探している  

## Tests

- 新人と経験者が、同じ変更で同じ Must／Want と採否になるか  
- プロセス、台帳、手引きの3点があり、埋める列が発注側とベンダーで分かれているか  
- ロック前に、回す人と1件を机上で通したか  
- 減額や対象外を、見積の行で指せるか  
- 月次の新しい行が、既存リスクの顕在化か、本当に予見できないものか
