# Pattern: FIS System Audit as Assurance

**Status:** Active  
**Origin:** Japanese financial-institution industry system-audit guidance (structure only; Program Line X). Checklist rows and proprietary item text are **not** stored here.

## Pattern statement

業界のシステム監査指針は、**チェックリストの写し**ではなく、発注側が使う**保証（assurance）の骨格**として扱う。買い手が問うのは「監査項目を埋めたか」ではなく、**どの統制クラスに対し、誰がリスクを引き受け、開発・運用・設備のどこで証拠を残すか**である。

| Stance | Success | Forbidden |
|--------|---------|-----------|
| **Buyer / assurance** | 統制クラスと責任部門が合意され、開発標準・運用設計・設備要件に証拠が載る | 指針のチェック行を仕様にコピペする |
| **Seller / delivery** | 自社成果物が監査テーマにどう対応するかを説明できる | 顧客の監査結論を代行する／未実施を「準拠」と書く |
| **External auditor** | リスク→コントロール→手続の筋が追える | 指針をそのまま監査手続にしない（細分化が前提） |

## Signals

- RFP や社内基準に「監査指針への準拠」だけが書いてあり、**どの層（技術／運用／設備／開発標準）で満たすか**が無い
- 開発プロジェクトが「運用・設備・監査は後工程」と切り、設計に証跡要件が入らない
- チェックポイント集を要件一覧に展開し、行数が増えるだけで責任者が増えない

## Underlying mechanism

監査指針の様式は概ね次の**メタ構造**を持つ（項目本文は登録しない）:

1. **要点（統制クラス）** — 計画、リスク、セキュリティ、開発、運用、利用、入出力、EUC、ネットワーク、資産、外部委託、コンティンジェンシー、文書化、など  
2. **対象の区分（大→小）** — 監査対象の切り方  
3. **リスク → コントロール → チェックポイント** — 想定リスクに対する主要な統制と、点検の粒度  
4. **被監査部門の印** — 企画／開発／運用（情報システム部門）と、本部・利用・EUC（ユーザー側）の役割分担  

つまり指針は「何を聞くか」の地図であり、「どう作るか／どう回すか」の標準そのものではない。後者は開発標準パック（ガイドライン／規約）と、技術・運用・設備の三基準層が担う。

## Implications

- **発注側:** 指針は自己点検・外部監査準備・RFP の assurance 条項の**骨格**に使う。項目の所有は企画・開発・運用・ユーザー・設備に振り分ける。  
- **開発標準との接続:** SDLC・変更管理・ドキュメントは Line H の開発管理／ドキュメント標準／リリースと対応づける。運用・監視・バックアップは運用設計／引継と対応づける。  
- **三基準との接続:** 技術＝システムが持つ耐障害・認証・防護などの**機能要件の型**、運用＝手続・権限・記録・委託などの**運用要件の型**、設備＝建物・電空・監視などの**物理要件の型**。監査テーマはこれら三層＋開発標準に**投影**する。  
- **公共防衛ドメインと混同しない:** `domains/public-defense.md` は官側調達・情報保証の文脈。本パターンは民間金融機関等の業界監査指針の使い方である。

## Response

1. まずスタンスを決める（buyer assurance / seller evidence / auditor procedure）。  
2. 統制クラス単位で「証拠は技術／運用／設備／開発標準のどこか」を表にする。  
3. チェックポイント集は原本に残し、リポジトリには**判断とマッピング**だけを残す。  
4. 設計・運用設計・引継のレビュー観点に、監査クラスへの参照を1行で足す（行の複製はしない）。

## Exceptions

- 規制当局・監査法人が指定する手続書がある場合は、その手続が優先。本パターンはその上位の**使い方**の話。  
- 非金融でも同型の「業界監査指針 → 自社標準への投影」は流用できるが、クラス名は業態に合わせて言い換える。
