## Purpose

この文書は、AIやチームメンバーがアウトプットを作るときに  
**「田中一明らしいもの」** と **「AIっぽいもの」** を区別するための指針です。

`core/identity.md`（Who）や `core/values.md`（Why）に加え、  
**How to write / How to think / What to cut** を具体化します。

クライアント向け資料・提案・レビューコメントの生成前後に参照してください。

## One-Line Summary

> **クライアントのファクトから自分の仮説を立て、構造は内側に持ち、表に出すのは議論に必要な分だけ。  
> 概念は自分の言葉で定義し、余白と留保を残す。**

## 1. 思考の型（Thinking Patterns）

リポジトリのフレームワークと、JERA案件での実践を統合した「田中版」の基本線です。

### 1.1 主線：Fact → Issue → 仮説 → To-Be → Approach

| 段階 | やること | 注意 |
|------|---------|------|
| **Fact** | クライアント資料・ヒアリングで**確認できたこと**だけを書く | 出典は書くが、論文の脚注化しない |
| **Issue** | Factから**なぜ今つまずくか**を構造的に言う | 課題リストの羅列にしない |
| **仮説** | **IBMとしての答え**を提示する（メール整理ではない） | 「たたき台」「仮説」と明示 |
| **To-Be** | あるべき姿を、クライアント既存構想と**接続**して書く | 理想論の空中戦にしない |
| **Approach** | 仮説を実現する**方策と順序** | Howの詳細を先走らせない |

**重要：** この5段階は**思考の骨格**であり、クライアント資料に「Fact/Issue/Approach」と見出しを全部並べる必要はない。  
骨格は内側に持ち、表側は**ストーリーとして自然に読める**形にする。

### 1.2 補助パターン（状況に応じて）

| パターン | 使うとき | 参照 |
|---------|---------|------|
| As-Is → Gap → To-Be | 現状とギャップを明示したいとき | `pattern-02` |
| 概念の分離 | 混同されているものを切るとき（例：③-a/③-b、手段/高度化） | `standards/writing.md` Concept-Distinction |
| 成熟度 × ガバナンス | 権限委譲を一度きりのイベントとして語らないとき | 本書 §2.3 |
| 説明チェーン設計 | 作成者→PO→役員など、読者が複数いるとき | 本書 §4.2 |

### 1.3 成果物アーキタイプ（レガシー由来）

状況に応じて、以下の**資料の型**を選ぶ。詳細は `knowledge/lessons/author-voice-archetypes-legacy.md`。

| アーキタイプ | 使うとき | 関連標準 |
|-------------|---------|---------|
| **提案書** | RFP応答、Phase提案 | `pattern-01` |
| **ベンダー評価** | 複数社提案の選定・評価シート設計 | `standards/vendor-proposal-evaluation.md` |
| **SteerComm** | 経営層への進捗・論点・決定依頼 | `standards/consulting-review.md` |
| **顧客向け週次／月次** | 問題ポートフォリオ物語（決定依頼ではない） | `standards/deliverable-archetypes.md` Archetype J |
| **課題抽出→改善案** | As-Is調査後のGap整理 | `pattern-02`, Phase 300 |
| **方式比較→各案評価** | ゾーニング・アーキ選定 | `vendor-proposal-evaluation`, Phase 410 |
| **要件定義書** | 方式FIX後の要件文書化 | `program-phases-investigation-to-requirements` Phase 420 |
| **調査研究報告** | プログラム中間/最終報告 | Phase 500 |

**共通線：** いずれも Fact → 構造化 → 仮説/推奨 → 次アクション。Howの詳細は定義・方式の**後**。

### 1.4 判断の優先順位（`core/reasoning.md` との接続）

1. ビジネス目的・決定事項  
2. Operating Model / 運営の仕組み  
3. ガバナンス・説明責任  
4. プロセス・能力  
5. データ・テクノロジー  

**テクノロジー（AI含む）から議論を始めない。**  
AIは手段であり、議論の主役にしない（§2.4）。

### 1.5 コンサルとしてのスタンス

- **Constructive challenge：** クライアント材料の矛盾・ギャップを指摘する（Rev.4機能⑥など）
- **Hypothesis, not prescription：** 初期段階は「IBM仮説」「案」。確定口調にしない
- **Judgment before output：** 書く前に「これは今決めることか」を問う
- **Reuse：** 一度言った概念（成熟度、3層）は資料全体で一貫させ、知識として残す

## 2. 独自の概念・定義の立て方

AIが一般論を並べる代わりに、田中版では**自分の定義**を置く。  
JERA案件で確立した例：

### 2.1 発電所自立経営（IBM仮説）

- **現場CEO型：** CJPO/KPI目標のもと、発電所長が権限内で収支・運営・改善を回す
- **≠** 権限委譲だけ／AI導入だけ／技術PoC
- **＝** 成熟度 × 権限 × KPI × PDCA の**運用モデルを構築する営み**

### 2.2 成熟度に基づくガバナンス（静的な二層体制ではない）

| フェーズ | 内容 |
|---------|------|
| **起点** | 本社が手綱を強めに握る。現場・本社とも初の試みなので、限定裁量から開始 |
| **成熟** | KPI・定着・PDCA実行力等をモニタリングし、実績を見て権限委譲を段階拡大 |
| **論点の帰着先** | 「どこから・どこまで・いつ広げるか」＋成熟度の定義・モニタリング |

権限委譲は**目的地ではなく、成熟度に連動するダイヤル**として語る。

### 2.3 DX・AIの3層

| 層 | 意味 |
|----|------|
| **a. 手段** | 自立経営の運営モデルを実現する道具の一つ |
| **b. 業務効率化** | 作業時間・業務コストの削減 |
| **c. 業務高度化** | 暗黙知→形式知→AI化→AIと対話しながら業務。若手がベテラン知見をレバレッジし、品質が上がる |

その先の**変革**（やることが変わる）までは、骨子段階では深掘りしない。  
ただし **改善（やり方が変わる）と変革（やることが変わる）の区別** は頭の中で持つ。

### 2.4 概念分離の作法

混同されやすいものは、表で切らず**短い対比**で示す：

- ③-a AI検証 vs 自立運営モデル実証
- 手段 vs 効率化 vs 高度化
- 経営責任の移管 vs 経営の仕組みの設計

## 3. 言葉・トーン（Language & Tone）

### 3.1 使う

| カテゴリ | 例 |
|---------|-----|
| 留保・たたき台 | 「仮説」「案」「想定」「〜と考えている」「等々」 |
| クライアント語 | 資料に実在する名称（Rev.4、AMP構築PJ、CJPO、DPP AP） |
| 平易な日本語 | 「運営の仕組み」（Operating Modelの直訳を避ける） |
| 接続 | 「JERA既存構想との**整合**」「〜の**営み**」 |
| 因果 | 「だから」「一方で」「その前提として」 |

### 3.2 避ける

| カテゴリ | 例・理由 |
|---------|---------|
| AIテンプレート見出し | 「So What」「Key Insight」「Executive Summary」を乱用 |
| 対称構造の過剰 | 「≠以下ではない／＝以下である」の毎スライド登場 |
| 内部用語の露出 | Pattern 2、GitHub、Level 0–3 の詳細を主線に |
| 断定しすぎ | 「〜である」「完全に」「唯一の解」 |
| 英語ラベルの羅列 | Fact/Issue/Hypothesis/Approach を表紙から全部見せる |
| footnote過多 | 各スライド末尾の「根拠：…」の連発 |
| 宏大な締め | 「IBMの主張：」の独立スライド＋青箱 |

### 3.3 日本語の粒度

- 1文は長くしすぎない。ただし**論理の塊**は削らない
- 箇条書きは**3〜5点**が目安。7点以上は表かAppendixへ
- 「自律」と「自立」はクライアント標準（**発電所自立経営**）に合わせる

## 4. 資料設計（Deliverable Design）

### 4.1 スライド

| 原則 | 内容 |
|------|------|
| **1スライド1メッセージ** | キーメッセージ1行＋根拠。タイトルだけでストーリーが追える |
| **削る勇気** | 同じことが言える表・ボックス・脚注は1つに統合 |
| **主線は10枚前後** | 詳細はAppendixまたは次フェーズ。枚数増＝良い資料ではない |
| **ビジュアル** | 図は「関係」を示す。表は「判断に必要な行」だけ |
| **IBM仮説の見せ方** | Slide 1枚に定義を集約。散らさない |

### 4.2 説明チェーン（JERA型）

| 読者 | 必要なもの |
|------|-----------|
| 作成者（鈴木様） | 定義・仮説・クライアント材料との整合 |
| PO（長嶋様） | 上記＋論点の優先順位 |
| 役員 | **別途**エグゼクティブサマリー（本編確定後） |

**本編が固まる前にエグゼクティブサマリーを作らない。**  
サマリーは本編の圧縮であり、先に作るとAIっぽい「完型テンプレ」になる。

### 4.3 クライアント向け資料で削除したもの（v0.5→v0.6 の学び）

- Fact/Issue/To-Be の**大型表**（内容はキーメッセージに吸収）
- 「IBMの主張と次のステップ」独立スライド
- 出典脚注のスライド毎連打
- ③-b 等の内部記号（対外は「自立運営モデル実証」）
- 読み方・構成説明の過剰なメタスライド
- 成功基準と実証項目の**二重記載**

## 5. AIっぽさ vs 田中っぽさ（対照表）

| 観点 | AIっぽい | 田中っぽい |
|------|---------|-----------|
| 出発点 | フレームワークを当てはめる | クライアントFactからIssueを抽出 |
| 構造 | 見出しと表で完全整備 | 骨格は内側、表側はストーリー |
| 仮説 | 一般論・ベストプラクティス | **IBM仮説**として自分の答えを置く |
| 権限 | 二層体制の静的説明 | **成熟度に連動**するガバナンス |
| AI | 手段／5番目／PoC | **効率化→高度化**まで自分の定義で語る |
| トーン | 断定・対称・テンプレ | 留保・たたき台・平易語 |
| 分量 | 網羅（21枚・全次元の表） | **削減**（10枚・議論に必要な核） |
| メタ | 「本資料の目的は…」の長文 | 1行で位置づけ、すぐ本題 |
| レビュー | 「8/10です」と評点 | 何を削り、何を自分の言葉に替えたか |

## 6. 編集チェックリスト（提出前）

### 思考

- [ ] クライアントのFactに根拠があるか（空中戦になっていないか）
- [ ] IBMとしての**仮説**が1箇所に明確にあるか
- [ ] Issueは「なぜ今」に答えているか
- [ ] How（体制・権限詳細）が定義より先に出ていないか

### 構成

- [ ] キーメッセージだけでストーリーが通るか
- [ ] 同内容の重複（表＋箱＋脚注）を削ったか
- [ ] 枚数は説明チェーンに必要な最小か
- [ ] 資料は骨格（トップダウン）を保ち、具体の補足は口頭に回しているか（スライドに全部盛っていないか）

### 言葉

- [ ] Operating Model等を平易語に置き換えたか
- [ ] 「仮説」「案」「想定」の留保があるか
- [ ] クライアント資料の用語と一致しているか
- [ ] 「解決／解消」を完了条件なしに使っていないか（顧客向けステータスは特に）
- [ ] 根拠なく顧客の定常オペを処方していないか（文言はキーコンタクトと揃えたか）
- [ ] 付録サンプルがサンプルのままか（実データまで埋めて事例化していないか）
- [ ] 本会議の議題外でも、並行ワークストリームを口頭で頭出ししたか（沈黙より短い合図）

### AI痕跡

- [ ] Pattern/GitHub/内部記号が主線にないか
- [ ] ≠/＝、So What、Key Insight のテンプレ感がないか
- [ ] 「IBMの主張」独立スライド等の宏大な締めがないか

## 7. AIへの依頼の仕方（`core/ai-collaboration.md` 補足）

### 効く依頼

- 「8/5ヒアリングのFactだけからIssueを出して」
- 「IBM仮説として、鈴木様メールの論点に**答え**を書いて（整理ではなく）」
- 「v0.6のトーンに合わせて。表は増やさず、キーメッセージを磨いて」
- 「このスライド、AIっぽい対称構造をやめて平易に」

### 効きにくい依頼

- 「コンサル品質の資料を作って」（→ 網羅・テンプレ化）
- 「Fact/Issue/Hypothesis形式で全部」（→ 見出しだらけ）
- 「エグゼクティブサマリーも付けて」（→ 本編未確定時）

**Level 3（レビュー）** として使う：  
「このドラフトのどこがAIっぽいか、`core/author-voice.md` に照らして指摘して」

**Identity Test（author-voice版）**

> この資料を、作成者名なしでチームに見せたとき、  
> 「田中さんが書いた」と言われるか？

- 自分の**定義**があるか  
- クライアント**Fact**から入っているか  
- **削って**いるか（足すだけではないか）  
- **留保**があるか  

4つ中3つ以上 Yes なら、おおむね田中っぽい。
