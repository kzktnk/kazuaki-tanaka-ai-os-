**Version:** v0.2

**Owner:** Kazuaki Tanaka  
**Purpose:** AMS・インフラ運用・AI運用への **移行設計** と定着化を、一人で読み進めながら Transition Manager として進める  
**Use when:** 実現化工程の後半から運用へ渡す、他社運用の take-on、定着が「説明した」で止まっている（指導者なし）  
**Do not use as-is for:** 日々の運用実務そのもの、②の PJ 間統合、①の戦略〜Gate 1、個々の相手を動かす技術（横串）、全社 AI ガバナンス  
**Source:** ③本編（`playbooks/operations-transition-playbook.md`）の自己学習版。2026-08-29。主張・型・表・演習は本編と同一。パス参照は冊名・章番号に置き換え。

## このPlaybookの目的

複数の運用ドメイン（AMS・インフラ運用・AI運用）への移行と定着化を任されたTransition Managerが、次の3つの問いに自力で答えられるようになることを目的とする。

- 運用への移行（自PJからの引き継ぎ、または他社からのTransition）をどう設計し、工数をどう見積もるか（Chapter 2〜4）
- AI運用に特有のタスク・役割・責任・スキルをどう設計し、育成につなげるか（Chapter 5・6）
- 定着化をチェンジマネジメントとしてどう進め、起きがちなトラブルにどう対処するか（Chapter 7）

AMS・インフラ運用・AI運用の日々の運用実務そのもの（インシデント対応、監視、保守作業など）は、各運用チーム・ベンダーの役割であり、本Playbookの対象外である。本Playbookが対象とするのは、**運用が始まる前の「移行設計」と、運用が始まった後の「定着」**である。

**成熟度**：Chapter 1〜4・7〜8は複数回の外部レビューを経た Core である。Chapter 5・6（AI運用のタスク・役割・スキル設計）は、姉妹framework（AI運用ロール設計）の確定待ちの **Experimental** であり、AI運用を伴わない案件を担当する場合はChapter 5・6を読み飛ばしてよい（詳細はChapter 5・6冒頭にも個別に明示）。

**射程の明示**：本Playbookは、次の既存frameworkの内容を土台に、Transition Manager一人称の実務手順として再構成した実務Playbookである。各frameworkの理論的背景・他資産とのnetwork上の位置づけは、それぞれの原典を参照されたい。

| 本Playbookが扱う実務 | 土台とする既存framework |
|---|---|
| 自PJからの運用引き継ぎ（Chapter 2） | Delivery Leadership の Service introduction |
| 他社からのTransition（Chapter 3） | Service Transition Approach、Delivery Leadership の Service transition |
| 工数見積もり（Chapter 4） | Application Outsourcing Solution Planning の Size & source、AMS Services Pyramid |
| インフラ運用固有の論点（Chapter 3・4内） | Infrastructure Outsourcing Solution Planning |
| 定着化・チェンジマネジメント（Chapter 7） | チェンジマネジメントの原典フレームワーク |

一方、AI運用のタスク・役割・責任・スキルレベル設計（Chapter 5・6）は既存frameworkが手薄な領域である。本Playbookは、姉妹framework（AI運用ロール設計。全社的なAI活用浸透ロール設計と対になる位置づけ）を参照し、Transition Managerがそれをどう実務に適用するかを扱う。

また、次の既存資産とは次の理由で棲み分ける。

- AI活用全体のガバナンス・CoE設計を扱う全社レベルの資産（別紙）とは、本Playbookが特定プログラムの移行実務に絞る点で異なる。
- 全社的なAI活用浸透の5ロール（User／Manager／Governor／Developer／Executive）を扱う資産（別紙）とは、本PlaybookのAI運用チーム自体のロール設計とは対象が異なる。

### Playbookシリーズにおける本書の位置づけ

本Playbookは単独で完結するものではなく、次の3段階からなるコンサルティング業務の一連の流れのうち、最後（実現化後の安定運用・定着化）を担うものと位置づけている。

```text

   IT戦略を含む戦略立案 → SCNによるCapability／Enablerへの分解 → KPI設定 → Gate 1 プロジェクト化
                        │
                        ▼
② Cross-Project Program Management Playbook
   複数ベンダー・複数プロジェクトを束ねる実現化工程を、統合的に管理する
                        │
                        ▼
③ Operations Transition Playbook（本書）
   AMS・インフラ運用・AI運用への移行設計と、実現化後の安定運用・定着化を担う
```

②から③への引き継ぎ地点は、単一のタイミングではなくGate構造で1.3に定義する。①はGate 1（Strategic Projectization Complete）を経て②に接続し、②はGate 2（Execution Mobilization Ready）から着手する。本Playbookは②の範囲を前提としつつ、実現化工程そのもの（②の対象）には立ち入らないことを原則とする。

## 使い方（自己学習版について）

本書は、③本編（指導者同席前提）を、一人で読み進める自己学習者向けに再構成した版である。内容・型・図表は本編と同一であり、要約や省略は行っていない。Chapter 8の演習も、指導者との対話ではなく、自分のペースで、自分で参考解答と照らし合わせながら進める前提に変更している。

1. Chapter 1で「Transition Managerは何を管理するのか」という視点を作る

4. Chapter 7で、定着化をチェンジマネジメントとして進める型を学ぶ
5. Chapter 8の演習で、実在に近いケースを使って一通り自分の手で作ってみる

読むだけで終わらせず、必ずChapter 8の演習、または自分が担当する実プログラムのどちらかで手を動かすところまでをワンセットとする。各Chapter末の振り返りメモは、指導者に問われて答えるものではなく、自分自身に問いかけるものとして使う。答えに詰まった項目があれば、そこが理解の甘い場所である。一人で判断がつかない場合は、無理に自己完結させず、先輩・上司に短く相談してよい。

## Chapter 1. Transition Managerは何を管理するのか

### 1.1 「運用そのもの」ではなく「移行設計と定着」を管理する

最初に押さえるべき最も重要なことは、次の一文に尽きる。

> Transition Managerは、AMS・インフラ運用・AI運用の日々の運用作業を自ら行う必要はない。
> Transition Managerが管理すべきは「運用が始まる前の移行設計」と「運用が始まった後の定着」である。

インシデント対応・監視・保守といった運用実務そのものは、各運用チーム・ベンダーの役割である。Transition Managerがそこに深く踏み込んで運用実務そのものを肩代わりし始めると、運用チームの当事者意識を奪い、かつTransition Manager自身がいつまでも運用のボトルネックになる。Transition Managerがやるべきは、運用が正しい形で立ち上がり、正しい体制・工数で回り、実際に組織に定着するところまでを見届けることである。

ただし、移行期（Hypercare）の間は、運用が計画どおり自走できているかを判断するために必要な範囲で、運用実務の状況を注視する。Transition Managerが「運用に関与しない」のではなく、「運用の一次責任を持たない」という意味である。

```text
移行前                  Transition Manager管理対象           移行後
─────────────      ─────────────────────      ─────────────
プロジェクトの運用設計   →  Transition Plan／KT       →   AMS・インフラ運用チーム
既存ベンダーの運用実態   →  デューデリジェンス         →   新運用体制
AI活用の役割・スキル計画  →  AI運用チームの役割設計      →   AI運用チーム
新しい運用への適応       →  チェンジマネジメント        →   現場での定着
```

「何を、いつ、どういう状態で引き継ぐか」「引き継いだ体制は、その工数・スキルで正しく回るか」「現場は実際にその新しい運用に定着しているか」を見るのがTransition Managerの仕事であり、日々のチケット対応・監視そのものはTransition Managerの一次的な仕事ではない。

### 1.2 Transition Managerの責任範囲

| 領域 | Transition Managerの責任 | 運用チーム・ベンダーの責任 |
|---|---|---|
| 運用実務（インシデント対応・監視・保守） | モニタリングのみ（一次責任なし。Hypercare期間中を除く） | 一次責任 |
| 移行設計（Transition Plan・KT計画） | 一次責任 | 計画への協力・KTの実行 |
| デューデリジェンス（他社引き継ぎ時） | 一次責任 | 既存ベンダーとしての開示協力（該当する場合） |
| 工数見積もり・体制設計 | 統合責任／成立性確認責任（作成自体はService Lead等が担う場合もある） | 見積りの作成、前提となる実態情報の提供 |
| AI運用の役割・スキル設計 | 統合責任／成立性確認責任（姉妹framework「AI運用ロール設計」を用いる） | 設計の作成・協力、現場実態のフィードバック |
| 定着化のモニタリング | 一次責任 | 新しい運用への適応・フィードバック |

工数見積もり・体制設計とAI運用の役割・スキル設計は、案件によってはService Delivery Manager・Solution Architect・AMS Solution Lead・Infrastructure Lead・AI Product Ownerなどが作成の一次責任を持つ場合がある。その場合もTransition Managerは、Transition前提（デューデリジェンスの結果、Wave計画、Ramp-upのタイミング）と整合しているかを確認する統合責任を持つ。本Playbookでどこまでの責任をTransition Managerに持たせるかは、育成対象・組織構造に応じて調整してよい。

### 1.3 ②（PgMO）との接続点 ―― Gate構造による橋渡し

①はGate 1（Strategic Projectization Complete）を経て②へ接続し、②はGate 2（Execution Mobilization Ready）から着手する（①、②）。②から③への接続も、同じ考え方でGateを置く。

> ②から③への引き継ぎ地点は「Steady Stateに入るタイミング」ではない。Transition Planの設計は②の実現化工程が完了に近づく段階から並行して始まるため、引き継ぎはもっと早い時点から段階的に進む。

| Gate | 内容 | 主な確認項目 |
|---|---|---|
| **Gate 3** Service Transition Planning Ready | ②の実現化工程が完了に近づき、Transition設計に着手できる状態 | 本番移行予定、運用対象スコープ、運用方式、運用受入先、初期RAID、Transition Managerアサイン |
| **Gate 4** Responsibility Transfer Ready | 運用責任を正式に移転できる状態（Chapter 3.6のResponsibility Dateに対応） | KT Sign-off、Runbook、ツール／アクセス、SLA、要員体制、Go/No-Go条件 |
| **Gate 5** Steady State Accepted | Transition Close完了（Chapter 3.6）かつAdoption Definition of Done達成（Chapter 7.6）の両方を満たし、③としての活動を終了できる状態 | Hypercare終了、SLA安定、自己完結、Critical RAIDなし、定着指標達成 |

②と③は、Gate 3から並走する。Gate 4で運用責任が正式に移転し（Chapter 3.6のResponsibility Date）、Gate 5でTransition CloseおよびAdoption Definition of Doneの双方を満たして③としての活動を終える（Chapter 3.6、Chapter 7.6）。①→②のGate 1／Gate 2と合わせると、シリーズ全体は次の5段階でつながる。

```text
Gate 1            Gate 2              Gate 3               Gate 4                Gate 5
Strategic     →  Execution       →   Service Transition →  Responsibility   →   Steady State
Projectization    Mobilization        Planning Ready        Transfer Ready        Accepted
Complete          Ready
  (①完了)          (②着手)             (②③並走開始)          (③へ責任移転)          (③終了)
```

②のGate 2到達時点では、Transition Managerのアサインはまだ確定していないことが多い。Gate 3の確認項目に「Transition Managerアサイン」を含めているのはそのためであり、②の実現化工程の後半で、PgMOがTransition Manager候補と早期にすり合わせておく。

**RAIDの継続利用**：③独自のRAID Logを新たに作るのではなく、②のRAID Log（②Chapter 8.3）を③でも継続利用し、次のTransition Category（分類）を追加する。

- SMEアクセス
- 契約終了
- ツール権限
- KT不足
- Warranty境界
- Shadow Support
- Adoption抵抗
- AI運用スキル不足

②から③への引き継ぎ資料（Dependency Register・Consistency Matrix・RAID Log）は、Gate 3の時点でTransition Managerへ引き継ぐ。RAID Logが②③で分断されると、実現化工程で認識していたリスクが運用移行フェーズで見失われるため、同一Logを使い続けることを原則とする。

小規模プログラムではPgMOとTransition Managerを同一人物が兼任することも多い。その場合の注意点は、②のChapter 1.5（PgMOとPMOを兼任する場合の注意点）と同様の構造で整理できる可能性が高い。詳細は実務での振り返りを踏まえ、本書のレビュー時に必要に応じて追加する。

### 1.4 体制図 ―― Transition Managerはどこに立つのか

②の体制図（Steering Committee・Program Director・PgMO・Vendor PM）を踏襲しつつ、運用移行フェーズでは次の関係者が加わる。

```text
                Steering Committee
             （Program Sponsor／経営層）
                        │
                 Program Director
                        │
          ┌─────────────┴─────────────┐
        PgMO（②）                Transition Manager（③）
  （実現化工程の統合管理）      （運用移行の設計・実行・定着化）
                                        │
        ┌───────────────┼───────────────┐
   AMS運用チーム      インフラ運用チーム       AI運用チーム
  （既存 or 新規       （既存 or 新規          （既存 or 新規
   ベンダー）           ベンダー）              ベンダー・社内チーム）
```

PgMOとTransition Managerは、1.3で述べた通り一時期並走する。両者が別人である場合、この図の左右を橋渡しする引き継ぎ会議体を、②の実現化工程完了前にあらかじめ設計しておく必要がある。

### 1.5 2つの移行シナリオ ―― 自PJからの引き継ぎ と 他社からのTransition

運用への移行には、性質の異なる2つのシナリオがある。この違いを最初に区別しておかないと、必要な準備がまったく異なるにもかかわらず、同じ手順で臨んでしまう。

シナリオを分ける本質的な軸は、「開発した会社が同じか違うか」ではなく、**運用実態が既知か、デューデリジェンスで発見しなければならないか**である。

> シナリオA＝既知のDelivery Knowledgeを持つ側からのIntroduction
> シナリオB＝既存運用実態そのものを再発見する必要があるTransition

自社が開発したシステムでも、開発から時間が経ち担当者が入れ替わっていれば実質的にシナリオBに近づく。逆に、他社が開発したシステムでも、直近まで自社と密に連携しながら運用してきた場合はシナリオAに近い。「誰が作ったか」は判定の出発点にすぎず、最終的には運用実態が既知かどうかで判定する。

| | シナリオA：自PJからの引き継ぎ（Chapter 2） | シナリオB：他社からのTransition（Chapter 3） |
|---|---|---|
| 前提 | 自分たちが要件定義・設計・開発を行ったシステムを、運用チームへ引き継ぐ | 既に他社が開発・運用していたシステムを、新しい運用体制で引き継ぐ |
| 判定の本質 | 運用実態（設計意図・既知の制約・トラブル履歴）が引き継ぐ側にすでに知られている | 運用実態が引き継ぐ側にとって未知であり、発見（デューデリジェンス）が必要 |
| 最大のリスク | 開発チームの知識が運用チームに正しく移転されないまま稼働してしまう | 引き継ぐ対象の実態（技術的負債・属人化・ドキュメント不備）が見えないまま契約・体制を決めてしまう |
| 最初にやること | Warranty（保証）期間の定義とKT計画の設計 | デューデリジェンスによる実態把握 |
| 主な拠り所 | Service Introduction（Chapter 2） | デューデリジェンス＋Service Transition（Chapter 3） |

実務では、この2つが1つのプログラムの中で同時に発生することも珍しくない（例：新規開発部分は自PJからの引き継ぎ、既存の周辺システムは他社からのTransition）。その場合は、対象システムごとに「運用実態が既知か、発見が必要か」でどちらのシナリオに当たるかを最初に仕分けることが、Chapter 2・3を使う前提になる。

## Chapter 2. 自PJからの運用引き継ぎ

### 2.1 Service Introductionとは何か ―― 「動くこと」と「支えられること」は別

自分たちが要件定義・設計・開発したシステムを運用チームへ引き継ぐ場面は、他社からのTransition（Chapter 3）と比べて「勝手が分かっている」ため軽視されやすい。しかし、Service Introductionで問うべきことは2つあり、この2つは別物である。

> システムが動くことと、運用チームがそれを支えられることは、別の問題である。

「動作すること」の検証は開発・テストチームの仕事としてすでに行われている。Service Introductionで新たに検証すべきは、「運用チームが、そのシステムを、開発チームの助けなしに支えられる状態にあるか」である。ここを混同すると、開発チームが本来的な意味で手を離せないまま、形式上だけ運用移管したことになってしまう。

### 2.2 引き継ぎ前のチェック：Operability（動作の健全性）

| チェック項目 | 内容 |
|---|---|
| リハーサル | 本番相当の環境・データ量で、運用開始後に想定される作業（障害対応、定期処理、バッチ、リリース）を実際に一度動かしてみる |
| Go/No-Go基準 | 「これが満たされていなければ移行しない」という基準を、移行日の直前ではなく計画段階で合意しておく |
| Post-Implementation Review | 移行後、一定期間（目安：Warranty期間終了時）を置いて、想定通り安定稼働しているかを振り返る |

Go/No-Go基準は、開発チーム側の「機能要件を満たしている」という基準だけでなく、2.3で述べる運用チーム側の準備状況も含めて合意する。

### 2.3 引き継ぎ前のチェック：運用チームの準備状況

技術的な健全性とは別に、運用チーム側の準備状況を独立して確認する。

- 運用手順書（Runbook）が、開発チームの助けなしに読めて実行できる粒度で存在するか
- エスカレーション経路（誰が、どのレベルで、誰に連絡するか）が定義され、関係者に共有されているか
- 監視・アラートの閾値が、開発チームの知見をもとに設定されているか（デフォルト値のまま移行していないか）
- 運用チームが、少なくとも1回はリハーサルまたは実運用に近い状況を経験しているか

この4点のいずれかが欠けたまま移行日を迎えると、移行直後のインシデントで開発チームへのエスカレーションが常態化し、実質的にService Introductionが完了しないまま時間だけが過ぎる。

### 2.4 Warrantyの設計 ―― 「保証」は「運用」ではない

Service Introductionで最も誤解されやすいのがWarranty（保証）期間の位置づけである。

> Warrantyは、移行時点で埋め込まれていた欠陥を無償で直す期間であり、運用そのもの（インシデント対応・問い合わせ対応）を提供する期間ではない。

この区別を移行前に合意しておかないと、Warranty期間中に運用チームから寄せられるあらゆる問い合わせ・要望に開発チームが応じ続けることになり、開発チームの本来の異動・アサイン変更ができないまま期間だけが延びる。Warranty設計で決めておくべきことは次の3点である。

1. **対象範囲**：Warrantyの対象は「移行時点で存在した欠陥の修正」に限るのか、軽微な追加要望も含むのか
2. **期間**：一般的な目安はあるが、システムの複雑度・運用チームの習熟度に応じて個別に判断する
3. **体制**：Warranty期間中、設計・開発チームの誰が、どの程度の稼働割合で残るか。全員をすぐに他アサインへ異動させると、欠陥修正の質が落ちる

### 2.5 KTの設計（自PJ版）

自PJからの引き継ぎであっても、開発チームの暗黙知が運用チームに正しく移転されなければ、2.1で述べた「支えられる状態」には到達しない。KTの具体的な進め方はChapter 3.5（他社からのTransitionにおけるKT実行）と共通する部分が多いため、ここでは自PJ特有の論点のみ述べる。

自PJからの引き継ぎでは、開発チームが「自分たちには当たり前すぎて、わざわざ説明するまでもない」と感じている情報ほど、実は運用チームにとって最も欠けている情報であることが多い。これは他社から引き継ぐ場合には（お互い前提が違うことが明白なため）むしろ起きにくく、自PJ引き継ぎに特有のリスクである。KT実施前に、開発チームに「運用チームに聞かれて即答できなかったこと」を振り返らせる、または実際に運用チームに一次対応させてみて詰まった箇所を洗い出す、といった形で、暗黙化した前提を意図的に掘り起こす必要がある。

### 振り返りメモ（自己学習用）
- [ ] 担当システムのGo/No-Go基準を、移行日直前ではなく今の時点で明文化できているか
- [ ] Warrantyの対象範囲・期間・体制の3点を、運用チームと合意できているか
- [ ] 開発チームに「当たり前すぎて説明していないこと」を意識的に振り返らせたか

## Chapter 3. 他社からのTransition

### 3.1 デューデリジェンス ―― Transition Planを設計する前に、実態を見る

他社（既存ベンダー、または他の開発元）が構築・運用してきたものを引き継ぐ場合、最初に行うべきはTransition Planの設計ではなく、デューデリジェンスによる実態把握である。

> Transition Planは、実態が分かって初めて設計できる。実態が分からないまま計画を先に立てると、その計画は最初から前提が崩れている。

デューデリジェンスで確認すべき典型項目は次の通りである。

| 観点 | 確認すること |
|---|---|
| ドキュメント | 運用手順書・構成情報が、実態と一致した形で存在するか。存在しても更新が止まっていないか |
| 属人化 | 特定の担当者しか知らない領域がどれだけあるか。その担当者が引き継ぎに協力的か |
| チケット・変更履歴 | 過去のインシデント・変更の傾向から、実際の運用負荷・複雑度を推定できるか |
| 環境・データアクセス | 引き継ぎ作業に必要な環境・ツール・データへ、いつからアクセスできるか |
| 契約・ライセンス | 既存ベンダーとの契約終了条件、ライセンスの帰属・移管可否 |

デューデリジェンスの結果は、Transition Planの前提だけでなく、Chapter 4で扱う工数見積もりの前提にもなる。デューデリジェンスが不十分なまま見積もった工数は、実態が判明した時点でほぼ確実に崩れる。

### 3.2 Transition Planの原則

デューデリジェンスを踏まえてTransition Planを設計する際、次の6原則を軸に置く。

1. **共同計画**：クライアントとプロバイダーが共同でオーナーシップを持つ。どちらか一方が「引き渡すだけ」「受け取るだけ」という受け身の姿勢では機能しない
2. **Wave単位での引き継ぎ**：リスク・依存関係・準備状況に応じて段階的に引き継ぐ。実績のない場合、一斉引き継ぎ（Big Bang）は避ける
3. **責任移転の前にKTを完了させる**：ナレッジトランスファーの品質ゲートを、運用責任の移転より前に置く
4. **並行ワークストリーム**：プログラム管理・サービスマネジメント設計・KT・ツール環境・要員体制準備を並行して進める
5. **完了基準の明示**：「いつ責任が移るか（Responsibility Date）」をWaveごとに明示し、暗黙のうちに移った状態にしない
6. **SMEアクセスを含むガバナンス**：既存ベンダー側のSME（有識者）へのアクセス・ツールアクセス・ドキュメント提供を、契約上の前提として合意する

### 3.3 Transition Lifecycle

```text
Plan（共同計画）
   ↓
Prepare（環境・ツール・アクセス・体制の準備）
   ↓
Assess KT（KT実施可否の評価：ドキュメント・SME・サンプル代表性）
   ↓
Execute KT（構造化セッション・シャドーイング）
   ↓
Pilot／並行run（フォールバックを残した限定的な本番対応）
   ↓
Responsibility transfer（Waveごとの正式な運用責任移転）
   ↓
Steady state（Hypercare終了、通常運用体制へ）
```

Assess KTを軽視して先にExecute KTへ進むと、ドキュメント不備やSME不在に途中で気づき、KTをやり直すことになる。Assess KTは形式的な通過点ではなく、進めてよいかどうかの判断点として扱う。

### 3.4 Wave設計

次のような場合、一斉引き継ぎではなくWaveに分割する。

- アプリケーション群の成熟度に差がある（レガシーと新規ERPが混在するなど）
- 対象範囲・言語カバレッジが段階的に拡大する
- 既存ベンダーとの契約終了日が対象ごとに異なる
- 特定領域（インターフェースなど）にリスクが集中している

各Waveでは、次を定義する。

| 要素 | 内容 |
|---|---|
| スコープ | 対象となる領域・システム |
| 開始／終了 | 計画期間と責任移転日 |
| 前提条件 | アクセス・データ・既存ベンダーの協力 |
| Exit基準 | SLAを満たせる状態、未解決課題の許容件数 |
| フォールバック | ロールバック、または並行run延長のトリガー |

### 3.5 KT（ナレッジトランスファー）の実行

**実行前の評価（Assess KT）**：ドキュメント在庫とギャップ分析、SMEマップと稼働可能時期、サンプルチケット・変更履歴の代表性、環境・データアクセスの準備状況、言語・タイムゾーンのカバレッジギャップを確認する。

**実行方法**

| 方法 | 使う場面 |
|---|---|
| 構造化セッション | プロセス・アプリケーション概要・主要シナリオの説明 |
| Job Shadowing | 既存担当者が作業し、引き継ぐ側が観察する |
| Reverse Shadowing | 引き継ぐ側が作業し、既存担当者が確認・是正する |
| Runbook／Playbook作成 | 暗黙知を運用アーティファクトとして明文化する |
| Pilot Support | 限定的な本番チケットを、エスカレーション経路を残した状態で対応する |

**Sign-off**：責任移転の前に、領域（Tower）ごとにコンピテンシー基準を満たしたことを確認する。「セッションを受けた」ことと「独力で対応できる」ことは別であり、Sign-offは後者を確認するものである。

### 3.6 マイルストーンとJoint Governance

**マイルストーンの型**（クライアントに応じて呼称は変えてよい）

| マイルストーン | 意味 |
|---|---|
| Transition Kickoff | 共同計画が承認され、体制が動き出す |
| KT Complete（Wave n） | 該当Waveのコンピテンシーサインオフ完了 |
| Parallel Operations Start | フォールバックを残した状態で、引き継ぐ側が対象範囲を扱い始める |
| Responsibility Date | 引き継ぐ側が該当WaveのSLAを正式に負う |
| Hypercare End | 強化サポート期間が終わり、通常運用体制へ |
| Transition Close | 全Wave完了、プログラムとして正式にクローズ |

**クライアント側の協力事項**：KTのためのSME稼働時間、ツール・システムへのタイムリーなアクセス、既存ベンダーの協力、論点整理のための意思決定の場、完了基準への合意。これらはTransition Planと契約スケジュールの両方に明記しておく。

### 3.7 リスクと対処

| リスク | 対処 |
|---|---|
| ドキュメント不備 | Assess KTをゲートとして機能させる、並行run期間を延長する |
| SME不在 | 契約上のSME稼働を確保する、経営層へのエスカレーション経路を用意する |
| 既存ベンダーの非協力 | 複数ベンダーが並存する期間のガバナンスルールを明確化する、Exit条項を確認する |
| ツールアクセスの遅延 | 環境準備ワークストリームを早期に立ち上げ、クリティカルパスとして追跡する |
| 責任移転時点でのスコープ曖昧さ | Waveごとに、L3スコープ（Chapter 4.2）に紐づいたExit基準を設定する |
| 移行時の問い合わせ急増 | サージ要員計画を用意し、Hypercareの定義を明確にしておく |

### 3.8 ERPからAMSへの引き継ぎという典型パターン

ERP導入プロジェクトの後にAMSが立ち上がる場合、次のパターンが典型的である。

- 導入パートナーがWarranty（Chapter 2.4）を持ち続けたまま、AMSプロバイダーが並行して立ち上がる
- KTは、導入チームが構成したモジュールについて実施する
- Waveは、モジュールのGo-Live順序に合わせる
- インターフェースとバッチジョブは、多くの場合最後にTransitionする

このパターンでは、シナリオA（自PJ引き継ぎ、Chapter 2）とシナリオB（他社Transition、Chapter 3）が同時並行で発生する。導入パートナー自身がAMSも担う場合はシナリオAに近づき、別会社がAMSを担う場合はシナリオBの要素が強くなる。

### 振り返りメモ（自己学習用）
- [ ] デューデリジェンスの5観点（ドキュメント・属人化・チケット履歴・環境アクセス・契約）を、Transition Plan着手前に確認したか
- [ ] Waveに分けるべき理由が、担当プログラムにあるかどうかを判断できたか
- [ ] Sign-offの基準を「セッションを受けた」ではなく「独力で対応できる」で設計できているか

## Chapter 4. 工数見積もりの勘所

### 4.1 見積もりは「どう運用するか」が決まってから始まる

工数見積もりを、対象システムの規模（画面数・テーブル数など）だけから機械的に算出しようとすると、高い確率で外れる。見積もりの前提として、まず次の2つが決まっている必要がある。

1. デューデリジェンス（Chapter 3.1）で把握した「実態」（As-Is）
2. To-Beの運用モデル（誰が、どのレベルで、何を担うか）

この構造は、「As-Is → Gap → To-Be」という思考パターンそのものである。As-Isを飛ばしてTo-Beと見積もりを先に進めると、Gapの根拠がないまま数字だけが独り歩きする。

なお、見積もりの作成自体はService Delivery ManagerやSolution Architectが担う案件もある。その場合もTransition Managerは、1.2で述べた統合責任として、見積もりがデューデリジェンスの結果・Wave計画・移行期のRamp-upと整合しているかを確認する。

### 4.2 スコープを結んでから人数に落とす ―― L1/L2/L3という2つの意味

見積もりの土台になるのが、運用スコープの階層整理である。ここで注意が必要なのは、「L1/L2/L3」という言葉が、実務では2つの異なる意味で使われることである。

**スコープ階層としてのL1/L2/L3**（「何が対象か」を決める）

| 階層 | 内容 | 例 |
|---|---|---|
| L1（サービスドメイン） | 契約に含まれる大きな領域 | Application Management |
| L2（サービスタワー） | L1の中の論理的な塊 | ERPアプリケーション支援、レガシーアプリケーション支援 |
| L3（サービスコンポーネント） | 繰り返し発生する具体的な作業単位。SLA・KPIで測定可能な粒度であるべき | インシデント管理、問題管理、変更支援、エンハンスメント |

**運用階層としてのL1/L2/L3**（「誰が対応するか」を決める）

| 階層 | 内容 |
|---|---|
| L1（サービスデスク） | 一次受付、既知の手順での一次対応 |
| L2（機能・技術サポート） | 原因調査、設定変更、データ修正 |
| L3（深い技術対応） | コードレベルの修正、性能対応、ベンダーエスカレーション |

見積もりでは、まずスコープ階層でL1〜L3の対象範囲を確定し（AM・開発・インフラの境界を明示する）、そのうえで運用階層のL1〜L3ごとに必要人数を積み上げる。この2つを混同したまま「L1/L2/L3の人数」とだけ会話すると、話している内容がスコープの話なのか体制の話なのか、途中で食い違う。

### 4.3 見積もりアプローチの選び方

対象システムの性質によって、適した見積もりアプローチは異なる。

**Bottom-up（パッケージERP・計測されたアプリケーション向け）**

| 要素 | 例 |
|---|---|
| 規模 | ユーザー数、トランザクション量、モジュール数 |
| サポート実績 | チケット発生率、解決時間、変更依頼の内訳 |
| 複雑度 | カスタマイズの深さ、インターフェース数、規制対応の重さ |
| 提供体制 | オンサイト／リモート比率、言語カバレッジ |
| 生産性 | ツール化・自動化・ナレッジ再利用の度合い |

**Top-down（レガシー・混在環境向け）**

| 要素 | 例 |
|---|---|
| ポートフォリオ | アプリケーション数、プラットフォームの多様性 |
| カバレッジ | サポート時間帯、エスカレーション経路 |
| 引き継ぎ負荷 | 既存ベンダーからの移行工数 |
| リスク調整 | ドキュメント不明点、SME依存度 |

デューデリジェンス（Chapter 3.1）で十分な実績データ・ドキュメントが得られた対象にはBottom-upを、実態が不透明な対象にはTop-downを使う。同一プログラム内でも、対象システムごとにアプローチを使い分けてよい。

### 4.4 要員ピラミッドと拠点戦略

4.2の運用階層L1〜L3に対応させて、人数だけでなく経験レベルの構成（ピラミッド）を設計する。複雑度の高いタワーほど、シニア層の比率を高くする。

**移行期は定常運用より一時的にシニア層を厚くする**。引き継ぎ直後は不確実性が高く、経験の浅いメンバーだけでは判断が滞留するためである。Hypercare終了に向けて段階的にシニア比率を下げていく計画を、最初から見積もりに織り込んでおく。この計画は、「なぜ最初だけ人数（コスト）が高いのか」を契約・予算の交渉材料として説明する際にも使える。

拠点戦略（オンサイト・ニアショア・オフショアの配分）も、この段階であわせて決める。

| 軸 | 問い |
|---|---|
| スキル | タワーごとに必要な深さ（機能知識・技術・言語） |
| 近接性 | ガバナンス・重大インシデント対応にオンサイトが要るか |
| タイムゾーン | Follow-the-sunか、単一シフトで足りるか |
| コストと品質 | ピラミッド構成とSLAリスクのバランス |
| データ・コンプライアンス | データ所在地・アクセス・監査要件 |
| クライアントの意向 | 既存の関係、過去のオフショア経験 |

### 4.5 前提条件（Assumption）を明文化する

見積もりが崩れる最大の要因は、前提条件を書き残さないまま数字だけを提示することである。②のRAID（Risk／Assumption／Issue／Dependency、②Chapter 8.3）と同じ考え方で、見積もりの前提となったAssumption（デューデリジェンスで確認できなかった点、正式資料化されていない口頭確認事項など）を明文化し、後から検証できる状態にしておく。前提が崩れた時点で、見積もりも見直すという運用をあらかじめ合意しておく。

### 4.6 見積もりが崩れる典型パターン

| 失敗パターン | 対処 |
|---|---|
| As-Is把握が甘いままTo-Beと見積もりを進める | デューデリジェンス（3.1）を見積もり着手のゲートにする |
| AM・開発・インフラの境界が曖昧なままスコープを積む | 4.2のスコープ階層L1〜L3を先に確定させる |
| 前提を書かずに数字だけ提示する | 4.5のAssumption明文化を徹底する |
| 移行期の工数を定常運用と同じ前提で見積もる | 4.4のシニア層厚めの移行期設計を織り込む |

### 振り返りメモ（自己学習用）
- [ ] デューデリジェンスとTo-Be運用モデルの両方が固まってから見積もりに着手しているか
- [ ] スコープ階層（L1〜L3）と運用階層（L1〜L3）を区別して会話できているか
- [ ] 見積もりの前提（Assumption）を、後から検証できる形で書き残しているか

## Chapter 5. AI運用のタスク・役割・責任設計

> **成熟度：Experimental（Pending framework validation）** ―― 本Chapterは姉妹framework（AI運用ロール設計、Status: Draft）を土台にしている。同frameworkがレビューされ確定するまで、4ロール構成・社内外の切り分けなどの記述は暫定として扱うこと。Chapter 2〜4・7（比較的成熟）とは扱いを分ける。

### 5.1 いつAI運用の設計を始めるか ―― AMS・インフラ運用との違い

Chapter 2・3で扱ったAMS・インフラ運用の移行には、必ず「引き継ぎ元」が存在した。自PJが開発したものであれ、他社が運用してきたものであれ、参照できる実態があった。AI運用には、多くの場合その参照先が存在しない。対象のAIシステム自体が新規である場合、デューデリジェンス（Chapter 3.1）で調べる「既存の運用実態」がそもそも存在しないためである。

> AI運用の体制設計は、Transition Planの実行段階ではなく、対象AIシステムのスコープが固まった時点から始める。

AMS・インフラ運用の引き継ぎがTransition Plan（Chapter 3）の実行フェーズで具体化するのに対し、AI運用は体制そのものをゼロから設計する必要があるため、着手のタイミングを早める。目安として、②の実現化工程でAIシステムの要件が固まった段階（本番稼働の3〜6か月前が目安になることが多い）で、AI運用ロール設計の姉妹frameworkを使ったタスクの棚卸しに着手する。

### 5.2 タスクの棚卸し ―― 6カテゴリを対象システムに当てはめる

姉妹framework「AI運用ロール設計」が定義する6つのタスクカテゴリ（モデル・品質監視／プロンプト・モデル管理／Human-in-the-Loopの運用／再学習・更新サイクル／フィードバックとナレッジ化／コスト・利用状況モニタリング）は、すべてのAIシステムに同じ重みで当てはまるわけではない。対象システムごとに、次のように棚卸しする。

| カテゴリ | 確認する問い |
|---|---|
| モデル・品質監視 | 精度・品質の劣化が、業務に致命的な影響を与えるか |
| プロンプト・モデル管理 | LLMベースか。プロンプトの変更頻度はどの程度想定されるか |
| Human-in-the-Loopの運用 | 誤判断が許容できない業務か。人間のレビューを常に挟む設計か |
| 再学習・更新サイクル | モデルは固定か、継続的に再学習する想定か |
| フィードバックとナレッジ化 | ユーザーからの訂正・フィードバックを収集する仕組みがあるか |
| コスト・利用状況モニタリング | 従量課金のAPI・モデルを利用するか |

「該当なし」と判断したカテゴリは、体制設計から外してよい。すべてのカテゴリに手厚い体制を組む必要はなく、対象システムの性質に応じて重み付けする。

### 5.3 体制の初期設計 ―― 4ロールを何人でどう埋めるか

小規模なプログラムでは、姉妹framework「AI運用ロール設計」が定義する4ロール（AI Ops Monitor／Engineer／HITL Reviewer／Lead）を、4人の専任者で埋められるとは限らない。実務でよくある組み方は次の通りである。

- 立ち上げ期は、Monitor役とEngineer役を1名が兼任することが多い（タスク量が少ないため）
- HITL Reviewerは、多くの場合専任ではなく、業務部門のドメインエキスパートが稼働の一部を割く形になる
- AI Ops Leadは、立ち上げ期はTransition Manager自身、またはTransition Managerが指名する担当者が兼任することが多い

体制は、5.2の棚卸し結果（どのタスクカテゴリが重いか）に応じて調整する。モデル・品質監視とプロンプト・モデル管理の負荷が高いシステムでは、Engineer役を早期に専任化する。Human-in-the-Loopの負荷が高いシステムでは、HITL Reviewerの稼働時間を先に確保する。

### 5.4 責任分担表

主要な意思決定について、誰が一次責任を持ち、誰が相談され、誰が最終承認するかを明確にする。

| 意思決定 | 一次責任 | 相談 | 承認 |
|---|---|---|---|
| 日次アラートへの一次対応 | AI Ops Monitor | ― | ― |
| モデル・プロンプトの変更 | AI Ops Engineer | HITL Reviewer | AI Ops Lead |
| フラグの立った個別判断の上書き | HITL Reviewer | ― | ― |
| 再学習の実施判断 | AI Ops Lead | AI Ops Engineer、HITL Reviewer | Governor（全社AI活用浸透ロールの原典） |
| AI運用の停止・縮退判断 | AI Ops Lead | Transition Manager | Governor、Executive |

「再学習の実施判断」「停止・縮退判断」は、AIガバナンスの原典が定めるRisk Ownership原則に沿い、AI Ops Lead単独ではなくGovernorへのエスカレーションを経由する設計とする。

### 5.5 社内外判断を体制・契約に落とす

姉妹framework「AI運用ロール設計」の社内外の切り分けは、実際の体制設計では次の順序で適用する。

1. 立ち上げ期は、4ロールすべてを内製で立ち上げる（外部化前提で設計すると、5.2で洗い出したタスクの重み付けが検証できないまま契約してしまう）
2. Hypercare終了後、実績とRunbookが十分に蓄積されたタスクから、AI Ops Monitorの外部化を検討する
3. Engineer・HITL Reviewer・Leadは、原則として内製を維持する（姉妹framework「AI運用ロール設計」の判断基準通り）

外部化を検討する際も、AI Ops Engineerの技術的な窓口機能（プロンプト・モデルの変更判断）は自社に残す。これは、Chapter 3.2のTransition Planの原則（責任移転の前にKTを完了させる）と同じ考え方で、外部化する場合もKTに相当する引き継ぎ期間を設ける。

## Chapter 6. AI運用のスキル・レベル・教育ロードマップ

> **成熟度：Experimental（Pending framework validation）** ―― Chapter 5と同じ理由により、本Chapterも姉妹framework（AI運用ロール設計）のレビュー確定まで暫定として扱うこと。

### 6.1 現在地を測る ―― 誰がどのレベルにいるか

姉妹framework「AI運用ロール設計」のRole × Maturity Levelを使って、まず現在のメンバーがどのレベルにいるかを可視化する。自己申告だけに頼らず、次のような具体的な証跡で判断する。

- Level 1〜2の判定：既知のインシデント種別について、Runbookなしで対応手順を説明できるか
- Level 3の判定：過去3か月で、モニタリング閾値やRunbookの改善を1件以上提案した実績があるか
- Level 4以上の判定：AI特有の根本原因分析（ドリフト・幻覚クラスタなど）を、他者の助けなしにリードした実績があるか

判定は、AI Ops Lead（5.4）が行い、Transition Managerは体制全体のレベル分布を把握する立場に立つ。

### 6.2 教育ロードマップを組み立てる

姉妹framework「AI運用ロール設計」のCore／Domain／Missionの3層に沿って、次の順で教育計画を組み立てる。

1. **Core（年次）**：全メンバー共通。監視ツールの操作、Runbookの理解、インシデント対応の基本。立ち上げ期は、ここを最優先で固める
2. **Domain（四半期）**：担当するユースケース群に共通するモデル知識。既存のAMS運用者にAI運用を追加する場合、ここが最大のギャップになりやすい
3. **Mission（プロジェクト単位）**：特定ユースケース固有の例外パターン。5.2のタスク棚卸しで重み付けした領域を優先する

Level 3（Improve）以降は、外部研修だけでは到達しにくい。社内にHITL Reviewer経験者がいる場合は、その知見をDomain・Mission層の教育に組み込む。いない場合は、立ち上げ期の一定期間、外部の専門人材を招いてOJT形式で育成する計画をあらかじめ織り込んでおく。

### 6.3 ゼロからの立ち上げ ―― Level 3以上が社内に存在しない場合

AI運用は新しい機能であることが多く、プログラム開始時点でLevel 3以上の人材が社内に一人もいないケースは珍しくない。この場合、次のいずれかで補う。

| 選択肢 | 向いている状況 |
|---|---|
| 外部人材の期間限定招聘 | 早期にLevel 3以上の判断が必要で、社内育成を待てない場合 |
| 外部ベンダーとの伴走型契約 | AI Ops Engineerの技術面を、契約期間中に併走しながら内製化していく場合 |
| Governor・Developer（全社AI活用浸透ロール）からの一時的な支援 | 全社的にAI活用を推進する体制が既にあり、そこから応援を受けられる場合 |

いずれの場合も、最終的にはLevel 3以上を内製で持つことを目標とする（姉妹framework「AI運用ロール設計」の社内外の切り分けで、Engineer・Lead は内製が基本とされているため）。外部人材・ベンダーの活用は、内製化までの橋渡しと位置づける。

### 6.4 Transition Planとの時間関係

教育は、Hypercare（Chapter 3.3・3.6）が始まってから慌てて行うのではなく、Pilot／並行run開始（Chapter 3.3）までにCore層を完了させておく。Domain・Mission層は、並行run期間中の実地経験と組み合わせながら進めてよい。

Hypercare終了時点でチーム全体がLevel 2に到達していることを、実質的な定着化（Chapter 7.1）の判断材料の一つとして扱う。

### 6.5 レベル分布のモニタリング

Chapter 7.6で定義した定着化のモニタリング指標に、AI運用チームについては次を追加する。

## Chapter 7. 定着化とチェンジマネジメント

### 7.1 定着化とは何か ―― 「移行が完了すること」と「定着すること」は別

> Transition Close（Chapter 3.6）は、Waveの技術的な作業が完了したことを示すマイルストーンであり、現場がその新しい運用を実際に信頼し、使いこなしていることを保証するものではない。

Transition Closeの時点で、SLA上の責任は正式に新しい運用チームへ移っている。しかし現場のユーザーが実際に新しい窓口・新しいプロセスを使っているとは限らない。旧ベンダーの担当者へ個人的に連絡を取り続けている、正規のチケット起票を経ずに直接メールで依頼している、といった状態は、技術的にはTransition Close後であっても、実質的にはまだ定着していない。

Transition Managerは、Transition Close（技術的な完了）と定着化（実質的な完了）を別のマイルストーンとして扱い、後者にも明示的な完了基準を持つ必要がある（7.6）。

### 7.2 Readiness ―― 定着化の準備は移行設計と同時に始める

チェンジマネジメントの原則は、コミュニケーション計画を立てる前に、まずReadiness（組織がこの変化を吸収できるか）を確認することを求めている。運用移行においても同様で、Transition Plan（Chapter 3）の設計と並行して、次を確認しておく。

- 過去に運用ベンダー・運用チームが交代した経験があるか。あった場合、その時の受け止められ方はどうだったか
- 現場が最も抵抗を示しそうな変化は何か（窓口が変わること自体か、対応スピードへの不安か、旧担当者との関係が切れることへの寂しさか）
- 「今の運用者への信頼」対「新しい運用者への不安」のギャップがどの程度あるか

Readinessを確認せずに7.3（Strategy）へ進むと、実際には抵抗が強い現場に対して、抵抗がない前提のコミュニケーション計画を当ててしまう。

### 7.3 Strategy ―― Waveは技術の単位であると同時に、変化の単位でもある

Chapter 3.4のWave設計は、KTやシステムの複雑度といった技術的な理由で分割されることが多い。しかし、Waveは同時に「現場がいつ、何を、新しく使い始めるか」という変化の単位でもある。

一斉切替（All-at-once）と段階的切替（One-step-at-a-time）のどちらを選ぶかは、次のような技術面の判断に、変化面の判断も加えて決める。

| | 技術面の判断 | 変化面の判断 |
|---|---|---|
| 一斉切替 | システム間の依存が強く、一部だけ新運用にできない | 混乱は一時的に集中するが、「もう後戻りできない」という区切りを作れる |
| 段階的切替 | 既存ベンダーとの契約終了日に余裕がある | 小さな成功（Quick Win）を早期に見せられるが、新旧運用が並存し「結局どちらに連絡すべきか」という混乱が長引きやすい |

Wave計画を技術的な観点だけで決めてしまうと、この変化面の設計が抜け落ちる。Wave設計（Chapter 3.4）を行う際は、変化面の判断もあわせて記録しておく。

### 7.4 Commitment ―― 現場が「使う」ようになるまでの4段階

このシリーズの Commitment 段階（業界のチェンジマネジメント標準と共通の考え方。ADKAR 等の代替ではない）である「Unawareness（無自覚）→ Awareness（認知）→ Buy-in（納得）→ Ownership（自分ごと化）」を、運用移行の文脈に当てはめると次のようになる。

| 段階 | 現場の状態 | Transition Managerがやること |
|---|---|---|
| Unawareness | 運用者が変わることを知らない | 変更の事実と時期を伝える |
| Awareness | 変わることは知っているが、自分にとって何が変わるかは分かっていない | 「新しい連絡先」「新しい手順」を具体的に伝える |
| Buy-in | 新しい手順を試してみる | 実際に使ってみた際の応答速度・品質を、旧運用と比べて悪くないと感じてもらう |
| Ownership | 新しい手順を当たり前として使う | 旧担当者への個人連絡が自然に減っていく |

このうち、現場が最も長くとどまりやすいのがBuy-inである。「新しい運用チームを試してみたが、まだ様子見」という状態のまま、旧担当者への個人連絡を並行して続けるユーザーは多い。Buy-inからOwnershipへ進めるには、新しい手順を使った際の体験（応答速度・的確さ）が、最低でも旧運用と同等以上であることが必要になる。ここが崩れると、せっかくBuy-inまで進んだ現場が逆戻りする。

現場に伝えるべきことは、次の3点に集約できる。**なぜ運用者が変わるのか／それが自分たちの部署にとって何を意味するのか／自分は具体的に何をどう変える必要があるのか**。この3点目（自分ごと）まで届いていない案内は、現場にとって「お知らせ」でしかなく、行動は変わらない。

> 現場が今どの段階にいるかはここで分かる。そこから実際に相手を動かす具体的な技術は、横串Playbook（Stakeholder Activation Playbook）に譲る。要点は7.8にまとめている。

### 7.5 移行後のトーン変化 ―― Soft Landingとその先

Hypercare（Chapter 3.3・3.6）が終わる前後で、コミュニケーションのトーンを意図的に変える。

- **移行直後（Hypercare中）**：「変更したこと」の告知ではなく、「困っていることを聞いている」「まだ設計は固定されていない」というSoft Landingのトーンにする。移行直後の不満・戸惑いを正面から受け止める姿勢を示す段階である
- **Hypercare終了後**：Soft Landingから、新しい運用の中でどう効率的に動くか（Performance Maximization）というトーンへ切り替える。「移行はもう終わったこと」として扱ってよい段階である

この2つの段階を同じトーンで通してしまうと、移行直後に「もう新しい運用に慣れてください」と迫って反発を招くか、逆にHypercare終了後もいつまでも「移行期」の空気を引きずり、現場のOwnership（7.4）が進まないか、どちらかの失敗につながる。

### 7.6 Adoption Definition of Done

定着化は主観的な印象ではなく、次のような指標でモニタリングし、一定の水準に達した状態を **Adoption Definition of Done** として定義する。Transition Close（Chapter 3.6、全Waveの運用責任移転が完了し、プログラムとして正式にクローズする状態）と、このAdoption Definition of Doneは別のマイルストーンであり、両方が揃って初めてGate 5（Steady State Accepted、Chapter 1.3）に到達する。

| 指標 | 見るもの |
|---|---|
| 正規チャネル利用率 | チケット起票のうち、正規の窓口・手順を経たものの比率（旧担当者への個人連絡・メール直送などの「シャドー対応」との比較） |
| エスカレーション自己完結率 | インシデントのうち、新運用チームが旧担当者・旧ベンダーの助けなしに解決できた比率 |
| 受容度（Acceptance）調査 | 定点でのアンケート・ヒアリングによる、新しい運用への信頼度の推移 |
| 段階分布 | 主要ステークホルダーが7.4のUnawareness〜Ownershipのどの段階にいるかの分布 |
| SLA安定 | 合意したSLAを、直近の一定期間安定して満たしているか |
| 未解決リスク | ②から継続利用しているRAID Log（1.3）のTransition Categoryに、未解決のCriticalな項目が残っていないか |
| AI運用チームのレベル（該当する場合） | Chapter 6.5のレベル分布・Level 3以上の内製比率が目標水準に達しているか |

Adoption Definition of Doneは、Transition Closeの報告とは別に、Steering Committeeへ独立して報告する。これにより、「移行は終わったはずなのに、なぜまだ現場が旧担当者に連絡しているのか」という状態を、曖昧なまま放置せずに済む。テンプレートはAppendix No.12を使う。

### 7.7 陥りやすいトラブルと対処

| トラブル | 内容 | 対処 |
|---|---|---|
| シャドーサポートの継続 | 正式な責任移転後も、現場が旧担当者・旧ベンダーに非公式に連絡を取り続ける | 旧担当者側にも「非公式な対応をしない」ことを正式に合意してもらう。新チームへの問い合わせが増えるまでの期間は、あえて旧担当者を巻き込まない判断を意識的に行う |
| 早すぎる「勝利宣言」 | Transition Close＝定着化の完了、と経営層・スポンサーが誤解し、モニタリングを打ち切ってしまう | 7.6の指標を、Transition Closeの報告とは別に、Steering Committeeへ継続的に報告する |
| 一度きりの告知で終わる | 移行の告知を1回のメールで済ませ、その後のフォローがない | 7.5のトーン変化を含め、マイルストーンに沿った複数回のコミュニケーションを計画する |
| ミドル層が「今のままでよい」と判断を止める | 現場に近いミドルマネジメントが、新しい運用の必要性を自分ごととして捉えず、変化への抵抗の主因になる | ミドル層を単なる伝達者ではなく、7.4のBuy-in〜Ownershipを最初に達成させるべき対象として扱う |

### 7.8 Stakeholder Activationへの接続 ―― 状態を見た後、どう動かすか

7.4で見た「相手が今どの段階（Unawareness〜Ownership）にいるか」は、あくまで現在地の診断である。そこから相手を実際に動かす具体的な技術は、姉妹Playbook（①②③共通で参照する横串Playbook）に譲る。要点だけ示すと、次の5ステップである。

1. **Segment**：全員を同じ熱量で説得せず、動きそう度×影響力で仕分ける
2. **Diagnose**：動かない理由をLogic／Emotion／Ability／Incentive-Environmentで診断する
3. **Select**：診断した障壁に応じて打ち手を選ぶ（論理的に正しい説明＝人が動く、ではない）
4. **Tailor**：メッセージのCommon Coreは共通にしつつ、相手ごとのReason to Actを変える
5. **Observe**：「説明したか」ではなく「行動が変わったか」を見る。変わらなければStakeholderの属性のせいにせず、Diagnose・Select・Tailor・Channelを見直す

Transition Managerが7.4のCommitment段階で現場を動かせず足踏みしている場合、次に見るべきはこのStakeholder Activation Playbookである。

## Chapter 8. 実践演習

### ケース：4社・5プロジェクトによる基幹システム刷新（続き）

②のChapter 9で扱った演習ケースの続きとして設定する。②の演習では、次の体制で基幹システム刷新プロジェクトが進行していた。

- PJ-A（A社）：業務要件定義・BPR
- PJ-B（B社）：基幹システム本体の設計・開発
- PJ-C（C社）：外部連携・周辺システムI/F
- PJ-D（D社）：データ移行
- PJ-E（社内／PMO兼任）：テスト統括・移行リハーサル

②のプログラムが完了に近づき、本番稼働の準備段階に入った。ここからは、あなたがTransition Managerとして、次の運用移行を設計する。

- **基幹システム本体（PJ-B成果物）とデータ移行（PJ-D成果物）**：自社が開発した新システムであり、社内のAMS運用チームへ引き継ぐ（シナリオA）
- **既存の周辺システムの一部**（PJ-Cが接続するI/F先のうち、これまで既存ベンダーX社が個別に運用してきた1システム）：基幹刷新にあわせて契約が更新されるタイミングで、新しいAMSベンダーへ引き継ぐことになった（シナリオB）

さらに、PJ-Bの一環として、問い合わせ内容を自動分類するAI機能（LLMベース）が追加開発された。分類結果に応じて、担当部署への自動振り分けと対応優先度の判定を行う。この機能の運用体制も、あなたがTransition Managerとして設計する（Chapter 5・6）。

### 演習ステップ

1. 対象システムをシナリオA／Bに仕分ける（Chapter 1.5）
2. シナリオAの対象について、Operability・運用チーム準備状況・Warrantyを設計する（Chapter 2）
3. シナリオBの対象について、デューデリジェンスを実施する（Chapter 3.1）
4. シナリオBのTransition Plan（Wave分け、KT計画）を設計する（Chapter 3.2〜3.6）
5. 両シナリオを踏まえ、工数見積もりの前提（スコープ階層、見積もりアプローチ、要員ピラミッド）を整理する（Chapter 4）
6. 定着化のReadinessを評価する（Chapter 7.2）
7. Wave設計に変化面の判断を追加する（Chapter 7.3）
8. 定着化のモニタリング指標を設計する（Chapter 7.6）
9. 追加されたAI機能について、6カテゴリのタスク棚卸しを実施する（Chapter 5.2）
10. AI運用の初期体制・責任分担・教育ロードマップを設計する（Chapter 5.3〜5.6、Chapter 6）

### 進め方（目安：90分×4回。自分のペースで進めてよい）

Session 1〜3（仕分け・Transition Plan・定着化）は、AMS・インフラ運用の移行を担うすべてのTransition Manager候補に共通する。Session 4（AI運用）は、AI運用を伴うプログラムを担当する場合に取り組めばよい。AI案件を担当しない場合にまでSession 4を無理に進める必要はない。

**Session 1：仕分けとデューデリジェンス（90分）**

1. 対象システムをシナリオA／Bに仕分ける
2. シナリオAについて、Go/No-Go基準を3つ挙げる
3. シナリオBについて、デューデリジェンスの5観点（Chapter 3.1）ごとに、確認すべき具体的な質問を1つずつ考える
4. デューデリジェンスの結果、最もリスクが高いと想定される観点を1つ選び、理由を言語化する

**Session 2：Transition Planと見積もり（90分）**

1. シナリオBの対象について、Waveに分けるべきかどうかを判断する（分ける場合はその理由も）
2. KTの実行方法（Chapter 3.5）のうち、このケースに最も適した方法を選び、理由を説明する
3. 見積もりのスコープ階層（Chapter 4.2）を、AM・開発・インフラの境界を明示して整理する
4. Bottom-up／Top-downのどちらのアプローチを使うか、対象ごとに判断する
5. 移行期に厚くすべきタワーを1つ選び、理由を説明する

**Session 3：定着化設計（90分）**

1. シナリオA・Bそれぞれについて、現場が最も抵抗を示しそうな変化を1つ挙げる
2. Wave設計（Session 2）に、変化面の判断（Chapter 7.3）を追加する
3. Unawareness→Ownershipの4段階（Chapter 7.4）のうち、このケースで現場が最も長くとどまりそうな段階を予測する
4. 定着化のモニタリング指標（Chapter 7.6）を2つ設計し、それぞれのデータソースを具体化する

**Session 4：AI運用体制の設計（90分）**

1. 追加されたAI機能について、Chapter 5.2の6カテゴリ棚卸しを実施する（該当・非該当を判断する）
2. 4ロール（Monitor／Engineer／HITL Reviewer／Lead）を、このプログラムの体制でどう埋めるか、初期体制案を作る
3. 「誤分類による重大インシデントの見落とし」という意思決定について、Chapter 5.4のRACIを作る
4. 現在のメンバー（PJ-B開発チームなど）にLevel 3以上に該当しそうな人材がいるかを検討し、いない場合はChapter 6.3のどの選択肢を取るか判断する
5. Core層教育の完了目標時期を、Pilot／並行run開始（Chapter 3.3）との関係で設定する

演習はSession 4で終わらせず、最後に「Transition CloseとDefinition of Doneの違い」（Chapter 7.1・7.6）に加え、AI運用チームのレベル到達状況（Chapter 6.5）も含めた定着化の全体像を、Steering Committeeに説明できる1〜2文にまとめるところまでを演習のゴールにする。

### 演習の参考解答（例）

自分の解答と照らし合わせるための記入例である。そのまま正解として書き写すのではなく、「自分の解答に抜けている観点はないか」を確認する目的で使う。

**Session 1（仕分けとデューデリジェンス）の記入例**

| システム | シナリオ | 理由 |
|---|---|---|
| 基幹システム本体（PJ-B成果物） | A | 自社が要件定義から開発まで担当 |
| データ移行（PJ-D成果物） | A | 同上 |
| 周辺システム（既存ベンダーX運用） | B | 既存ベンダーが開発・運用し、今回契約が切り替わる |

デューデリジェンスで最もリスクが高いと想定される観点の例：**属人化**。既存ベンダーX社の担当者が長年同じ1名であるケースでは、契約終了後にその担当者へアクセスできなくなるリスクが最も高い。KT計画の中で、その担当者からのセッションを最優先に確保する必要がある。

**Session 2（Transition Planと見積もり）の記入例**

周辺システム（シナリオB）はWaveを分けない（対象が1システムのみで、分割する技術的理由がないため）。KTは、属人化リスクが高いことを踏まえ、Job ShadowingとReverse Shadowingを組み合わせ、既存担当者の稼働可能時間を早期に確保する。

スコープ階層の整理例：

| 階層 | 内容 |
|---|---|
| L1 | Application Management |
| L2 | 基幹システム支援、周辺システム支援 |
| L3 | インシデント管理、問題管理、変更支援 |

周辺システムはドキュメントが薄くチケット履歴の代表性も低いと想定されるため、Top-downアプローチを使う。基幹システムは新規構築でモニタリング設計もこれから行うため、当初はTop-down寄りで見積もり、Hypercare期間中の実績を踏まえてBottom-upへ移行する計画とする。

移行期に厚くすべきタワーは周辺システムのL3（深い技術対応）。属人化していた領域であり、Hypercare中に想定外の問い合わせが集中しやすいため。

**Session 3（定着化設計）の記入例**

シナリオAで現場が抵抗を示しそうな変化：これまで存在しなかった正式な運用チーム・チケット制度そのものへの不慣れ。シナリオBで抵抗を示しそうな変化：長年同じ担当者に直接連絡していた習慣からの切り替え。

Wave設計への変化面の追加：周辺システムのTransitionは、既存ベンダーX社の担当者とのなじみが強いため、一斉切替ではなく、Parallel Operations Start（Chapter 3.6）の期間を長めに取り、並行run中に新チームへの信頼を積み上げる方針とする。

現場が最も長くとどまりそうな段階：Buy-in。特に周辺システムでは、長年の個人的信頼関係があるため、Ownershipへの移行に時間がかかると想定される。

定着化のモニタリング指標の例：①正規チャネル利用率（データソース：チケットシステムの起票経路ログ）②エスカレーション自己完結率（データソース：インシデント管理システムのエスカレーション記録、旧ベンダーX社への問い合わせ有無のタグ付け）。

**Session 4（AI運用体制の設計）の記入例**

タスク棚卸しの例：

| カテゴリ | 該当性 | 理由 |
|---|---|---|
| モデル・品質監視 | 該当 | 誤分類は業務影響が大きい（優先度判定を誤ると重大インシデント対応が遅れる） |
| プロンプト・モデル管理 | 該当 | LLMベースであり、分類基準の変更にプロンプト修正が伴う |
| Human-in-the-Loopの運用 | 該当 | 高優先度と判定されたものは人間のレビューを挟む設計とする |
| 再学習・更新サイクル | 該当（低頻度） | 問い合わせ傾向の変化に応じ、四半期程度で見直す想定 |
| フィードバックとナレッジ化 | 該当 | 誤分類の訂正を蓄積し、プロンプト改善に反映する |
| コスト・利用状況モニタリング | 該当 | 従量課金のLLM APIを利用 |

初期体制案の例：立ち上げ期はPJ-B開発チームの1名がMonitor・Engineerを兼任する。HITL Reviewerは、問い合わせ対応部署の主任クラスが稼働の一部を割く。AI Ops LeadはTransition Manager自身が兼任する。

責任分担表の例（誤分類による重大インシデントの見落とし）：一次責任はHITL Reviewer（高優先度判定の見落としがないかレビュー）、相談はAI Ops Engineer（プロンプト側の問題かどうかを切り分け）、承認はAI Ops Lead経由でGovernorへ。

Level 3以上の人材確保の例：PJ-B開発チームにLLM運用経験者がいない場合、Chapter 6.3の「外部ベンダーとの伴走型契約」を選び、Hypercare期間中に技術面を併走しながら内製化する計画とする。Core層教育の完了目標は、Pilot／並行run開始（Chapter 3.3）の1か月前に設定する。
