## 複数ベンダー・複数プロジェクトを統合管理するための実践ガイド【自己学習版】

## このPlaybookの目的

複数ベンダー・複数プロジェクトを束ねるプログラムマネジメント（PgMO）を任された担当者が、次の3つの問いに自力で答えられるようになることを目的とする。

- プロジェクト間の連携ポイントをどう整理するか（Chapter 2・3）
- スケジュール・スコープ境界・内容（要件や設計など）の整合性をどう取るか（Chapter 4・5・6）
- モニタリング＆コントロールをどう回すか（Chapter 7・8）

個別プロジェクトの管理（WBS・進捗管理・課題管理）はベンダーPM／PLの役割であり、本Playbookの対象外である（WBSの作り方自体は別紙の WBS 設計プレイブックを参照）。本Playbookが対象とするのは、**個別プロジェクトの「中」ではなく「間（あいだ）」をどう管理するか**である。

**射程の明示**：本Playbookが扱うのは、Program Managementの中でも複数PJ間の統合・依存・整合・統制（Cross-Project Integration & Control）に絞った領域である。Benefits／Value Realization、Strategic Alignment、Program-level Business Case、Stakeholder／Change Management、Resource／Investment Prioritization、Program Lifecycle（Tranche）管理といった、Program Management全般に含まれる他の領域は、本Playbookの対象外である。タイトルが単純な「Program Management Playbook」ではなく「Cross-Project Program Management Playbook」であるのはこのためである。あわせて、本Playbookが扱うのは戦略の実現化工程（プロジェクト化された後の複数PJ統合管理）に限られる。IT戦略立案やSCNによる施策・KPI・プロジェクト化といった上流工程、および実現化後の運用・定着化（AMS・AI運用・インフラ運用等）といった下流工程は、いずれも本Playbookの対象外である。

### Playbookシリーズにおける本書の位置づけ

```text
① 戦略立案・SCN
   IT戦略を含む戦略立案 → SCN → KPI → Gate 1 プロジェクト化
                        │
                        ▼
② Cross-Project Program Management Playbook（本書）
   複数ベンダー・複数プロジェクトを束ねる実現化工程を、統合的に管理する
                        │
                        ▼
③ Operations Transition Playbook
   AMS・インフラ運用・AI運用への移行設計と、実現化後の安定運用・定着化
```

①・③は本Playbookの対象外であり、②の範囲に閉じ、越境しないことを原則とする。①の Gate 1 完了後、本章の着手前チェック（Gate 2）へ接続する。複数の相手（Vendor PM・部門長・意思決定者等）を実際に動かす技術は、①②③共通の横串Playbook（Stakeholder Activation Playbook）を参照する。

## 使い方

1. Chapter 1〜2で「PgMOは何を管理するのか」という視点を作る
2. Chapter 3〜6で管理対象を5領域（Scope Boundary / Dependency / Interface / Consistency / Schedule）に分解する型を学ぶ
3. Chapter 7〜8でモニタリング＆コントロールとガバナンスの回し方を学ぶ
4. Chapter 9の演習で、実在に近いケースを使って一通り自分の手で作ってみる
5. Appendixのテンプレートを、自分が実際に担当するプログラムに当てはめて埋める

読むだけで終わらせず、必ずChapter 9の演習、または自分が担当する実プログラムのどちらかで手を動かすところまでをワンセットとする。各Chapter末の振り返りメモは、指導者に問われて答えるものではなく、自分自身に問いかけるものとして使う。答えに詰まった項目があれば、そこが理解の甘い場所である。一人で判断がつかない場合は、無理に自己完結させず、先輩・上司に短く相談してよい。①／③との境界（本書は実現化の「間」のみ）は、Chapter 2に入る前に把握しておく。

## Chapter 1. Project Management と Cross-Project Program Management の違い

### 1.1 個別PJではなく「PJ間」を管理する

最初に押さえるべき最も重要なことは、次の一文に尽きる。

> プログラムマネジメントでは、各PJの中身を全部管理する必要はない。
> PgMOが管理すべきなのは「PJとPJの間」である。

個別プロジェクトのWBS・課題・進捗はベンダーPMが管理する。PgMOがそこに深く踏み込んで細かくレビューし始めると、ベンダーPMの責任範囲を侵食し、かつPgMO自身がボトルネックになる。PgMOがやるべきは、プロジェクト間の受け渡し・依存・整合を見ることである。

ただし、PJ間への影響を判断するために必要な範囲では、個別PJの進捗・課題・品質をモニタリングする。PgMOが「中を見ない」のではなく、「中の管理責任を持たない」という意味である。実際、大規模プログラムでは、あるPJの遅延がDependencyの必要日にまだ達していない段階でも、PgMOがその予兆として拾う必要がある（Chapter 7.6の先読みを参照）。

```text
Project A          PgMO管理対象             Project B
───────────      ───────────────      ───────────
要件定義       →  Input / Output   →   基本設計
API仕様        →  Interface        →   API実装
環境構築       →  Dependency       →   テスト
マスタ定義     →  Consistency      →   データ移行
4/30完了       →  Milestone        →   5/1開始
```

「Aが何をいつBへ渡すのか」「Bは何を前提としているのか」「その前提は一致しているのか」を見るのがPgMOの仕事であり、Aの中身・Bの中身そのものを見るのはPgMOの一次的な仕事ではない。

### 1.2 PgMOの責任範囲

| 領域 | PgMOの責任 | ベンダーPMの責任 |
|---|---|---|
| 個別PJの進捗・課題・品質 | モニタリングのみ（一次責任なし） | 一次責任 |
| プロジェクト間の連携ポイント | 一次責任 | 自PJ側の窓口対応 |
| 全体スケジュールの整合 | 一次責任 | 自PJスケジュールの精度 |
| スコープの重複・抜け | 一次責任 | 自PJスコープの正確な申告 |
| クロスファンクションな意思決定 | エスカレーション先の整理・招集 | 意思決定への参画 |

### 1.3 ベンダーPMとPgMOの役割分担

ベンダーが異なる複数PJでは、各ベンダーPMは自社の契約範囲・自社PJの成功を最優先する。これは正しい行動であり、責めるべきものではない。だからこそ、**PJ間の整合を見る役割は、どのベンダーにも属さない中立的なPgMOが担う必要がある**。この前提を最初に理解させないと、「なぜ自分（PgMO）が各社の板挟みになるのか」が腹落ちしないまま消耗してしまう。

### 1.4 体制図 ―― PgMOはどこに立つのか

責任範囲（1.2）を頭で理解するだけでは不十分で、**PgMOが体制図上どこに立っているか**を自分自身で絵として描いてみることで初めて、責任範囲とエスカレーション先が結びつく。プログラムによって細部は異なるが、典型的な体制は次の形になる。

```text
                Steering Committee
             （Program Sponsor／経営層）
                        │
                 Program Director
              （プログラム全体の最終責任者）
                        │
                      PgMO
        （プロジェクト間の整合・調整・エスカレーション）
        ┌───────────┼───────────┐
    Vendor A PM    Vendor B PM    Vendor C PM
   （PJ-Aの一次責任） （PJ-Bの一次責任） （PJ-Cの一次責任）
```

この図で押さえるべきポイントは3つある。

- **PgMOはベンダーPMの上位者ではなく、横に立つ調整役である**：PgMOに各ベンダーPMへの人事権・契約上の指揮命令権はない。だからこそ、Chapter 1.3の「中立性」が機能の前提になる
- **PgMOには単独で決められない事項がある**：契約・追加コスト・優先順位に関わる判断は、Program DirectorまたはSteering Committeeが最終決定者である（Chapter 7.5・8.5のエスカレーションはこの図に沿って行う）
- **体制図は組織によって変わる**：Program Directorという役職が存在せず、PgMOが直接Steering Committeeに報告する体制もあれば、PgMOが発注者側のIT部門の下に位置づけられる体制もある。重要なのは役職名ではなく、「誰が最終判断者か」「誰に何を相談すればよいか」が明文化されているかどうかである

着任したら最初にやるべきことは、抽象的な理解ではなく、**自分のプログラムの実際の体制図を、上記のテンプレートに当てはめて描いてみる**ことである。描けない場合、それ自体が「エスカレーション先が未整理」という問題として扱う。

### 1.5 PgMOとPMOを兼任する場合の注意点

PgMOが、特定ベンダーのPJのPMO（そのPJ内のプロジェクトマネジメントオフィス機能）を兼任するケースは実務上珍しくない。体制上の制約や人員不足が理由であることが多いが、これは1.3で述べた「中立性」と構造的に矛盾する可能性があるため、兼任させる場合は注意が必要である。

**兼任によって生じるリスク**

- 自分が兼任するPJに有利な判断を、無意識のうちに行ってしまう（利益相反）
- 他ベンダーから見て、PgMOが特定PJの肩を持っていると受け取られ、以降の報告が事実ベースでなくなる
- Chapter 5.4のような分界線の判定や、Chapter 7のエスカレーション判断が、当該PJに関わる場面でだけ甘くなる

**対処の型**

1. 兼任している事実を、着任時点で全ベンダーに開示する。隠したまま進めると、後で発覚したときの信頼毀損の方が大きい
2. 自分が兼任するPJが当事者になる対立・分界線の判定は、PgMOが自分で裁定せず、Program Directorや契約担当など第三者に判断を委ねる
3. 兼任するPJに関する意思決定は、Decision Logに「兼任者本人が関与」と明記し、後から誰でも検証できる状態にしておく
4. 可能であれば、PgMO業務とPMO業務を体制上分離する（人が同じでも、会議体・報告ラインを分ける）のが望ましい。分離が難しい小規模プログラムでは、せめて役割を切り替えて発言していることを本人が自覚し、周囲にも明示する
5. 兼任が避けられない体制であることをSteering Committeeにあらかじめ伝え、利益相反が疑われる判断は必ず事後報告する運用にしておく

兼任そのものが問題なのではない。**中立性は自動的に保たれるものではなく、意識して設計しなければ崩れるものである**、という前提をまず自分の中に持っておく。

### 1.6 既存プログラムへの途中参画 ―― 信頼関係が先にある中でのプレゼンス確立

長年続いているプロジェクトが既に存在し、そこに他のプロジェクトが加わって規模・複雑性が増したタイミングで、PgMOとして新たに参画するケースは実務でよくある。この場合特有の難しさがあるため、1.1〜1.5とは別の観点として押さえておく必要がある。

**このケースで起きやすいこと**

- 顧客側には、既存プロジェクトを長年担当してきた信頼の厚いベンダー担当者（多くは10年単位の付き合い）がすでに存在し、そちらへの信頼度の方がPgMOより高く見える
- 「複数PJを束ねるノウハウがある」という期待でPgMOが選定されたにもかかわらず、そのノウハウが顧客から見えてこない
- PgMOチームが実務上の細々したアドミタスク（権限付与の代行、連絡調整など）に忙殺され、プログラムを大きく変えるような提案型の活動ができていない
- 多くの意思決定プロセスが、特定の顧客キーパーソン一人を通す形に固定化されており、権限委譲を提案しても「今のやり方でよい」と却下される
- 最悪の場合、ベンダー交代の検討にまで発展しうる

これは、自分のスキル不足というより、**新任PgMOと既存の信頼関係との間に構造的な非対称性がある**ことから生じる。着任してすぐに解消できるものではないという前提を、あらかじめ自分の中に持っておく。

**対処の型**

1. **オーナーシップへの視点転換**：「自分はPMO（管理者）だ」という意識で仕事をすると、指示待ちになり後手に回りやすい。「自分が顧客側のPM／POだったら」という当事者意識で見ると、不足や課題が自然と見えてくる。それをPgMOの文脈に持っていくと、多くの場合それは「提案」として顧客に認識される
2. **味方を作る構図**：既存の信頼関係を持つ人物（顧客側キーパーソンや長年のベンダー担当者）を、対立相手ではなく味方として位置づける。結論をいきなり顧客に提示するのではなく、その人物を巻き込んで仮説段階まで一緒に作ったうえで顧客に持っていくと、「PgMO 対 既存の信頼関係」ではなく「PgMO＋既存の信頼関係 対 顧客の課題」という構図になり、無用な対立を避けながら信頼を積み上げられる
3. **現場の実力者との関係構築を最初の一歩にする**：いきなり顧客キーパーソンとの関係構築を狙うより、まず現場で信頼されている人物と個別に関係を作り、「〇〇さんとも相談してこれがいいと思っています」という形で顧客とコミュニケーションを取ると、「この人はちゃんと話ができる人だ」という最初の信頼につながりやすい
4. **交点（Interface／Dependency）に注目する**：大規模・複数関係者が絡むプログラムでPgMOが最初に見るべきは、複数の関係者・PJが接する「交点」である（Chapter 3のDependency・Interfaceそのもの）。交点を洗い出し、状態を定義し、月次→週次でトラッキングする体制を確立することが、信頼される提案の土台になる
5. **アドミタスクに埋没しない**：日々の事務作業に忙殺されると、提案型の活動に割ける時間がなくなる。ルーティン作業はできる限り委譲・簡素化し、複数PJを横断する構造的な課題の発見に時間を割り当てる

このケースで持たせたい前提は、**プレゼンスは実績の蓄積でしか作れないが、構図の作り方次第で蓄積のスピードは変えられる**、ということである。

## Chapter 2. プログラム全体を構造化する

### 着手前チェック ―― 前提条件チェックリスト

Chapter 2以降の管理表は、ゼロから作れるものではない。土台となる資料が揃っていないまま管理表作成に着手すると、プログラムのコントロールではなく、いつまでも構造化作業そのものに追われ続けることになる。着手前に、次の観点で前提資料の有無を確認する。

| 管理表／成果物 | 必須の前提資料 | あると望ましい資料 | 主な確認先 |
|---|---|---|---|
| Project Landscape（2.1） | プログラムに含まれるPJの一覧 | 各PJの契約概要 | Program Director、契約担当 |
| Project Interaction Map（2.3） | 各PJの体制図、各PJのWBS（Lv3〜4程度） | スコープ定義書、マイルストン一覧 | 各PJのPM／PL |
| Dependency Register（3.3） | Interaction Mapの完成版 | 過去の類似プログラムのDependency実績 | 各PJのPM／TL |
| Scope Boundary Matrix（5.1） | 各PJの契約書・RFPのスコープ記載 | 過去の類似プログラムの分担実績 | 契約担当、各PJのPM |
| Consistency Matrix（6.2） | 各PJの要件定義書・基本設計書（ドラフトで可） | データ定義書、非機能要件書 | 各PJのTech Lead |
| Integrated Milestone Plan（4.2） | 各PJのマスタースケジュール | Lag／バッファの合意事項 | 各PJのPM |

**前提資料が揃わない場合の対処**

前提資料が揃わないこと自体は珍しくない。揃うまで待たせるのではなく、次のように動かせる。

1. **口頭ヒアリングで暫定版を作る**：WBSや体制図が未整備の場合、各PJのPM／PLへの個別ヒアリングを設定し、聞き取りながら暫定版の管理表を作る。ヒアリングの過程そのものが、PJ間の関係を把握する機会にもなる
2. **暫定であることを明示する**：ヒアリングベースで作った管理表には「未確認」「暫定」等のマークを付け、後日正式な資料で裏付けが取れ次第更新する
3. **ワークショップで複数PJを同時に引き合わせる**：Tech Lead同士の連携など、複数PJにまたがる確認が必要な場合は、個別ヒアリングより先に関係者を一堂に集めるワークショップを設定した方が早いことが多い。特にConsistency Matrix（Chapter 6）は、各PJのTech Leadが顔を合わせて初めて整合の穴が見つかるケースが多い
4. **足りない資料の整備自体をPgMOのタスクとして扱わせる**：体制図やWBSが存在しないこと自体が、そのプログラムの管理成熟度の低さを示す兆候である。管理表作成の前提として、資料整備そのものをPgMOのタスクリストに乗せ、着手初期のマイルストーンとして扱わせる

このチェックリストは、着手時だけでなく、新しいPJがプログラムに加わるたびに再確認する。上流①から受け取るのは Gate 1（Why／What／Project切り／KPI／Scope概要／Sponsor）まで。上表の体制図・WBS・契約スコープ等は Gate 2（本書の着手前）で確定させる領域である（①）。

本書が扱うのは Gate 2 から Gate 3 到達までの実現化工程である。実現化工程が完了に近づくと、Gate 3（Service Transition Planning Ready）で③（Transition Manager向け）へ引き継ぐ。引き継ぐのは Dependency Register（3.3）・Consistency Matrix（6.2）・RAID Log（8.3）であり、Gate 3 到達前に新たに作り直す必要はない。詳細は③ Chapter 1.3。

### 2.1 Project Landscape ―― まず全体像を描く

いきなり管理表から作り始めない。最初にやるのは、プログラムに含まれるプロジェクトの一覧化と、その位置づけの整理である。

| 項目 | 内容 |
|---|---|
| PJ名 | 例：PJ-A 業務要件定義 |
| ベンダー | 元請・二次請けを含む |
| スコープ概要 | 1〜2文で |
| 開始・終了予定 | |
| 主要な受け渡し先／受け取り元PJ | |

### 2.2 Scope Boundaryを最初に引かせる

「誰がどこまでやるか」が曖昧なまま進むプログラムは、後工程で必ず「抜け」か「重複」が発覚する。Chapter 5で詳しく扱うが、この段階では概略でよいので各PJの境界線を引かせる。

### 2.3 Project Interaction Mapを描かせる

```text
                 ┌─────────────┐
                 │ PJ-A 業務要件 │
                 └──────┬──────┘
                        │要件
                        ▼
┌──────────┐      ┌─────────────┐
│ PJ-D データ│ ───→ │ PJ-B システム │
└──────────┘      └──────┬──────┘
                         │IF仕様
                         ▼
                  ┌─────────────┐
                  │ PJ-C 外部連携 │
                  └─────────────┘
```

矢印一本一本について「何が流れるのか」を必ず書かせる。矢印だけ引いて中身を書かせないと、連携ポイントの漏れが見過ごされたまま先に進んでしまう。このMap作成だけでも、連携ポイントの漏れがかなり見つかる。

### 2.4 Dependencyの洗い出し方

Interaction Mapの矢印は、後述するCross-Project Dependency Register（Chapter 3・Appendix）に転記する。この時点では粒度は粗くてよく、「洗い出しの網羅性」を優先する。精緻化は後のサイクルで行う。

### 2.5 PgMOの異常検知５問

Interaction Map・Dependency Register・Consistency Matrix・Integrated Milestoneは、あくまで「表を埋める」ためのツールにすぎない。部下が実際につまずくのは、表を作り終えたあとの次の段階である。

> 「表は作れました。でも、何が危ないのか分かりません」

管理表というフォーマットを渡すだけでは、この段差は埋まらない。**表を見るときに何を疑うべきか、という視点そのもの**を渡す必要がある。管理表を作った直後、および更新のたびに、次の5つの問いを必ず自問する。

| No. | 観点 | 問い | 主に見る管理表 |
|---|---|---|---|
| 1 | 未接続 | 本来あるべきPJ間の矢印がないところはないか？ | Interaction Map（Chapter 2.3） |
| 2 | 未確定 | 後続PJが必要なのに、Input/Outputの内容・Owner・日付が未確定ではないか？ | Dependency Register（Chapter 3.3） |
| 3 | 不一致 | FromとToで成果物の定義・粒度・前提が違っていないか？ | Consistency Matrix（Chapter 6） |
| 4 | 余白不足 | Hand-offと後続着手の間にレビュー・修正期間（Lag）がないのではないか？ | Integrated Milestone Plan（Chapter 4.2） |
| 5 | 単一障害点 | 1つ遅れるだけで複数PJが止まるDependencyはどれか？ | Critical Dependency（Chapter 3.5） |

この5問は、管理表を一度作って終わりにするための質問ではない。Weekly Meetingのたびに、更新された管理表に対して繰り返し当て続けるものである。特に「1. 未接続」と「2. 未確定」は初期段階で、「3. 不一致」と「5. 単一障害点」はプログラムが進むにつれて重みが増していく。5問すべてに「問題なし」と即答できる状態は、実務ではむしろ疑ってよい。どこかの観点でまだ見えていないだけの可能性が高い。

### 2.6 5領域のメンタルモデル

この後Chapter 3〜6で、Interaction Map・Dependency Register・Scope Boundary Matrix・Consistency Matrix・Integrated Scheduleという個別の管理表を順に扱っていく。しかし管理表の名前や書式そのものは、覚えることが目的ではない。持っておきたいのは、その背後にある次の一枚のメンタルモデルである。

```text
                  Program Outcome
                        │
                 Integrated Schedule
                        │
        ┌───────────────┼───────────────┐
        │                │                │
  Scope Boundary     Dependency       Consistency
                        │                │
                    Interface ───────────┘
                        │
                   PJ-A ↔ PJ-B
```

それぞれの問いを一言で定義すると、次のようになる。

| 領域 | 一言の定義 | 対応Chapter |
|---|---|---|
| Boundary（Scope Boundary） | 誰が担当するか | Chapter 5 |
| Dependency | 何を、いつ、誰から誰に渡すか | Chapter 3 |
| Interface | どう繋ぐか（項目・型・タイミングの合意） | Chapter 3.6 |
| Consistency | 内容（要件・設計・データ）が一致しているか | Chapter 6 |
| Schedule | 全体として期日に間に合うか | Chapter 4 |

管理表の名前や書式を忘れても、この5つの問いさえ持っていれば、PgMOとして次に何を確認すべきかを自分で考えられる。Chapter 3〜6を一通り学んだ後に、この一枚に立ち返らせると定着しやすい。

### 2.7 プログラム構造のHealth Assessment ―― PJ境界が「汚い」ケースへの対処

2.1〜2.6は、契約単位・ベンダー単位のPJがそれぞれ独立した単位として切られていることを暗黙の前提にしている。しかし実務では、1つの契約・1つのPJの中に、技術的には独立した複数のサブシステムが、「共通基盤」「共通機能」といった名目の1つの契約にまとめて発注されているケースが珍しくない。

この場合、Project Interaction Map（2.3）をPJ単位でそのまま描こうとしても描けない、あるいは描けたつもりでも実態を反映しない。PJという管理単位そのものが、実質的には複数の疑似PJの寄せ集めになっているためである。ここに気づかないまま2.1〜2.6の管理表を機械的に当てはめると、表面上は整合しているように見えて、実際には管理の粒度が粗すぎて重要な連携漏れを見逃す、という事態が起きる。

このズレは描き方が悪いのではなく、プログラム構造そのものに起因する。着任後、Project Landscape（2.1）を作る段階で、次の観点から構造の「健全性」を確認しておくと、後になってからInteraction Mapが描けずに立ち往生する事態を防げる。

| 確認観点 | 確認方法 | 「汚い」構造のサイン |
|---|---|---|
| 契約単位とシステム単位は一致しているか | 契約書・RFPのスコープ記載とシステム構成図を突き合わせる | 1契約の中に、独立してテスト・リリース可能な複数のサブシステムが含まれている |
| PJ内のサブシステム間の連携は把握されているか | そのPJのベンダーPM／技術責任者にヒアリングする | 「PJ内のことなので連携図は不要」という反応が返ってくる |
| PJ内サブシステム間の連携の密度は、他PJとの連携より高いか | Interaction Mapを試しにサブシステム単位で描いてみる | サブシステム間の矢印の本数が、PJ間の矢印の本数より明らかに多い |

**「汚い」構造だと分かった場合の対処**

1. **管理単位をPJ境界からシステム境界に切り替える**：Interaction Map・Dependency Register等を、契約上のPJ単位ではなく、実態に合わせたサブシステム単位で描き直す
2. **契約単位×システム単位のマトリクスを作る**：「どのサブシステムがどの契約に含まれるか」を一覧化し、契約上の責任範囲と実際の技術的な依存関係が一致しない箇所を可視化する
3. **契約担当と技術担当を分けて確認する**：契約上のPJ単位の話は契約担当（ベンダーPMなど）に、サブシステム間の技術的な依存関係の話は技術責任者に、別々に確認する。同じ人に両方を聞くと、契約上の建付けに引きずられて技術的な実態が見えなくなることがある

このHealth Assessmentは、プログラム構造が「綺麗」であれば数分で終わる確認作業である。むしろ、綺麗ではないプログラムほど早期に気づかせることに価値がある。①側の Projectization Health Assessment（①7.2）は同じ問題の**事前予防**；本節は**事後検知と立て直し**。どの7.2観点が甘いと本節のどの症状に現れるかの対応表は、①7.2に置いてある。

### 振り返りメモ（自己学習用）
- [ ] Interaction Mapの矢印すべてに「何が流れるか」が書けているか
- [ ] 矢印の抜け（実際には連携しているのに描かれていない関係）がないか、本人以外の目でも確認したか
- [ ] 異常検知５問を、自分の担当プログラムの管理表に対して実際に当ててみたか
- [ ] 5問すべてに即答で「問題なし」と答えていないか（本当に見えていないだけではないか）
- [ ] Boundary／Dependency／Interface／Consistency／Scheduleの5領域を、管理表を見ずに自分の言葉で説明できるか
- [ ] 契約単位のPJの中に、技術的に独立した複数のサブシステムが混在していないか

## Chapter 3. Cross-Project Dependency Management

### 3.1 Dependencyとは何か

あるPJの成果物・意思決定・環境が、別のPJの開始・完了・品質の前提になっている状態を指す。Dependencyは「日付の前後関係」ではなく、「何が何に依存しているか」という因果関係で捉える。

### 3.2 Input / Output と Predecessor / Successor

Chapter 3の考え方は「Input → Process → Output」という思考パターンの応用である。個別PJ内の工程分解に使う型を、PJ間の受け渡しに拡張して使う。

- Predecessor（先行PJ）：何を渡す側か
- Successor（後続PJ）：何を受け取る側か
- Input/Output：具体的に何が受け渡されるか（成果物名・データ・環境・意思決定事項）

### 3.3 Dependency Register

Chapter 2で洗い出したDependencyを、次の形式で一覧化する（詳細版はAppendix）。

| ID | From PJ | To PJ | 連携ポイント | Input/Output | 必要日 | Owner | Status | 影響 |
|---|---|---|---|---|---|---|---|---|
| D01 | PJ-A | PJ-B | 業務要件 | 要件定義書 | 9/15 | A社 | Green | 開発開始 |
| D02 | PJ-B | PJ-C | API仕様 | IF仕様書 | 10/1 | B社 | Amber | IF開発 |
| D03 | PJ-D | PJ-B | マスタ | データ定義 | 9/20 | C社 | Red | DB設計 |

### 3.4 単なる一覧表で終わらせない

各行について、必ず次の問いに自分で答える。

> これが遅れる／間違うと、誰の何が止まるか？

この問いに答えられない行は、そのDependencyをまだ本当には理解できていないと判定してよい。一覧表を埋めることが目的化し、「なぜこのDependencyが重要か」を説明できないまま形式だけ整っているケースは非常に多い。

### 3.5 Critical Dependency

すべてのDependencyが同じ重要度ではない。次のいずれかに該当するものをCriticalとして別管理する。

- 遅延した場合、全体スケジュールのクリティカルパスに直接影響する
- 遅延・誤りが後工程で発見された場合、手戻りコストが大きい（設計段階の誤りが結合テスト以降で発覚する、など）
- 複数のSuccessor PJに影響が波及する

### 3.6 IF（インターフェース）設計レビューの手順

Interface（I/F）はDependency Registerの1行として管理されるが、「連携ポイント：API仕様」のように1行に要約してしまうと、実際のレビューをどう進めるかが伝わらない。IFはDependencyの中でも特に「日付は合っているが中身が食い違う」事故が起きやすい領域なので、Register上の管理とは別に、レビューの手順そのものを型として持っておく。

**IF Design Reviewの5ステップ**

1. **IF一覧化**：対象となるIF（API、ファイル連携、DB直結、画面連携など）をInteraction Map（Chapter 2）から洗い出し、Dependency Register上のIDと紐づける
2. **仕様ドラフトの突き合わせ**：送信側・受信側それぞれの仕様ドラフトを、Owner（Tech Lead等）が同じ場で並べて確認する。片方のPJ内だけでレビューを終わらせない
3. **項目レベルのチェック**：次の観点で項目単位に確認する
   - 項目の有無（送信側にあるが受信側で使っていない／その逆）
   - データ型・桁数・コード体系の一致
   - 必須／任意の一致（受信側が必須と想定しているのに送信側が任意で送らないケースがある）
   - タイミング・頻度（リアルタイムかバッチか、日次か都度か）
   - エラー時の挙動（送信失敗時にどちらが検知し、どう回復するか）
4. **合意記録**：確認済みの仕様に両者が合意した記録を残す（Decision Logまたは仕様書のバージョン確定）。合意なきまま「確認中」のまま実装が先行することを防ぐ
5. **Consistency Matrixへの反映**：レビューが完了し矛盾がないことを確認できた時点で、Chapter 6のConsistency Matrixの「IF」行に「○」を付ける。ここで初めてDependency RegisterのStatusも Green にできる

**レビュー時の問い**

> このIF仕様は、送信側・受信側の両方の担当者が「同じ場」で確認したものか？
> それとも、どちらか一方が作った仕様書を、もう一方が読んだだけの状態か？

後者のまま進むIFは、結合テストで初めて食い違いが発覚するパターンが最も多い。PgMOは、IFレビューが「読み合わせ」で終わっていないか、両者合同のレビューになっているかを必ず確認する。

### 振り返りメモ（自己学習用）
- [ ] Dependency Registerの各行について「遅れる／間違うと何が止まるか」を即答できるか
- [ ] Critical Dependencyを3件挙げられるか、その理由を説明できるか
- [ ] IFレビューが「送信側・受信側の合同レビュー」になっているか、片方が作った仕様の読み合わせで終わっていないか

## Chapter 4. Integrated Schedule Management

### 4.1 各PJ WBSの統合方法

各ベンダーのWBSをそのまま重ねるのではなく、Dependency Register上のHand-off（受け渡し）ポイントを基準に、PJをまたぐマイルストーンだけを抽出して統合スケジュールを作る。全工程を統合しようとすると管理不能になるため、**PgMOが統合すべきはCross-Project Milestoneのみ**と割り切らせる。

### 4.2 Cross-Project Milestone / Hand-off / Lead・Lag

| 用語 | 意味 |
|---|---|
| Cross-Project Milestone | 複数PJに影響する節目（例：IF仕様確定） |
| Hand-off | 成果物・環境・意思決定がPJ間で受け渡される瞬間 |
| Lead | 後続PJが前倒しで着手できる余地 |
| Lag | 受け渡し後に必要な準備期間（レビュー・調整期間など） |

Lag（バッファ）を持たないスケジュールは、実務ではほぼ確実に破綻する。「A社の設計完了が5/10、B社の開発開始が5/15」だけを見て「OK」と判断してしまわないことが重要である。

### 4.3 「日付の整合」から「意味の整合」へ

経験が浅いと、次のような判断になりがちである。

> 「Aの設計完了が5/10、Bの開発開始が5/15なのでOK」

しかし本来確認すべきは次のレベルである。

> 「Bが必要とする設計情報は何か？」
> 「Aの5/10時点の成果物にそれが含まれるか？」
> 「レビュー・修正を含めて5/15に本当に使える状態か？」

日付が並んでいることと、渡すべき内容が本当に使える状態で存在することは別問題である。これが「日付の整合」から「意味の整合」へのステップアップであり、本Playbook全体で繰り返し強調すべきポイントである。

### 4.4 Critical Path と Impact Analysis

統合スケジュール上でクリティカルパスに乗っているHand-offを特定し、そこにInput/Outputの中身が伴っているかをChapter 6のConsistency Managementと突き合わせて確認する。スケジュールとConsistencyは別々の管理表に見えて、実際には表裏一体である。

### 振り返りメモ（自己学習用）
- [ ] 統合スケジュールに乗っているマイルストーンが、本当にCross-Project Milestoneか（単なる個別PJの内部マイルストーンが紛れ込んでいないか）
- [ ] 「日付は合っている」で終わらず、「渡す中身」まで確認する癖がついているか

## Chapter 5. Scope & Responsibility Management

### 5.1 Scope Boundary Matrix

「誰がどこまでやるか」をPJ横断でマトリクス化する。個別PJの契約範囲だけでなく、PJ間の境界線上にあるタスク（どちらが担当するか曖昧なもの）を明示的に洗い出すことが目的である。

| 作業項目 | PJ-A | PJ-B | PJ-C | 備考 |
|---|---|---|---|---|
| 業務要件定義 | ○ | | | |
| データ移行設計 | | △ | △ | AとBのどちらが主導か未確定 |
| 外部IF仕様策定 | | ○ | △ | 協業 |

### 5.2 RACI

Scope Boundary Matrixだけでは「実施責任」と「説明責任」が混同されやすい。重要な意思決定・成果物についてはRACI（Responsible / Accountable / Consulted / Informed）まで落とし込む。

### 5.3 Gap / Overlap

Scope Boundary Matrixで「△」が付いた項目、または誰の欄にも○が付かなかった項目がGap（抜け）である。逆に複数のPJが同じ作業を独自に進めていればOverlap（重複）である。どちらも契約変更・追加コストに直結するため、PgMOが最も早期に検出すべき事項の一つに位置づける。

### 5.4 ベンダー間責任分界

契約上の責任分界（どのベンダーがどこまで契約上の義務を負うか）と、実務上の作業分担（Scope Boundary Matrix）は必ずしも一致しない。両者にズレがある場合は、実務が回らなくなる前に契約担当・PM上位者へエスカレーションする。

**なぜズレが生まれるのか**

分界線のズレは、担当者の注意不足ではなく、次のような構造的な理由で生まれることがほとんどである。

- 契約形態の違い（請負／準委任）で、そもそも「成果物への責任の取り方」が異なる
- RFP・契約書のスコープ記載が抽象的で、詳細化した実務作業のレベルまで書き切れていない
- 各ベンダーが見積もり時点の前提（「そこは相手PJがやってくれるはず」）を握ったまま契約している
- プログラム開始後に要件が具体化し、契約時には存在しなかった作業（グレーゾーン作業）が新たに発生する

**典型的なグレーゾーンの例**

| グレーゾーンの例 | 起きやすい原因 |
|---|---|
| データクレンジング | 「正しいデータの定義」（要件定義PJ）と「実際の変換作業」（移行PJ）のどちらが担うか契約書に明記がない |
| 結合テスト環境の構築 | インフラベンダーと開発ベンダーの契約範囲の境界にちょうど落ちる |
| 移行リハーサルの実施主体 | 「移行」と「本稼働準備」が別ベンダー契約になっている場合に生じやすい |
| 監視・運用設計 | 非機能要件の担当が契約時点で明記されないまま進み、稼働直前に判明する |

**分界線のズレを扱う手順**

1. 契約書・RFPのスコープ記載を確認する（曖昧な場合は「記載なし」として扱う）
2. Scope Boundary Matrix上の実態（実際に誰がやっているか）と突き合わせる
3. ズレが「単なる作業分担の調整」で済むか、「契約上の解釈・追加コストが絡む」かを判定する
4. 前者は、PgMOに委譲された権限の範囲内で関係者間のOwnerを調整・合意し、Scope Boundary Matrixの備考欄に決定理由を残す
5. 後者はChapter 8.4のChange Controlプロセスに乗せ、契約担当・PM上位者の判断を仰ぐ

**判定基準（手順3の目安）**

| 判定 | 目安 | 対応 |
|---|---|---|
| PgMOで完結 | 作業量が小さい／追加コストが発生しない／既存契約の解釈の範囲内で説明できる | Scope Boundary Matrixに記録し、次回Weekly Meetingで共有するのみ |
| エスカレーション必要 | 追加コストが発生する／契約書の解釈がベンダー間で割れている／双方が「契約外」と主張している | Change Controlを起票し、Steering Committeeの判断を仰ぐ |

最もつまずきやすいのは、「PgMOで完結できるか、エスカレーションが必要か」の見極めである。判断を単なる作業量や金額の大小から始めるのではなく、まず契約書・RFP上の責任範囲と前提を確認する。そのうえで、既存契約の解釈の範囲内で処理できるか、追加コストや契約解釈の相違を伴うかを判定する。後者であれば、PgMOが独自に責任分界を決めず、Change Controlへ上げる。

なお、「PgMOで完結」とは、PgMOが独自の裁量で分界線を確定させることではない。正確には「PgMOに委譲された権限の範囲内で、関係者間の作業分担を調整・合意すること」を指す。PgMOにその権限が委譲されていないプログラムでは、作業量が小さく見える場合でも、念のためPM上位者に確認を取ってから記録する方が安全である。

なお、本来はプログラム開始前のRFP・契約書作成段階で、Scope Boundary Matrixに近い整理を済ませておくのが理想である。ただしPgMOが契約締結後にアサインされるケースも多く、その場合は本項の手順で事後的に穴を塞ぐことになる。

- [ ] Gap/Overlapが見つかった場合、誰にいつまでにエスカレーションするかを決められたか
- [ ] 契約書の記載とScope Boundary Matrixの実態がズレている項目について、「PgMOで完結できるか」「エスカレーションが必要か」を判定できたか

## Chapter 6. Requirement / Design Consistency Management

### 6.1 Consistencyとは何か

まず「Consistency（整合性）」が何を指すのか、具体例で揃えておく。カタカナ語のまま渡すと、本人には輪郭がつかめないまま先に進んでしまいやすい。

個別PJの成果物は、それぞれのPJの中だけで見れば正しく作られていることが多い。問題は、複数PJの成果物を実際につないだときに初めて矛盾が発覚するケースである。たとえば次のような状態を指す。

> PJ-Aのデータ定義書では「顧客ID」は10桁で定義されている。PJ-Bのシステム設計書では「顧客ID」は8桁で定義されている。どちらの成果物も、それぞれのPJの中ではレビューされ、承認済みである。しかし、いざ連携すると顧客IDが受け渡せない。

これが**「各社の成果物単体では正しいが、つなぐと成立しない」**状態であり、Consistency管理が対象とするのはまさにこの種の不整合である。個別PJ内のレビューでは検出できず、PJをまたいで初めて見える問題だからこそ、PgMOが管理する必要がある。

### 6.2 Cross-Project Consistency Matrix

これが今回のような相談に特に効く管理表である。「どのPJとどのPJの間で、どの観点の整合性確認が済んでいるか」を俯瞰するための表であり、詳細はMatrix自体には書かない（詳細は6.4のIssue Logに書く）。

| 整合性観点 | PJ-A | PJ-B | PJ-C | 確認内容 | Owner |
|---|---|---|---|---|---|
| 業務要件 | ○ | ○ | | 要件→システム設計 | PgMO |
| データ定義 | ○ | ○ | ○ | コード・桁・意味 | Data Lead |
| IF | | ○ | ○ | I/F項目・タイミング | Tech Lead |
| 非機能 | ○ | ○ | ○ | 性能・可用性等 | Architect |
| セキュリティ | ○ | ○ | ○ | 認証・権限 | Security |
| テスト | ○ | ○ | ○ | E2Eシナリオ | Test Lead |

このマトリクスによって、6.1で述べた「各社の成果物単体では正しいが、つなぐと成立しない」状態をPgMOが検出できるようにする。

### 6.3 対象となる整合性の観点

7つの観点は言葉だけを並べると抽象的に見えるが、実際には次のような具体的な不整合として現れる。観点名ではなく右列の「具体例」から入ると腹落ちしやすい。

| 観点 | 確認すること | 具体例（放置するとこうなる） |
|---|---|---|
| Requirement Traceability | 要件がどのPJのどの設計に反映されているか | 「与信チェック必須」という要件が決済PJの設計に反映されておらず、リリース直前に発覚する |
| Architecture | 全体アーキテクチャ方針と各PJの設計が矛盾していないか | 全体方針は疎結合のAPI連携なのに、PJ-Cだけが他PJのDBに直接アクセスする設計になっている |
| Interface | I/F項目の定義・粒度・タイミングが両側で一致しているか | PJ-Aは項目を必須、PJ-Bは任意として設計しており、連携時にエラーになる |
| Data | コード体系・桁数・意味定義が一致しているか | 同じ「顧客ID」がPJ-Aでは10桁、PJ-Bでは8桁で定義されている |
| Security | 認証方式・権限モデルが各PJ間で矛盾していないか | PJ-AはSSO前提、PJ-Bは個別ログインのままで、ユーザーが二重にログインを求められる |
| Non-functional Requirements | 性能・可用性等の前提がPJ間で共有されているか | PJ-Aは99.9%可用性を前提に設計しているが、PJ-Bが使うインフラはその前提を満たしていない |
| Test Scenario | E2Eシナリオが個別PJのテスト範囲だけでカバーされていないか | 「複数PJをまたぐ購入フロー」のテストが、どのPJのテスト計画にも入っていない |

### 6.4 Consistency Issue Log ―― Matrixだけでは足りない部分

Consistency Matrixは「○」か空欄かの二値で、整合確認の**俯瞰**を得るための表である。しかし実務では、Matrixの「○」だけでは次のことが後から分からなくなる。

> PJ-AとPJ-Bの何と何を、どういう観点で突き合わせて、結果どうだったのか？

これを残すために、Matrixとは別に**Consistency Issue Log**（詳細ログ）を持たせる。Matrixが「俯瞰」であるのに対し、Issue Logは「具体的な不整合の記録」である。

| ID | 観点 | From成果物 | To成果物 | 確認ポイント | Result | Open Point |
|---|---|---|---|---|---|---|
| C01 | 要件 | 業務要件定義書 v1.3 | 基本設計書 v0.8 | 要件反映 | Amber | 要件R-032が未反映 |
| C02 | Data | データ定義書 | DB設計書 | 桁・型・コード | Green | ― |
| C03 | IF | API仕様 | IF設計書 | 項目/型/必須/頻度 | Red | 顧客ID桁数が不一致 |

ポイントは次の3つである。

- **From/Toは成果物名＋バージョンまで書く**：「PJ-Aの要件」ではなく「業務要件定義書 v1.3」まで特定する。バージョンが変わればIssueも再確認が必要になるため、これが曖昧だと「いつの時点の確認か」が追跡できなくなる
- **確認ポイントを具体化する**：「整合確認」ではなく「要件反映」「桁・型・コード」「項目/型/必須/頻度」のように、何を突き合わせたのかを一段具体化して書く
- **ResultはDependency Registerと同じGreen/Amber/Redで統一する**：管理表間で status の意味を揃えておくことで、Weekly Dashboardでの横断集計がそのまま使える

運用としては、Matrixの「○」を付ける前提として、対応するIssue Logの行がGreenになっていることを条件にする。つまり、**Matrixは結果の一覧、Issue Logはその根拠**という関係になる。Matrixだけを埋めて、根拠となる突き合わせ記録が存在しない状態を防ぐのがこのログの役割である。

### 6.5 MatrixとIssue Logをどう使い分けるか

Consistency Matrixだけを渡すと、本人は「Matrixのセルを○で埋める作業」だと誤解しやすい。実際は逆で、**先に埋めるのはIssue Logであり、Matrixの○はその結果が自動的に映るものにすぎない**。運用は次の順序で回す。

```text
① Hand-off発生時、またはIFレビュー完了時（Chapter 3.6）
        ↓
② Consistency Issue Logに1行追加する
   （From/To成果物・バージョン・観点・確認ポイントを記載）
        ↓
③ 実際に成果物を突き合わせて確認する
   （Ownerは該当領域の成果物を読める担当者）
        ↓
④ Result（Green/Amber/Red）を判定する
   （判定基準はChapter 8.2のRAGステータス定義を使う）
        ↓
⑤ Greenになって初めて、Consistency Matrixの該当セルに「○」を付ける
        ↓
⑥ Amber/Redの間、Matrixのセルは空欄のまま
   （Issue LogとWeekly Meetingで経過を追う）
```

Consistency Matrixの「○」は「レビュー済み・整合確認済み」を意味するものであり、単に「両PJに関係がある」という理由だけで機械的に埋めてはならない。Ownerは、該当領域の成果物を実際に突き合わせ、矛盾がないことを確認した上で初めて「○」を付ける。

最も誤解しやすいのは、「Matrixのセルから埋め始めようとする」ことである。Matrixに触れる前にまずIssue Logの1行を自分で書いてみて、「Matrixは自分で塗るものではなく、Issue Logの結果が映るものだ」という順序で理解すると定着しやすい。

- [ ] 「Consistency」が指す不整合を、自分の言葉で具体例つきで説明できるか
- [ ] Consistency Matrixの「○」が、実際の突き合わせに基づいているか（機械的に埋めていないか）
- [ ] 「各社の成果物単体では正しいが、つなぐと成立しない」事例を最低1件、自分で見つけられたか
- [ ] Matrixで「○」を付けている行について、根拠となるConsistency Issue Logの記録があるか
- [ ] Issue LogのFrom/To成果物にバージョンが明記されているか
- [ ] Matrixのセルから埋めようとせず、Issue Logの1行から書き始められているか

## Chapter 7. Monitoring & Control

### 7.1 「差分を見る」というシンプルな原則

毎週すべての成果物を読む必要はない。見るべきは常に次の流れである。

**Baseline → Current → Variance → Impact → Action**

### 7.2 具体例

```text
Dependency D-12
Baseline
A社：9/10 API仕様確定
      ↓
B社：9/15 開発開始

Current
A社：9/18予定
      ↓
8日遅延

Impact
B社開発開始 +8日
→ 結合テスト +5日
→ 総合テスト開始 +3日

Action
① API仕様を分割確定
② Critical項目のみ9/10確定
③ 残項目9/18
④ B社はCritical部分から開発開始
```

### 7.3 「遅れてます」ではPgMOになっていない

> 「遅れてます」ではPgMOになっていない。
> 「何に波及するか」と「どう吸収するか」まで考えて初めてControlである。

遅延の事実報告だけを行い、下流への波及（Impact）と対応策（Action / Recovery Option）まで踏み込まない状態は、モニタリングはできていてもコントロールはできていない。Impact ExtendingとRecovery Optionは、常にセットで考える。

### 7.4 Forecast と Recovery Plan

Varianceが発生した時点で、現状のペースのまま進んだ場合の着地予測（Forecast）を作り、Baselineとの差分に対する挽回策（Recovery Plan）を検討する。挽回策の選択肢は多くの場合、次のいずれかに整理できる。

- スコープを分割し、Critical項目のみ先行確定させる
- 並行作業できる範囲を広げ、後続PJの着手を前倒しする
- バッファ（Lag）を消化する
- 後続PJのスコープ・体制を調整する

### 7.5 Escalation

PgMO単独で解決できない事項（契約・追加コスト・優先順位判断を伴うもの）は、放置せず速やかにSteering Committeeへエスカレーションする。エスカレーションの基準（Amber/Redの定義）はChapter 8.2で具体的に定義する。

### 7.6 先読み（転ばぬ先の杖）を「型」にする

ここまでのBaseline→Current→Variance→Impact→Actionは、**すでに起きた変化**にどう対応するかという型である。しかしPgMOにはもう一段上の動きが求められる。**まだ起きていない変化を、起きる前に潰す**動きである。これがいわゆる「転ばぬ先の杖」であり、多くの担当者がここでつまずく。

**なぜ先読みができないのか**

精神論で「先を読め」と言っても改善しないことが多い。原因は本人の資質ではなく、次の3つの構造的な要因であることがほとんどである。

| 要因 | 内容 |
|---|---|
| 経験不足 | 「これが遅れると3週間後にこう波及する」という因果の連鎖は、過去に似た失敗パターンを見たことがある人にしか見えない。見えていないものには備えようがない |
| インセンティブの歪み | 火消し（起きた問題への対応）は目に見えて評価されるが、予防（起きなかった問題）は「何も起きなかった」としか見えないため評価されにくい。加えて、確定していない懸念を早めに言うと「気にしすぎ」と扱われるリスクがあるため、確信が持てるまで黙ってしまう |
| キャパシティ不足 | 目の前の対応で手一杯だと、先を読む余力そのものが残らない |

これらは指導や叱責では解決しない。**先読みを本人の資質ではなく、型・儀式・ノルマに変える**ことで解決する。

**対策1：Weekly Meetingを「今のAmber/Red」だけでなく「未来のAmber/Red」を扱う場にする**

Chapter 8.1のCross-Project Control Cycle②「2〜4週間以内のPJ間受け渡し」を、単なる予定確認で終わらせない。次の問いに、Weekly Meetingで毎回、最低1件は自分で答える。

> 今Greenのものの中で、2〜4週間後にAmberへ落ちる可能性が最も高いのはどれか？　その予兆は何か？

これにより、「先読みするかどうか」が本人の裁量ではなく、会議の必須アジェンダになる。Chapter 3.5のCritical Dependencyの判定基準（波及が大きい・手戻りコストが大きい）は、そのままこの問いの判断軸として使える。

**対策2：早期警告の「空振り」を罰しないと明言する**

早期警告が外れても構わないことを、自分の中で明確な前提として持っておく。

> 杞憂で終わった指摘のコストは数分だが、言われなかったリスクが実際に起きたときのコストは数週間になる。だから今後は空振りでいいから、早めに教えてほしい。

これを明言しないと、「外れたら恥をかく」という理由で沈黙を選び続けてしまう。早期警告を出した回数そのものを、遅延を防いだ回数と同じかそれ以上に評価する姿勢を、自分の中で持っておく。

**対策3：フェーズの節目でプリモーテム（事前検死）を行う**

プリモーテムとは、まだ何も起きていない時点で「将来失敗したと仮定して、その原因を先に洗い出す」手法である。フェーズの節目（要件FIX前、統合テスト開始前など）ごとに、次の手順で実施する。

1. 「3ヶ月後、このプログラムが炎上したと仮定する」という前提を置く
2. 「原因は何だったと思うか」を自由に挙げる（この時点では実現可能性を問わない）
3. 挙げられた原因のうち、実際に予兆があるものをDependency RegisterまたはRAID Logに転記する
4. 予兆がまだないが可能性として否定できないものは、RAID LogにAssumption／Riskとして残しておく

プリモーテムは「今何が起きているか」ではなく「将来失敗するとしたら何が原因か」を強制的に想像させる練習であり、経験不足を補うための最も効果的な訓練の一つである。

### 振り返りメモ（自己学習用）
- [ ] Baseline→Current→Variance→Impact→Actionの5ステップを、実際のDependencyで3件説明できるか
- [ ] 「遅延の報告」で終わらず、「波及」と「吸収策」まで言語化できているか
- [ ] 直近のWeekly Meetingで、「今Greenの中で次にAmberへ落ちそうなもの」を1件でも挙げられたか
- [ ] 早期警告を出したことを、自分の中できちんと前向きに評価できているか（外れたことを気に病みすぎていないか）

## Chapter 8. Cross-Project Governance

### 8.1 Weekly Cross-Project Meetingを進捗報告会にしない

各ベンダーが「予定通りです」「設計中です」「課題2件あります」と順番に報告するだけの会議は、プログラム会議として機能していない。個別PJの進捗報告は各PJ内の会議で完結させ、Cross-Project Meetingでは次の**Cross-Project Control Cycle**のみを扱う。

```text
① 前回から変わったDependency
        ↓
② 2〜4週間以内のPJ間受け渡し
        ↓
③ Amber / Red Dependency
        ↓
④ Scope / Requirement / Designの不整合
        ↓
⑤ 意思決定が必要な事項
        ↓
⑥ Action / Owner / Due
```

### 8.2 RAGステータスの判定基準

Dependency Register・Integrated Milestone Plan・Consistency Issue Log・RAID Logは、いずれもStatus列にGreen／Amber／Redを記入する運用になっている。しかし、この判定基準を最初に定義しておかないと、担当者ごとに「Green」の意味がずれ、Weekly Dashboardの集計が実態を反映しなくなる。

| Status | 定義 | 対応 |
|---|---|---|
| Green | Baselineどおり進んでいる、またはVarianceが許容バッファ内に収まっている | 現状維持。次回更新まで通常のモニタリングを続ける |
| Amber | Varianceが発生しているが、Recovery Planによって許容バッファ内に着地する見込みがある。またはVariance自体は軽微でも、放置すると悪化する予兆がある | Forecast／Recovery Planを作成し、Weekly Meetingで経過を追う。原則としてPgMO内で対応を試みる |
| Red | Recovery Planを講じても許容バッファを超える見込みである。または契約・追加コスト・優先順位判断を伴う事項が発生している | 直ちにSteering Committeeへエスカレーションする（8.5） |

「許容バッファ」は目安であり、機械的な閾値ではない。プログラムの規模やリスク許容度に応じて、たとえば「Varianceが5営業日以内はAmber、それを超えたらRed」のように、着任後の早い段階で具体的な数値基準を決めさせておくと、判定のブレが減る。

もう一点、徹底したいのは、**RAGはBaseline／Varianceという事実に基づく判定であり、ベンダーとの関係性への配慮で甘くする（忖度でGreenにする）ものではない**という点である。これはChapter 7.6の「早期警告の空振りを罰しない」姿勢と表裏の関係にあり、正直にAmber／Redを付けられる自分なりの基準を持っておくことが前提になる。

### 8.3 RAID

Risk（リスク）・Assumption（前提）・Issue（課題）・Dependency（依存）を一元管理する。特にAssumptionは軽視されがちだが、「前提が違っていた」ことが後工程で発覚するとほぼ確実に手戻りが発生するため、Dependency Registerと同じ重みで扱う。

4つの区分は似て見えるが、問うべき観点が異なる。区分を混同したままログに書くと、対応の緊急度もオーナーも曖昧になるため、最低限次の観点だけは押さえる。

| 区分 | 一言の定義 | 問うべき観点 | 主な記入タイミング |
|---|---|---|---|
| Risk（リスク） | まだ起きていないが、起きる可能性がある将来の問題 | 発生確率は？　発生した場合の影響度は？　誰が監視するか？ | 着任時、フェーズの節目、プリモーテム実施時 |
| Assumption（前提） | 確認せずに「そうだろう」と置いている仮定 | 何を前提にしているか？　誰がいつまでに確認・裏付けを取るか？　外れていた場合の影響は？ | 管理表・計画を作成するタイミング全般 |
| Issue（課題） | すでに顕在化している、対応が必要な問題 | 誰がいつまでに、何を対応するか？　放置した場合の影響は？ | 発生を検知した時点で即時 |
| Dependency（依存） | PJ間で受け渡しが必要な事項（Chapter 3で詳述） | 何を、いつ、誰から誰に渡すか？ | Interaction Map作成時、以降は変更検知時 |

4区分の中で最も見落とされやすいのはAssumptionである。RiskやIssueは「問題」として意識されやすいが、Assumptionは「当然そうだろう」という思い込みの形を取るため、本人が意識的に洗い出さない限りログに乗らない。Chapter 7.6の対策3（プリモーテム）で洗い出された「予兆がまだないが可能性として否定できないもの」の受け皿は、このAssumption／Risk区分である。フェーズの節目でプリモーテムを行った際は、その場でRAID Logへの転記までを一連の作業としてやり切る。

### 8.4 Decision Log / Change Control

PJ間にまたがる意思決定は、口頭や個別メールで済ませず、Decision Logに残す。あるPJの合意がSteering前提だったのか、PgMO内で完結してよい事項だったのかを後から追跡できるようにする。スコープや前提に影響する変更は、必ずChange Controlのプロセスを通す。

Change Controlの最小限の流れは次の通りである。

```text
① 変更起票（誰が・何を・なぜ変えたいか）
        ↓
② 影響分析（Dependency Register / Consistency Matrix / Scheduleへの波及）
        ↓
③ PgMO一次判断（軽微：PgMOで処理可／重大：Steeringへ）
        ↓
④ 承認（PgMO or Steering Committee）
        ↓
⑤ Dependency Register・Consistency Matrix・Scheduleへの反映、関係PJへの通知
```

本Playbookが扱うのは「変更は必ずこの流れを通す」という原則と、②の影響分析にDependency Register・Consistency Matrixを使うという接続部分までである。承認体制（SteerComm／Program Board／standup／inspectionの各会議体の設計と役割分担）そのものの詳細設計は、姉妹Playbook（会議体設計の原典）の範囲とする。ガバナンス設計そのものを任される場合は、あわせてそちらも参照する。

### 8.5 Steering Committee

PgMOが単独で判断できない事項（優先順位・追加コスト・契約に関わる事項）を扱う上位会議体。Chapter 1.4の体制図における最上位のエスカレーション先にあたる。Amber/Redのままエスカレーションせずに滞留させることが最もリスクが高いパターンであるため、エスカレーション基準と頻度を事前に合意しておく。

### 8.6 ベンダー間の板挟みへの具体的対処

Chapter 1.3で述べた通り、各ベンダーPMが自社の利益を優先するのは自然な行動であり、PgMOは構造的に板挟みになりやすい立場にある。感覚論で乗り切らせず、次の具体的な型を持たせる。

1. **事実と主張を分けて記録する**：「A社は要件が遅いと言っている」「B社は要件を受け取っていないと言っている」という双方の主張を、Dependency RegisterやConsistency Matrix上の事実（Status・確認日・Owner）と突き合わせる。感情的な対立が起きている場面ほど、PgMOは記録された事実だけで語る
2. **契約論とプログラム全体最適論を分離する**：「契約上どちらの責任か」という論点と、「プログラム全体としてどう前に進めるか」という論点を同じ会議で混在させない。前者は契約担当・PM上位者の論点であり、PgMOがその場で裁定しようとしない
3. **合同会議の前に個別ヒアリングを挟む**：対立が先鋭化している場合、いきなり合同会議で対峙させず、まず1対1で双方の言い分を個別に聞いてから、論点を整理した上で合同の場に持ち込む
4. **「誰が悪いか」ではなく「Scope Boundary Matrix上どうなっていたか」に立ち返る**：責任のなすりつけ合いになったら、感情論ではなくChapter 5のScope Boundary Matrixで実際に○が付いていたのはどちらかという事実に立ち返って議論する
5. **抱え込まずエスカレーションする**：PgMO自身が板挟みのストレスを一人で抱え込み、判断を先送りにすることが最もリスクが高い。エスカレーション基準（8.5）に該当する場合は、遠慮せずSteering Committeeに上げる

### 8.7 更新頻度とツール（PMIS）の選び方

Dependency Register・Consistency Matrix・RAID/Decision Logは、作って終わりでは機能しない。更新頻度とツールを最初に決めておく。

| 項目 | 目安 |
|---|---|
| Dependency Register・RAID Log | 週次（Weekly Cross-Project Meetingの前に更新） |
| Consistency Matrix | Hand-off発生時、またはIFレビュー完了時に都度更新 |
| Integrated Milestone Plan | 月次で洗い替え、Varianceが発生したら都度更新 |
| Weekly Dashboard | 毎週のCross-Project Meeting直前に集計 |

ツールは、プログラムの規模とベンダー数に応じて選ぶ。PJ数が少ない（目安5PJ以下）うちはExcel（Appendixのテンプレート）で十分機能する。PJ数・ベンダー数が増え、複数拠点・複数社が同時編集する必要が出てきたら、PMIS（Project & Program Management Information System。Smartsheet・Confluence＋Jira・MS Projectサーバ版等）への移行を検討する。ツールを変えても、Chapter 3〜6で定義した「管理すべき5領域」という構造そのものは変わらない。ツール選定を先に決めてから中身を考えさせないこと。

### 振り返りメモ（自己学習用）
- [ ] 直近のWeekly Meetingのアジェンダが、進捗報告会になっていないか
- [ ] Green/Amber/Redの判定基準を、Varianceの日数など具体的な数値で決めているか
- [ ] RAID/Decision Logのうち、実は口頭合意のまま記録されていない事項がないか
- [ ] 直近のベンダー間対立で、事実（管理表）と主張を分けて整理できていたか
- [ ] 各管理表の更新頻度が、本人の中で明確になっているか

## Chapter 9. 実践演習

### ケース：4社・5プロジェクトによる基幹システム刷新

以下は演習用の設定である。実際の担当プログラムに近い形に読み替えて実施してもよい。

- PJ-A（A社）：業務要件定義・BPR
- PJ-B（B社）：基幹システム本体の設計・開発
- PJ-C（C社）：外部連携・周辺システムI/F
- PJ-D（D社）：データ移行
- PJ-E（社内／PMO兼任）：テスト統括・移行リハーサル

### 演習ステップ

1. Interaction Mapを作る（Chapter 2）
2. Dependencyを抽出する（Chapter 3）
3. Scope Boundaryを定義する（Chapter 5）
4. Integrated Scheduleを作る（Chapter 4）
5. 不整合を発見する（Chapter 6）
6. 遅延影響を分析する（Chapter 7）
7. Recovery Planを作る（Chapter 7）
8. Steering向けに報告する（Chapter 8）

### 進め方（目安：90分×2回。自分のペースで進めてよい）

**Session 1：構造化（90分）**

実際の担当プログラムについて、次の順で自分に問いながらInteraction Mapを作る。

1. PJはいくつあるか
2. 各PJの責任範囲はどこまでか
3. PJ間に矢印を引く
4. その矢印で何が渡るか
5. いつ渡るか
6. 間違っていたら何が起こるか

**Session 2：Control（90分）**

実際のDependencyを3件選び、次の順で自分で考える。

1. Baselineは何か
2. 現在はどうなっているか
3. Varianceはどれくらいか
4. Downstream Impactは何か
5. Recovery Optionは何か
6. 誰に何を決めてもらう必要があるか
7. Steering Committeeへの説明を、Detect（検知）→ Analyze（分析）→ Recover（挽回策）→ Recommend（推奨）→ Ask（依頼）の1枚にまとめる

演習はステップ6で終わらせない。Recovery Optionを考えたところで止まると、本人は「分析はできるが、決めてもらうところまで持っていけない」状態のままになる。ステップ7で、実際にSteering Committeeに何を承認してもらうのかを、1〜2文で言い切らせるところまでを演習のゴールにする。

この2セッションを通してやれば、型としての感覚はかなり掴める。以後は自分のプログラムで実践しながら、月1回程度、Consistency Matrixとの突き合わせ結果を振り返るとよい。

### 演習の参考解答（例）

参考解答の記入例。自分の解答をそのまま置き換えるのではなく、「観点が抜けていないか」を照らし合わせる目的で使う。先に見ず、まず自分で解いてから照らし合わせること。

**Session 1（Interaction Map）の記入例**

```text
PJ-A（業務要件定義）─要件定義書─▶ PJ-B（基幹システム）
PJ-D（データ移行）  ─データ定義─▶ PJ-B（基幹システム）
PJ-B（基幹システム）─API/IF仕様─▶ PJ-C（外部連携）
PJ-B（基幹システム）─移行用データ環境─▶ PJ-D（データ移行）
PJ-B・PJ-C・PJ-D    ─テストシナリオ─▶ PJ-E（テスト統括）
```

想定される「抜けやすいポイント」：PJ-Bのテスト環境をPJ-Eがいつ・どの状態で受け取るか（環境というInputが図から漏れがち）。自分の解答にこの矢印がなければ、そこを見直す。

**Session 2（Baseline→Recovery）の記入例**

対象Dependency：PJ-B → PJ-C（API仕様確定）

| 項目 | 内容 |
|---|---|
| Baseline | PJ-B社内レビュー完了 9/10、PJ-C開発着手 9/15 |
| Current | PJ-B社内レビューが要件差し戻しで 9/18 にずれ込む見込み |
| Variance | 8日遅延 |
| Downstream Impact | PJ-C開発着手 +8日／結合テスト +5日／総合テスト開始 +3日（バッファLagで一部吸収） |
| Recovery Option | ①API仕様のうちCritical項目（認証・必須項目）のみ9/10で先行確定 ②非Critical項目は9/18確定 ③PJ-CはCritical部分から開発着手し並行度を上げる |
| 誰に決めてもらうか | Critical/非Critical分割の妥当性はPgMOで判断可。開発体制の組み替えはPJ-C側のPMと合意が必要 |

この記入例のポイントは、Recovery Optionが「待つ」以外の選択肢（分割・並行化・バッファ消化）を含んでいること、および最後の行で「PgMOだけで完結する意思決定」と「相手PJの合意が要る意思決定」を切り分けていることである。自分の解答がAction止まりで終わっている場合は、この切り分けまで踏み込んで考える。

**Session 2（Steering Committeeへの Decision Request）の記入例**

上記の分析を、Steering Committeeでそのまま話せる1枚に落とすと次のようになる。

> PJ-BのAPI仕様確定が8日遅延見込みです（Detect）。現状のままでは総合テスト開始に3日波及します（Analyze）。一方、Critical項目を先行確定すれば影響を吸収できます（Recover）。PJ-C側の開発体制組替えが必要なため（Recommend）、本日はこの対応方針の承認をお願いします（Ask）。

ポイントは、Detect（何が起きたか）とAnalyze（何に波及するか）だけで終わらせず、Recover（どう吸収するか）・Recommend（PgMOとしての推奨案）まで自分で組み立てたうえで、最後は必ずAsk（何を承認してほしいのか）で締めることである。これは「結論→根拠→提案→依頼」という構造化思考の型とも一致しており、Detect／Analyze／Recoverが根拠、Recommendが提案、Askが依頼にあたる。自分の解答が「現状報告」で終わっている場合、Askの一文が言えるかどうかを最後に必ず確認する。

### 振り返りメモ（自己学習用）
- [ ] 演習で作ったInteraction Mapを、実プログラムに置き換えられるか
- [ ] Session 2で選んだ3件のDependencyについて、Recovery Optionを自分の言葉で説明できるか
- [ ] Detect→Analyze→Recover→Recommend→Askの1枚を、現状報告で終わらせずAskまで言い切れているか
