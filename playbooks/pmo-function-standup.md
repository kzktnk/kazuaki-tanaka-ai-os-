# PMO Function Standup Playbook

**Version:** v0.1  
**Status:** Active  
**Owner:** Kazuaki Tanaka  
**Purpose:** 業務改革／基幹導入の **PMO を文書としてではなく運用可能な組織として立ち上げる**  
**Use when:** 次期中計や ERP / 基幹導入の前に「PMO 規定はあるが回っていない」、品質・進捗・拠点展開の章が目次だけのとき  
**Do not use as-is for:** 官側調達 PMO（`frameworks/public-it-procurement-support.md`）、単一プロジェクトの事務事務局

Pairs with `frameworks/transformation-pmo.md`（PMO とは何か）and `standards/pmo-operating-guide.md`（回し方）。本 Playbook は **立ち上げ順序**。人側の計画の中身は `frameworks/change-management.md` §4。AI で CoE / PgMO / Change を混ぜるなは `knowledge/patterns/ai-coe-vs-pgmo-vs-change.md`。

## Trigger

改革プログラムの管理規定・組織図はあるが、品質管理・拠点進捗・問題エスカレーションが実運用まで落ちていない。次期フェーズの本格立ち上げまで時間が残っている。

## Objective

本格期間の開始時点で、管理枠組みを **パイロット運用済み** にし、PMO の役割・スキル・拠点カバーが人と手順に載っている状態にする。

## Prerequisites

- プログラムの目的と期間（今期／次期）がスポンサーで共有されている  
- 「PMO を置く」こと自体が目的化していない（成果は業務・システムの一体導入）  
- 拠点展開があるなら、本部 PMO と現場進捗の切れ目が認識されている  

## Required inputs

- 既存の PJ 管理規定（目次と中身の差が分かるもの）  
- プログラム体制案、拠点一覧、品質・進捗の現状ルート  
- 次期フェーズの大日程（未確定なら仮でも可）  
機密の社名、期番号、金額、個人名は原本のみ。

## Escalation conditions

- 規定の穴（特に品質）を埋めずにキックオフ日だけ決まっている → スポンサーへ「運用なき PMO」リスクを上げる  
- 拠点問題が個別プロジェクト長に閉じて見える → プログラム層へエスカレーション設計を要求  
- 人材が「調整役」しかいない → `knowledge/patterns/hybrid-talent-in-transformation.md`  

## Sequence

1. **規定の穴を列挙する**  
   目次にあるが中身がない章（品質が典型）を、運用可能な手順まで落とす対象にする。枠組み理解のセッションと同時に進める。

2. **PMO のカバー範囲を決める**  
   プログラム全体、個別 PJ、拠点導入の進捗・問題のどれを見るかを分ける。全部を一人に載せない。

3. **役割と必要な経験を役割単位で書く**  
   スキルは「PMO 経験」ではなく、統合・品質・拠点・意思決定支援のどれか。

4. **本格期の前に準備組織を置く**  
   ベースライン確定とパイロット運用を、本格体制の前に終える。キックオフ当日に規定を配らない。

5. **パイロットで枠組みを回す**  
   小さな領域で進捗・問題・品質のルートを一度通す。通らない手順は本規定に戻さない。

6. **人と枠を同時に渡す**  
   枠だけ残して人が空、人だけ増えて枠が空、のどちらも失敗。ハイブリッド人材は別パターン。

## Done when

- 品質を含む管理規定が、目次ではなく手順になっている  
- 準備組織がパイロットを一度回している  
- 本格期の体制イメージ（PJ 長支援と拠点）が人と役割で対応している  

## Limitations

単一パッケージ導入の WBS 詳細、法定公共調達の官側事務局、定常 PMO の年間ローテーションは対象外。
