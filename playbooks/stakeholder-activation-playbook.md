# Stakeholder Activation Playbook

**Version:** v0.1  
**Status:** Active  
**Owner:** Kazuaki Tanaka  
**Purpose:** 特定の相手（個人／少人数）を、説得ではなく **行動変容の設計** で動かす  
**Use when:** 正しい説明をしているのに人が動かない、誰から動かすかが決まっていない、説明したことを進捗と誤認している  
**Do not use as-is for:** 組織全体のチェンジプロセス設計（`frameworks/change-management.md`）、操作・欺瞞、①の戦略構造化、②の PJ 間統制、③の移行設計そのもの  
**Source revision:** local Stakeholder Activation Playbook draft（2026-08-28）

Pairs with `frameworks/change-management.md`（Readiness／Strategy／Commitment の組織層）。本 Playbook はその中の **戦術層**：Segment → Diagnose → Select → Tailor → Observe。①②③すべてから参照する横串。Channel は 6 ステップ目ではなく Tailor と Observe の間の実行レイヤー。

## このPlaybookの目的

Stakeholderを動かす場面を持つすべての実務担当者が、次の3つの問いに自力で答えられるようになることを目的とする。

- 誰から、どの順番で動かすべきか（Chapter 2）
- 相手が動かない理由を、どう診断し、どう打ち手を選ぶか（Chapter 3・4）
- メッセージをどう相手ごとに調整し、行動が変わったかをどう確認するか（Chapter 5・6）

**射程の明示**：本Playbookは、特定の相手（個人、または少人数のグループ）を、実際の判断・行動へと動かすための実務レベルの技術を扱う。組織全体のチェンジマネジメント・プロセス設計（Readiness評価、全体戦略、ワークストリーム設計）は`frameworks/change-management.md`の対象であり、本Playbookはその中で、個々のStakeholderに対して**具体的に何をどう働きかけるか**という、より戦術的・個人技術的なレイヤーを扱う。

本Playbookは、相手を意のままに操作するための技術ではない。目的は、相手が抱える論理的・感情的な障壁を理解し、相手自身が必要な判断・行動を取りやすい状態を設計することである（Chapter 1.4）。

### ①②③との関係 ―― 横串のPlaybook

本Playbookは、①②③のようにコンサルティング業務の特定フェーズに紐づく縦の資産ではなく、①②③のすべてから参照される横串の資産である。

```text
① 戦略立案・SCN          ② Cross-Project           ③ Operations Transition
  Sponsor／事業部を        Vendor PM・部門長・        現場・ミドル層に
  動かす                   意思決定者を動かす         新運用を使わせる
        │                        │                        │
        └────────────────────────┴────────────────────────┘
                                  │
                    Stakeholder Activation Playbook
              （相手ごとに、なぜ動かないかを診断し、
                打ち手とメッセージを選ぶ「動かし方」の型）
```

③のChapter 7.4は「相手が今どの段階にいるか」を診断するが、そこから実際に相手を動かす技術は本Playbookに譲っている（③Chapter 7.8参照）。

## 使い方

1. Chapter 1で、本Playbookの軸（相手の属性で片付けない、操作のPlaybookにしない）を作る
2. Chapter 2で、誰から動かすかをSegmentする
3. Chapter 3で、動かない理由をDiagnoseする
4. Chapter 4で、診断に応じた打ち手をSelectする
5. Chapter 5で、メッセージをTailorする
6. Chapter 6で、行動が変わったかをObserveし、変わっていなければChapter 3〜5およびChannel選択（Chapter 8）を見直す
7. Chapter 7で、Segmentの両端（Champion候補・Key Blocker）への具体的な対応を学ぶ
8. Chapter 8で、打ち手を届けるチャネル（1対1／会議／Workshop／Sponsor経由）の使い分けを学ぶ
9. Chapter 9の演習で、実在に近いケースを使って5ステップを一通り自分の手で作ってみる
10. Appendixのテンプレートを、自分が実際に動かそうとしている相手に当てはめて埋める

Segment→Diagnose→Select→Tailor→Observeは、一度回して終わりではなく、Observeの結果に応じてDiagnoseからやり直す循環として使う。

### Self-study companion（メンティー向け）

指導者同席を前提にした本文が正本。一人で進めるときは次だけ守る（全文の別コピーは持たない）。

1. Chapter 順に読み、各章末の「レビュー用メモ」を**セルフチェック**として自分で埋める
2. 読むだけで終わらせず、Chapter 9 か実在の相手のどちらかで手を動かす
3. Chapter 9 は facilitator なしでも可。参考解答は先に見ない
4. ①②③の特定フェーズの Playbook ではなく、横串であることを先に把握してから Chapter 2 に入る
5. Observe で行動が変わっていなければ Diagnose / Select / Tailor / Channel に戻る
6. 内容改訂は常に本 Playbook 側。文体だけのセルフスタディ派生はローカルに留め、repo には本節のみ載せる

## Chapter 1. 人は「正しい説明」だけでは動かない

### 1.1 核心の主張

最初に押さえるべきことは、次の一文に尽きる。

> 論理的に正しい説明をすることと、人が実際に動くことは、別の問題である。

同じ立場・同じ情報に接している人の間でも、自ら動き出す人と、なぜか関心を示さない人に分かれることがある。例えば、同じ実務担当という立場の中でも、自分の仕事を振り返って型（アセット）に残そうとする人もいれば、勧めても手が動かない人もいる。両者が受け取った説明は同じであることが多い。差を生んでいるのは、情報の量でも正しさでもない。

### 1.2 「相手が動かない」を相手の属性にしない

「相手が動かない」を見たとき、最も安易な説明は「あの人はやる気がない」「あの人は保守的だ」という、相手の属性への帰属である。これは思考停止に等しい。相手の属性で片付けた瞬間、次に自分がやることがなくなるからである。

> 「相手が動かない」をStakeholderの属性として片付けない。まず、自分の診断・打ち手・メッセージ・チャネルが適切だったかをレビューする。

これが本Playbookを貫く原則である。相手が動かないなら、それは診断（Chapter 3）が誤っているか、打ち手（Chapter 4）が合っていないか、メッセージ（Chapter 5）が相手に刺さっていないか、伝えるチャネルが適切でないかのいずれかである可能性を、まず自分の側に置く。

### 1.3 5つのステップの全体像

本Playbookは、次の5ステップで「動かし方」を型にする。

1. **Segment**（Chapter 2）：全員を同じ熱量で説得しようとせず、誰から動かすかを仕分ける
2. **Diagnose**（Chapter 3）：動かない理由を、論理・感情・能力・環境のどれかで診断する
3. **Select**（Chapter 4）：診断した理由に応じて打ち手を選ぶ
4. **Tailor**（Chapter 5）：メッセージの芯は共通にしつつ、相手ごとに響く理由を変える
5. **Observe**（Chapter 6）：説明したかではなく、行動が変わったかを見る

```text
Segment → Diagnose → Select → Tailor → [Channelで届ける] → Observe
```

Channel（1対1／会議／Workshop／Sponsor経由、Chapter 8）は、独立した6つ目のステップではない。Selectした打ち手とTailorしたメッセージを「どう届けるか」を決める実行レイヤーであり、Tailorの後・Observeの前に必ず一度通る。5ステップという骨格を崩さないために、Channelは太い箱ではなく、Tailor→Observeの間に挟まる細い実行の箱として扱う。

この5ステップは、③のChapter 7.4（Unawareness→Awareness→Buy-in→Ownership）のような「相手が今どこにいるか」を診断するモデルと組み合わせて使う。現在地が分かった後、実際にその人を動かす技術が本Playbookである。

### 1.4 これは「操作」のPlaybookではない

本Playbookの目的は、相手を意のままに操作することではない。相手が抱える論理的・感情的な障壁を理解し、相手自身が必要な判断・行動を取りやすい状態を設計することである。相手を欺いたり、不安を煽ったり、事実を歪めて伝えたりする技術は、本Playbookの対象外であり、推奨もしない。

### レビュー用メモ（本人との議論用）
- [ ] 「相手が動かない」を相手の属性で片付けそうになった経験を、具体的に1つ思い出せるか
- [ ] 5つのステップを、自分の言葉で順番通り説明できるか

## Chapter 2. Segment ―― 誰から動かすか

### 2.1 全員を同じ熱量で説得しない

Stakeholderへの働きかけは、時間・体力ともに有限である。にもかかわらず、動かない相手ほど繰り返し説得しようとし、放っておいても動く相手には時間を使わない、という配分の逆転が起きやすい。

> 全員を同じ熱量で説得しない。

まず相手を仕分け、どこに時間を使うかを決めることが最初の作業になる。

### 2.2 動きそう度×影響力で仕分ける

| | 影響力 低 | 影響力 高 |
|---|---|---|
| 動きそう度 高 | Supporter | **Champion候補** |
| 動きそう度 低 | Observe | **Key Blocker／Key Influencer** |

「動きそう度」は、Chapter 3で診断する4つの障壁（論理・感情・能力・環境）が、その人にとってどれだけ低いかの見立てである。「影響力」は、その人が動いたときに他の人へどれだけ波及するかである。

最初のSegmentは、Chapter 3のDiagnoseをまだ行っていない段階で置く仮置きでよい。観察できる行動や過去の反応（会議での発言、これまでの類似の変化への反応など）から見立て、Diagnoseした後に必要ならSegmentを更新する。Segment→Diagnoseは一方通行ではなく、後から仮置きを直す前提で使う。

### 2.3 4象限それぞれの扱い方

| 象限 | 扱い方 |
|---|---|
| Supporter（動きそう度高・影響力低） | 個別に丁寧な説得は不要。感謝を伝え、必要なときに事例として使わせてもらう |
| Champion候補（動きそう度高・影響力高） | 最優先で投資する。「説得する相手」ではなく「他者を動かす側に回ってもらう相手」として扱う |
| Observe（動きそう度低・影響力低） | 今は積極的に動かしにいかない。状況が変われば再評価する対象として保留する |
| Key Blocker／Key Influencer（動きそう度低・影響力高） | 最優先でDiagnose（Chapter 3）にかける。放置すると他者への波及がマイナス方向に働く |

Champion候補とKey Blocker／Key Influencerの2象限に時間の大半を割く、というのがSegmentの実務的な結論である。

### レビュー用メモ（本人との議論用）
- [ ] 今動かそうとしている相手を、実際にこの2×2に当てはめられるか
- [ ] Champion候補とKey Blocker／Key Influencerに、時間の大半を割けているか

## Chapter 3. Diagnose ―― なぜ動かないか

### 3.1 「もっと説明しよう」が典型的な失敗である理由

相手が動かないとき、最も起きやすい反応は「もっと説明しよう」である。資料を厚くする、会議を増やす、根拠を積み増す。しかし、動かない理由が説明不足でなかった場合、この対応は効果がないばかりか、相手の負担を増やして逆効果になることさえある。

診断せずに打ち手を打つのは、症状を聞かずに薬を出すのと同じである。

### 3.2 4つの障壁

| 障壁 | 内容 |
|---|---|
| Logic | 必要性やメリットが理解できていない |
| Emotion | 不安、喪失感、不信感がある |
| Ability | やる意思はあるが、Knowledge／Skill／Tool／Experienceが足りずできない |
| Incentive／Environment | 自分の役割だと思っていない、優先されていない、時間がない、評価されない、権限がない |

Abilityは「やり方が分からない・できない」に限定して狭く取る。「自分の仕事だと思っていない」「後回しにされている」といった役割・優先順位の問題は、能力の欠如ではなくIncentive／Environmentに分類する。ここを混同すると、AbilityとIncentive／Environmentの境界で診断が止まりやすい。

### 3.3 同じ現象でも、障壁は人によって違う

同じ「動かない」という現象でも、原因は人によって異なる。例えば、ある業務でアセット化（自分の仕事を型として残すこと）に消極的な人がいたとして、それが

- アセット化の価値が分かっていない（Logic）のか
- 自分の仕事だとは思っていない（Incentive／Environment：役割の未定義）のか
- 具体的なまとめ方が分からない（Ability：Knowledge／Skill不足）のか
- 興味はあるが忙しい（Incentive／Environment：時間）のか
- 他の評価指標の方が重要だと考えている（Incentive／Environment：評価）のか

によって、次に選ぶ打ち手（Chapter 4）はまったく違う。診断を飛ばして「もっと説明する」を選ぶと、Logic以外の障壁を持つ相手には響かない。

### レビュー用メモ（本人との議論用）
- [ ] 今動かせずにいる相手について、4つの障壁のどれに当たるか、仮説を立てられるか
- [ ] その仮説は、相手に確認していない「自分の推測」のままになっていないか

## Chapter 4. Select ―― 原因に応じて打ち手を選ぶ

### 4.1 障壁と打ち手の対応

| 障壁 | 主な打ち手 |
|---|---|
| Logic | Fact、構造化した説明、Business Case、具体例 |
| Emotion | 傾聴、共感、懸念の可視化、小さな成功体験 |
| Ability | Training、Template、伴走、最初の1回を一緒にやる |
| Incentive／Environment | Enabling Sponsorの関与、役割の明確化、評価指標への組み込み、時間の確保 |

打ち手は、診断した障壁に対応するものを選ぶ。Emotionが障壁の相手にFactを重ねても響かず、Abilityが障壁の相手に危機感を煽っても行動にはつながらない。

Incentive／Environmentの打ち手にある「Sponsorの関与」は、役割・時間・評価基準を整えるためにSponsorの力を借りる**Enabling Sponsor**であり、早期から普通に使ってよい。これは、Key Blockerを頭越しに動かす**Escalation to Sponsor**（Chapter 7.4、8.5）とは別物である。Enabling SponsorとEscalationを混同すると、「Sponsorは最後の手段」という原則（Chapter 7.4）と矛盾しているように見えるので、両者を区別しておく。

### 4.2 論理的に正しい説明 ≠ 人が動く

> 論理的に正しい説明 ≠ 人が動く

この一文を、打ち手を選ぶ前に必ず思い出す。特にコンサルタント・PMOのように論理構築を仕事にしている人ほど、原因をLogicに寄せて見立てやすい。実務ではLogic以外が主因であるケースも少なくない、という前提を持っておく。

なお、Key Blocker（Chapter 2.3）に対しては、対立構造で説得するより、`playbooks/cross-project-program-management.md`（②簡潔版）1.6にある「味方を作る構図」――既存の信頼関係を持つ人物を巻き込み、仮説段階から一緒に作る――という技術が有効な場面がある。

### レビュー用メモ（本人との議論用）
- [ ] 障壁の診断（Chapter 3）と、選んだ打ち手が対応しているか
- [ ] Logicの打ち手に偏っていないか、一度立ち止まって確認したか

## Chapter 5. Tailor ―― 共通コアと相手ごとのReason to Act

### 5.1 Messageは共通、Reason to Actは相手ごとに変える

> Messageは共通、Reason to Actは相手ごとに変える。

伝える内容の芯（Common Core）を相手ごとに変えると、一貫性が失われ、後で「言っていることが違う」という不信を招く。変えるべきは芯ではなく、その芯が「なぜあなたにとって重要か」という理由付けである。

### 5.2 Common Coreを作る

Common Coreには、次の3点を置く。

- なぜ今、これをやるのか
- 組織にとってどんな価値があるか
- 何をすればよいか

### 5.3 相手ごとのReason to Actを作る

Reason to Actは、相手の役割に応じて変える。例えばアセット化であれば：

| 相手 | Reason to Act |
|---|---|
| Executive | 再利用による生産性・品質・競争力の向上 |
| Manager | チームのデリバリー効率、育成のしやすさ、再利用のしやすさ |
| Practitioner | 自分の次の仕事が楽になる、評価される、作り方が簡単になる |

Common Coreは変えず、Reason to Actだけを相手の立場に翻訳する。

### 5.4 共通7割・固有3割という目安

目安として、Common Core 7割・Reason to Act 3割程度の配分で設計する。Reason to Actの比重を上げすぎると、相手ごとにバラバラな話をしているように見え、Common Coreの一貫性が薄れる。

### レビュー用メモ（本人との議論用）
- [ ] Common Coreの3点を、相手を問わず同じ言葉で言えるか
- [ ] 今の相手向けのReason to Actを、その人の役割の言葉で言い直せるか

## Chapter 6. Observe ―― 行動が変わったかを見る

### 6.1 「説明したか」ではなく「行動が変わったか」

Stakeholderへの働きかけがうまくいっているかどうかを、次のような基準で判断していないか、まず確認する。

- メールを送った
- 説明会を開いた
- 「賛成です」と言ってもらえた

これらはすべてこちら側の**行動**であり、相手の行動ではない。見るべきは、相手が実際に期待する行動を取ったかどうかである。

### 6.2 Observable Behaviorで定義する

行動が変わったかどうかは、Observable Behavior（観察可能な行動）で定義する。③のUnawareness→Awareness→Buy-in→Ownership（③Chapter 7.4）に対応させると、次のように書ける。

| 段階 | Observable Behaviorの例 |
|---|---|
| Unawareness | まだ話題にしていない |
| Awareness | 会議で自分から話題にするようになった |
| Buy-in | 自分の案件で試した |
| Ownership | 他の人にも使わせ始めた |

「賛成と言ってくれた」はBuy-in未満であることが多い。実際に自分の案件で試すところまで見て、初めてBuy-inとみなす。

### 6.3 動かなかったときは、Diagnose・Select・Tailor・Channelに戻る

Observeの結果、行動が変わっていなければ、次にやることは「もっと押す」ではない。Chapter 1.2の原則に戻り、次を順に見直す。

1. Diagnose（Chapter 3）：障壁の診断自体が間違っていなかったか
2. Select（Chapter 4）：診断は合っていたが、打ち手が弱かったのではないか
3. Tailor（Chapter 5）：Reason to Actが、その相手にとって本当に重要な理由になっていたか
4. Channel（Chapter 8）：打ち手とメッセージは合っていたが、届け方（1対1／会議／Workshop／Sponsor経由）が合っていなかったのではないか

この4つを見直さずに「あの人は動かない人だ」という結論に至るのは、たいてい早すぎる。見直した結果、動きそう度の見立て自体が変わることもある。その場合はSegment（Chapter 2）も更新する。

### レビュー用メモ（本人との議論用）
- [ ] 今、相手の「行動」で語れているか、それとも自分の「働きかけ」で語ってしまっているか
- [ ] 動かなかったとき、Diagnose・Select・Tailor・Channelのどこを見直すべきか、順番に検討したか

## Chapter 7. Champion／Key Blockerへの対応

### 7.1 Championに「変える」のではなく「なってもらう」

Chapter 2で見たChampion候補は、単に説得が要らない相手ではない。放置すると、その人は「賛成している一人」で終わる。Championとは、他のStakeholderを動かす側に回ってもらった状態を指す。「説得が終わった相手」と「Championになった相手」は別の状態である。

Champion候補（動きそう度高・影響力高）の中でも、実際に投資する相手は、次の2点で絞り込む。

- **Credibility**：このテーマについて語る正当性があるか。周囲から信頼されているか
- **Advocacy Willingness**：自分の評判を少し賭けてでも、語る意思があるか

影響力が高くても、テーマへの信頼性が低い、あるいは自分から語る意思がない相手は、Championとしては弱い。

### 7.2 Champion化のステップ

1. **早期に情報を共有する**：意思決定の前段階から声をかけ、「知っている側」に置く
2. **自分の言葉で語ってもらうよう明確に頼む**：「賛成してください」ではなく「あなたの言葉で、周りに話してもらえますか」と具体的に依頼する
3. **実際に語る場を作る**：会議で発言してもらう、資料に事例として名前を出す（本人の同意を得た上で）、後続の相手への説明に同席してもらう
4. **貢献を可視化し、感謝を伝える**：Championとして動いてくれたことを、本人にも周囲にも分かる形で示す

Championは自然発生しない。放っておくと単なるSupporterのまま終わる。

### 7.3 Key Blocker／Key Influencerの見極め

声が大きい人と、影響力が高い人は別である。会議でよく発言する、不満を表明する、という**目立ちやすさ**と、その人が動いたときに周囲にどれだけ波及するかという**影響力**を混同しない。声の大きさだけでKey Blocker認定すると、本当に重要な、静かだが影響力の高い相手を見落とす。

### 7.4 Key Blockerへの対応の順序

1. **Diagnoseを飛ばさない**：動かない相手ほど「押し切りたく」なるが、まずChapter 3の4障壁のどれに当たるか見立てる
2. **1対1から入る**：会議など人前での説得は避ける。人前で意見を変えることは本人にとって「負け」に見えやすく、Emotionの障壁をかえって強める
3. **味方を作る構図を使う**：対立構造ではなく、Key Blockerが信頼している人物を巻き込み、仮説段階から一緒に作る（Chapter 4.2、`playbooks/cross-project-program-management.md` 1.6）
4. **Escalation to Sponsorは最後の手段とする**：Key Blocker個人を頭越しに動かすためのSponsor権限行使は、診断・打ち手・チャネルを一通り試した上でなお動かない場合に限る（Chapter 8.5）。役割・時間・評価基準を整えるEnabling Sponsor（Chapter 4.1）は、これとは別物であり、早期から使ってよい

### 7.5 やってはいけないこと

- 会議など人前でKey Blockerを名指しし、意見を変えさせようとする
- 診断せずに、いきなりSponsor経由で頭越しに進める
- 一度Key Blockerと判定した相手を、状況が変わった後も固定的に扱い続ける。診断の前提（Diagnose）が変われば、Segmentも見直す

### レビュー用メモ（本人との議論用）
- [ ] 今Championにしたい相手に、「賛成してもらう」ではなく「語ってもらう」依頼を具体的にしたか
- [ ] Key Blockerだと思っている相手が、本当に影響力が高いのか、単に目立っているだけなのかを確認したか
- [ ] Key Blockerへの対応を、1対1から始めているか

## Chapter 8. チャネルの使い分け

### 8.1 チャネルは打ち手の「乗せ物」である

Chapter 4で選んだ打ち手は、どう届けるかによって効き方が変わる。正しい打ち手を、誤ったチャネルで届けると、届く前に効果が失われる。チャネルは、打ち手を運ぶ乗り物である。

### 8.2 1対1

| 向いている場面 | 理由 |
|---|---|
| Emotionが障壁の相手 | 人前では本音の不安・不信を話しにくい |
| Key Blockerとの初期接点 | 人前での説得は「負け」に見え、かえって態度を硬化させる |
| Abilityが障壁で、本人が引け目を感じている場合 | 「分からない」と人前で言いにくい |

1対1は個別最適だが、スケールしない。全員に使うと時間が足りなくなる。Chapter 2のSegmentで優先度をつけた相手に絞って使う。

### 8.3 会議（定例・少人数）

| 向いている場面 | 理由 |
|---|---|
| Logicが障壁の相手 | 構造化された説明・質疑応答に向く |
| 決定過程を可視化したい場合 | 「誰がどう決めたか」を関係者に見せられる |

会議は集団力学が働くため、Emotionの障壁を抱えた相手が本音を出しにくい。会議で「賛成です」と言ったことを、Buy-inの確定と誤解しない（③Chapter 7.4、本Playbook6.2）。

### 8.4 Workshop

| 向いている場面 | 理由 |
|---|---|
| Abilityが障壁の相手・グループ | 実際に手を動かす体験を、その場で作れる |
| Common Coreの理解を一斉に揃えたい場合 | 同じ場で同じ体験を共有できる |

Workshopは準備・進行の負荷が高い。ファシリテーションの質が低いと、かえって「時間を取られた」という不満（Emotion障壁の新規発生）を生む。

### 8.5 Sponsor経由

Sponsor経由には性質の異なる2種類がある。

| 種類 | 向いている場面 | 使うタイミング |
|---|---|---|
| Enabling Sponsor | Incentive／Environmentが障壁の相手。役割の明確化・評価指標への組み込み・時間確保は、現場の実務担当者では決められない | 早期から普通に使ってよい |
| Escalation to Sponsor | Key Blockerへの対応が他のチャネルで尽きた場合。組織的な権限で個人を動かす最終手段 | 診断・打ち手・チャネルを一通り試した後 |

この2つを混同しない。Enabling Sponsorを早期から使うことと、Escalation to Sponsorを最後の手段として温存することは矛盾しない。混同してEscalationを早く・多く使いすぎると、実務担当者自身の信頼が積み上がらないまま、常に上位者の力に頼る状態になる。7.4で述べたKey Blocker対応の「最後の手段」は、Escalationの方を指す。

### 8.6 組み合わせる

実務では、1つのチャネルだけで完結することは少ない。典型的な順序の例：

```text
1対1でDiagnose        Workshopで              Sponsor経由で
（本音の障壁を          Abilityを               Incentive／Environment
 個別に確認）    →      底上げ           →       の障壁を最終調整
```

チャネルは一度選んで終わりではなく、Observe（Chapter 6）の結果に応じて、次にどのチャネルを使うかを都度選び直す。

### レビュー用メモ（本人との議論用）

- [ ] Sponsor経由を、最初の手段として使おうとしていないか
- [ ] 会議で得た「賛成」を、Buy-inの確定と誤解していないか

## Chapter 9. 実践演習

### ケース：③の演習ケースの続き

③（Operations Transition Playbook）Chapter 8の演習ケースの続きとして設定する。周辺システム（既存ベンダーX社が運用していたもの）のTransitionは完了し、KT Sign-off・Transition Closeも済んでいる。

しかし、この周辺システムを日常的に使う業務部門側のある課長は、正規のチケット窓口をほとんど使わず、今も個人的に旧ベンダーX社の元担当者へ直接連絡を取り続けている（③Chapter 7.7の「シャドーサポートの継続」）。あなたはTransition Managerとして、この課長を動かす。

### 演習ステップ

1. この課長を、Segmentする（Chapter 2）
2. 動かない理由を、複数の仮説でDiagnoseする（Chapter 3）
3. 仮説ごとに異なる打ち手をSelectする（Chapter 4）
4. この課長向けのReason to Actを、Common Coreを崩さずにTailorする（Chapter 5）
5. 使うチャネルを選ぶ（Chapter 8）
6. Observable Behaviorを定義する（Chapter 6）

### 進め方

まず一人で、次の問いに順番に自分の言葉で答える。答え終えたら、指導者と一緒に照らし合わせる。

1. この課長の「動きそう度」「影響力」を、今分かっている情報だけで仮に見立てる
2. 動かない理由として考えられる仮説を、Logic／Emotion／Ability／Incentive-Environmentの4つそれぞれについて、1つずつ考える
3. 最も可能性が高いと思う仮説を1つ選び、その根拠を書く
4. 選んだ仮説に対応する打ち手を、Chapter 4の対応表から選ぶ
5. その打ち手を届けるチャネルを、1対1／会議／Workshop／Sponsor経由から選び、理由を書く
6. 3か月後、「動いた」と判断するためのObservable Behaviorを1つ定義する

### 演習の参考解答（例）

自分の解答と照らし合わせるための記入例。

**Segment**：動きそう度は低め（旧担当者への信頼が厚く、新チャネルを試した形跡がない）、影響力は中程度（部門内の一部業務に限られるが、ここで定着が崩れると同様の課がほかにも現れうる）。Key Blocker寄りとして扱う。

**Diagnose（仮説）**：

| 障壁 | 仮説 |
|---|---|
| Logic | 新しい窓口を使うメリットを理解していない可能性 |
| Emotion | 長年の担当者との関係が切れることへの寂しさ、新チームへの不信 |
| Ability | 新しいチケットシステムの使い方が分からない可能性 |
| Incentive／Environment | 旧担当者に直接連絡する方が速いという体験が続いており、切り替える動機がない |

**最も可能性が高い仮説**：Emotion（長年の信頼関係）とIncentive／Environment（今のやり方の方が速いという体験）の複合。Logicの問題ではなさそうである（新チャネルの存在自体は知っていると想定されるため）。

**Select**：Emotionには傾聴と小さな成功体験、Incentive／Environmentには「新チャネルの方が実は速い」という体験を実際に1回作ること（例えば、優先的に早く対応する）。

**Tailor**：Common Core（なぜ今新運用に切り替えるのか／組織にとっての価値／何をすればよいか）は変えず、この課長向けのReason to Actは「新チャネルを使えば、あなたの部署の対応がむしろ今より速くなる」に置く。

**チャネル**：1対1を選ぶ。人前で「今のやり方は良くない」と指摘すると、Emotionの障壁をかえって強める。

**Observable Behavior**：「次回の障害・問い合わせを、旧担当者への個人連絡ではなく、正規チケットで起票した」を、動いたことの定義とする。

### レビュー用メモ（本人との議論用）
- [ ] 自分の仮説（Diagnose）を、確認もせずに「正しい」と決めつけていないか
- [ ] 選んだチャネルは、この相手のEmotion障壁を悪化させないか
- [ ] Observable Behaviorは、「賛成してくれた」ではなく、実際の行動で定義できているか
