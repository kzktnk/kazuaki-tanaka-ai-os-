# Program Governance Cadence Playbook

**Version:** v0.1  
**Status:** Active  
**Owner:** Kazuaki Tanaka  
**Purpose:** 複数プロジェクトを持つプログラムで、**誰が何のために集まり、層の間で何を上げ、検査と進捗を混ぜないか**を設計する  
**Use when:** Phase 1 でプログラム事務局（PMO / PgMO）を立ち上げたあと、定例・横断調整・プログラム会議・ステコミ・検査が同じ「報告会」に見え始めている  
**Do not use as-is for:** 事務局そのものの立ち上げ順序（`playbooks/pmo-function-standup.md`）、PJ 間の依存・整合・Hand-off 管理（`playbooks/cross-project-program-management.md`）、共同利用の複数ロット開始判定（`playbooks/public-multi-lot-construction-pmo.md`）、官側調達設計（`frameworks/public-it-procurement-support.md`）

Pairs with `frameworks/transformation-pmo.md`（PMO とは何か）and `standards/pmo-operating-guide.md`（機能と PPM）。本 Playbook は **会議階層と文書クラス**。ステコミ資料の型は `standards/deliverable-archetypes.md` Archetype C。文書番号・台帳は `standards/document-management-standard.md`。

## Trigger

キックオフ後、週次は回っている。横断の論点は定例の最後に口頭で出る。初回の経営会議が作業報告を兼ねる。検査がチェックシートの記入催促になっている。

## Objective

各層が **決めること / 調整すること / 確認すること / 保証すること** を別の場にする。Phase 1 では、方針とロードマップと会議パックが **管理対象** になり、現行の議事録や検査結果は原本のまま残る。

## Prerequisites

- プログラムに2つ以上のプロジェクト（またはワークストリーム）がある  
- 事務局が進捗の書記ではなく、統合とエスカレーションのオーナーである  
- スポンサーとプロジェクト長の切れ目が、少なくとも名前の上ではある  

## Required inputs

- プロジェクト一覧と依存の粗い図（系統・現場名は原本）  
- 既存の会議名（定例／調整／全体／ステコミ／検査）  
- 管理文書の置き場（仕様、計画、方針、会議、作業）  
機密の社名、円、議事本文、人名、組織図、KPI 実績、現行入札・プログラム事実は原本のみ。

## Escalation conditions

- 他プロジェクトが動かないと解けない論点が、週次定例の「共有」で止まっている → 調整会議を別建てする  
- プログラムの順序・共有資源・対外約束が、プロジェクト長同士の調整だけでは閉じない → プログラム全体会議へ  
- 範囲・優先・資源・停止が、事務局とプロジェクト長の権限を超える → ステコミへ  
- 進捗は緑だが、WBS・課題・リスク・文書台帳・レビュー記録が実在しない → 検査所見としてプログラム層へ（週次の「問題なし」で消さない）  
- 初回ステコミが作業WBSの読み合わせになっている → 経営層向け Archetype C に切り、全体会議と分離する時期を決める  

## Sequence

1. **会議階層に名前を付ける**  
   下から、プロジェクト定例 → プロジェクト間調整 → プログラム全体会議 → ステコミ。検査は並列の保証層であり、定例の別名にしない。

2. **層ごとにジョブを一文で固定する**  
   定例は直近の進捗と例外。調整は特定の依存を解く。全体会議はプログラムとしての物語と横断決定。ステコミは権限のある決定。検査は管理の実在を証拠で見る。

3. **上げる条件を先に書く**  
   「困ったら上へ」ではなく、依存 / プログラム影響 / 決裁権限、のどれかを満たしたときだけ上げる。上げた論点は、下の層の進捗スライドに再掲して終わらせない。

4. **Phase 1 の管理文書セットを閉じる**  
   入力は委託仕様。事務局の作業要領は計画。プログラムの回し方は管理方針。到達状態は立ち上げロードマップ。定例の型は会議パック（と議事の型）。受領した現行計画・提案本文・要員の内部再配分は、方針の引用元であって管理対象そのものにしない。

5. **週次をパイロットする**  
   立ち上げ月は短い週次でパックを一度通す。決定がない週は書面報告でよい。書面報告は検査の代替ではない。

6. **ステコミと全体会議を、必要になるまで兼ねてよい**  
   経営が聞く論点がまだ1つなら兼ねる。作業進捗を経営に読ませたくなった時点で分ける。分けたあとも、同じデッキを使い回さない。

7. **調整会議はイベント駆動にする**  
   週次の恒常アジェンダにしない。対象プロジェクト、解きたい依存、事前すり合わせ、を部屋の前に固定する。

8. **検査を進捗の後追い週にしない**  
   台帳類が存在してから波を打つ。プログラム事務局がチェックリストを持ち、プロジェクトごとに証拠パック（WBS、進捗報告、課題／リスク／ToDo、管理文書一覧、レビュー記録）を見る。検査結果の説明資料と、記入中のシートは別成果物。

## Decision points

| 問 | 決めること |
|----|------------|
| この論点は誰の場か | 定例 / 調整 / 全体 / ステコミ / 検査のどれか一つ。兼ねるなら期限付き |
| 今週は部屋が要るか | 決定または新規例外がなければ書面 |
| 検査を始めてよいか | 様式だけでなく、少なくとも一つのプロジェクトで台帳が動いている |
| ステコミ資料は何か | 依頼する決定。進捗の全集約ではない |

## Quality checks

- 各層の目的が、参加者ではなく **成果（決定／解消／保証）** で書いてある  
- エスカレーション条件が、感情や「重要そう」ではなく権限と依存で書いてある  
- 検査の対象が、スライドの印象ではなく管理成果物である  
- Phase 1 の納品が、受領資料の再掲ではなく方針・ロードマップ・会議型である  
- 議事録本文と検査の実記入が、リポジトリや横断テンプレに混入していない  

## Outputs

- 会議階層図（層、周期の目安、上げる条件）  
- Phase 1 管理文書セットの目次（仕様／作業要領／方針／ロードマップ／会議パック。中身は原本）  
- 検査の証拠パック定義（実データは原本）  
- ステコミと全体会議を兼ねる／分ける判断の一文  

## Done when

- 誰かが「全部定例でよい」と言えなくなっている  
- 検査が週次の延長としてスケジュールされていない  
- Phase 1 の管理対象と、現行の議事・検査結果・提案本文が、置き場として分かれている  

## Limitations

現行プログラムの議事本文、検査結果、管理文書の中身、ロット構成、現場名、KPI 実績、入札事実は対象外。文書の版管理手続の詳細は `document-management-standard.md`。PMO を人として立ち上げる順序は `pmo-function-standup.md`。
