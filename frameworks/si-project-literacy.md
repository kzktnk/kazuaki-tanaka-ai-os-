# SI Project Literacy

**Version:** v0.6
**Status:** Draft
**Owner:** Kazuaki Tanaka
**Purpose:** SI未経験のPgMO担当者が、現場から上がってくる報告を聞いて後工程への典型的な波及を推測し、確認すべき質問を自分で組み立てられるようになるための前提知識を提供する
**Use when:** SI未経験者をPgMOに配置する（している）。`playbooks/cross-project-program-management.md`（以下②）を渡しても、Dependency Registerや Scope Boundary Matrixに何を書けばよいかの判断材料がない
**Do not use as-is for:** 個別PJのPMとしてSIを回す実務そのもの、②が扱うPJ間統合管理の型
**Source revision:** なし（新規作成）

Pairs with `frameworks/consultant-capability-skill-model.md`（Capability II のPrerequisite Knowledgeとして接続）。本Frameworkは②を実行するための前提知識を扱うものであり、②の代わりにはならない。

## SI未経験のPgMO担当者が「中で何が起きているか」を理解するための最低限の解像度

## このFrameworkの位置づけ

②は次のように明記している。

> PgMOが「中を見ない」のではなく、「中の管理責任を持たない」

PJ間への影響を判断するためには、個別PJの進捗・課題・品質を最低限モニタリングする必要がある。しかし、それを実際にやるには、SIプロジェクトで今何が起きていて、放置すると何に波及するかを読み取れる解像度がいる。この解像度はSI経験者であれば案件を通じて自然に身についているため、②はこれを暗黙の前提として書かれている。

SI未経験者がPgMOに配置された場合、②の型（Dependency Register・Scope Boundary Matrix等）を渡されても、「何をCriticalと判断すればよいか」の判断材料そのものがない。本Frameworkが埋めるのはこの部分であり、PMとしてSIを回せるようになることが目的ではない。

```text
SI Project Literacy（本Framework）
「PJの中で何が起きているか」を理解する
                        │
                        ▼
② Cross-Project Program Management Playbook
「それがPJ間でどう波及するか」を判断する
                        │
                        ▼
PgMO実務
Detect → Analyze → Recommend → Act / Escalate
```

①②③＋横串の系列（`playbooks/strategy-scn.md` → ② → `playbooks/operations-transition-playbook.md`、横串 `playbooks/stakeholder-activation-playbook.md`）に新しい段階を追加するものではない。横串と同じく、系列に対して直交する前提知識層として位置づける。

## 使い方の原則：Fact → What it means → What happens next → What PgMO should ask

各Chapterは工程の教科書的な説明を本体にしない。SI未経験者に必要なのは、**「この事実を聞いたら、次に何を疑い、何を聞くか」**である。したがって全Chapter共通で次の4段構成を使う。

| 段階 | 内容 |
|---|---|
| Fact | 現場から報告として上がってくる一文 |
| What it means | その事実が意味している状態 |
| What happens next | 放置した場合に後工程へ波及すること |
| What PgMO should ask | 確認すべき質問 |

「IF仕様の確定が遅れている」という一文だけでは、SI未経験者にはそれが何を意味するか分からない。SI経験者の頭の中では、次の連鎖が自動的に走る。

```text
IF仕様確定が遅れている
        ↓
双方の基本設計は何を前提に進めている？
        ↓
もう実装に入っていないか？
        ↓
結合テストで不整合が出るのでは？
        ↓
後から直すと両PJに手戻り
        ↓
今週中に両Tech Leadを集めて仕様を突き合わせよう
```

この連鎖を再現できるようにすることが、本Frameworkの唯一のゴールである。工程知識はそのための手段にすぎない。

## Chapter 1：SIプロジェクトの全体像

> これらの質問は、間への波及があるかを見るためであり、個別PJの品質管理を引き取るためではない。

### 1.1 ライフサイクルの流れ

SIプロジェクトは、おおむね次の順序で進む。

```text
要件定義 → 基本設計 → 詳細設計 → 開発 → テスト（単体→結合→総合→UAT） → 移行 → 稼働
```

それぞれの工程は独立した作業ではなく、**前工程の成果物を前提にして次工程が進む**という依存関係を持つ。基本的には前工程の成果物を次工程が前提として使う。ただし実案件では工程の並行・反復・手戻りも起きる。本Frameworkではまず依存の骨格を理解するため、この順序で捉える。

要件定義で決まらなかったことは基本設計で仮置きされ、基本設計で決まらなかったことは詳細設計・開発で仮置きされる。この「仮置きの連鎖」は、下流に進むほど、未確定事項が手戻りや不具合として顕在化しやすくなる。各工程の目的と成果物の詳細はChapter 2で扱う。本Chapterでは、まず「どこで何が決まり、それが次にどう渡るか」という骨格だけを押さえる。

本Framework中の工程名（要件定義・基本設計等）は典型的な呼び方であり、実際の案件・開発方式（Agile／ハイブリッド等）では呼称も区切り方も異なる。重要なのは工程名を覚えることではなく、「何かが決まり、それが次に引き渡され、決まっていない部分は仮置きで進む」という受け渡しと仮置きの連鎖そのものを見抜くことである。

### 1.2 ②のケースで確認する

②のChapter 9演習ケース（4社・5プロジェクトによる基幹システム刷新）を、ライフサイクルの視点で並べ直すと次のようになる。

| PJ | 担当工程 | 前提にしているもの |
|---|---|---|
| PJ-A（業務要件定義・BPR） | 要件定義 | ― |
| PJ-B（基幹システム本体設計・開発） | 基本設計〜開発 | PJ-Aの要件定義書 |
| PJ-C（外部連携・周辺システムI/F） | 基本設計〜開発（IF） | PJ-BのAPI／IF仕様 |
| PJ-D（データ移行） | 設計〜リハーサル | PJ-Bのデータ構造・移行用データ環境 |
| PJ-E（テスト統括・移行リハーサル） | テスト〜移行 | PJ-B・C・Dのテストシナリオ・環境 |

自分が担当するプログラムでも、まずこの表を実際のPJ名で埋め、「どのPJが何をどの工程で担当していて、どのPJの成果物を前提にしているか」を描くのが本Chapterのゴールである。

### 1.3 Fact → What it means → What happens next → What PgMO should ask

**例1：要件定義は完了しているが、非機能要件が定義書に記載されていない**

| 段階 | 内容 |
|---|---|
| Fact | 要件定義が完了したとされているが、基本設計に必要な非機能要件（性能目標・可用性目標等）が定義書に記載されていない |
| What it means | 「完了」が機能要件のみを指しており、非機能要件の合意が先送りされている |
| What happens next | 基本設計・アーキテクチャ選定が仮の前提で進み、後で非機能要件が固まった際に設計のやり直しが発生する。総合テストでの性能検証計画にも影響する |
| What PgMO should ask | 非機能要件はいつ・誰が確定させるか／現在の設計はどのような前提（暫定値）で進んでいるか／確定が遅れた場合、設計にどこまで影響するか |

**例2：基本設計のレビュー未完了のまま、一部が詳細設計・開発に着手している**

| 段階 | 内容 |
|---|---|
| Fact | 基本設計のレビューが完了していないのに、一部チームが詳細設計・開発に着手している |
| What it means | スケジュール遵守を優先し、前工程の成果物が未確定のまま次工程を並行させている（工程の圧縮） |
| What happens next | 基本設計が後から変更されると、先行して進めた詳細設計・開発が手戻りになる。手戻りの範囲が広いほど、後続のテスト・移行スケジュールへの影響も大きい |
| What PgMO should ask | 未確定のまま先行しているのはどの部分か／基本設計側で今後変わりうる論点は何か／その論点が変わった場合、先行分のどこまでが手戻りになるか |

### 1.4 早見表

| 兆候 | 疑うべきこと |
|---|---|
| 前工程が「完了」しているのに、次工程の前提資料に「別途調整」「暫定」等の言葉がある | 実質的に未確定の前提の上で次工程が進んでいる |
| 前工程のレビュー未完了のまま次工程が並行して着手されている | 工程が圧縮されており、手戻りリスクを内包している |

## Chapter 2：各工程の目的と主要成果物

> これらの質問は、間への波及があるかを見るためであり、個別PJの品質管理を引き取るためではない。

### 2.1 「完了」を主要指標だけで判断しない

各工程の「完了」報告には、主要成果物の提出と引き換えに省略されやすい確認事項がある。

| 工程 | 主要成果物 | 「完了」でよく省略される確認事項 |
|---|---|---|
| 要件定義 | 要件定義書 | 非機能要件の合意有無、業務例外ケースの網羅性 |
| 基本設計 | 基本設計書 | IFの前提条件の明記、他PJとの整合レビュー実施有無 |
| 詳細設計 | 詳細設計書 | 基本設計からの逸脱有無、エラー処理の網羅性 |
| 開発 | ソースコード、単体テスト結果 | 単体テストのカバレッジ、既知不具合の有無 |
| 結合テスト | テスト結果報告 | 実施率（消化率）と不具合の解消率は別（詳細はChapter 5.1） |
| 総合テスト | テスト結果報告 | 本番相当条件（データ量・環境）での検証有無 |
| 移行リハーサル | リハーサル報告書 | 本番相当データでの実施有無、切り戻し手順の検証有無 |
| UAT | 受入判定書 | Acceptance Criteriaとの対応、例外業務の洗い出し状況 |

「完了しました」という報告を受けたら、この表の右列を確認する。数字（消化率・完了率）が良好でも、右列の確認事項が未確認であれば、その報告をそのまま受け入れず、未確認事項がOpen Point／Riskとして明示され、Owner・期限・後工程への影響が管理されているかを確認する。100%決まってから次工程に進むことを求めているのではない。**未確定のまま進むなら、未確定であることが管理されているか**を見る（この考え方は1.3の例2「工程圧縮」とも一致する）。

### 2.2 Fact → What it means → What happens next → What PgMO should ask

**例：基本設計は完了しているが、PJ間にまたがる部分だけ「別途調整」のままになっている**

| 段階 | 内容 |
|---|---|
| Fact | 「基本設計が完了しました」と報告があったが、他PJとのインターフェースに関わる部分は「別途調整」という記載のまま残っている |
| What it means | 自PJ内で閉じる部分は完了しているが、PJ間にまたがる部分の設計判断が先送りされている |
| What happens next | 後工程（詳細設計・結合テスト）でこの「別途調整」部分の前提が食い違っていることが判明し、両PJの手戻りにつながる。成果物上は「完了」に見えるため、②のDependency Registerに載せるべき項目が見落とされやすい |
| What PgMO should ask | 「別途調整」とされている項目は具体的に何か／いつ・誰が調整するか／それが確定するまで、自PJはどのような仮定で設計を進めているか |

### 2.3 早見表

| 兆候 | 疑うべきこと |
|---|---|
| 「完了」の中に「別途調整」「暫定」等の言葉がある | 未確定事項がOpen Point／Riskとして管理されていない可能性 |
| 主要指標（消化率・完了率）だけが報告される | 指標に含まれない側面（残存不具合の重大度、確認事項の充足）が未確認 |

## Chapter 3：要件・設計

要件定義・基本設計・詳細設計は、後工程の「前提」を作る工程である。ここでの曖昧さ・未決事項は、成果物としては「完了」の体裁を取りながら、後工程で牙をむく。Chapter 1・2で見た「仮置きの連鎖」「未確定のまま進む場合の管理」を、要件・設計工程に絞って具体化する。

> これらの質問は、間への波及があるかを見るためであり、個別PJの品質管理を引き取るためではない。

### 3.1 Fact → What it means → What happens next → What PgMO should ask

**例1：要件定義は完了しているが、Open Pointの件数が減らない**

| 段階 | 内容 |
|---|---|
| Fact | 要件定義が完了したとされているが、要件定義書に記載されたOpen Point（未決事項）の件数が、基本設計工程に入ってからも減っていない |
| What it means | 「要件定義完了」の判定が、Open Pointの解消ではなく、スケジュール上の区切り（工程移行の日付）で行われている |
| What happens next | Open Pointを前提にしたまま基本設計が進み、後で要件が確定した際に設計の手戻りが発生する。Open Pointの数が多いほど、どの設計判断がどのOpen Pointに依存しているかの追跡自体が難しくなる |
| What PgMO should ask | Open Pointは何件あり、それぞれ誰がいつまでに決めるか／各Open Pointは、どの設計判断の前提になっているか／確定しない場合の代替（暫定仕様での設計継続）は決まっているか |

**例2：業務側の判断待ち事項を、システム側の仮定で設計している**

| 段階 | 内容 |
|---|---|
| Fact | 業務側の判断が必要な論点（例：承認フローの分岐条件）について、業務側からの回答を待たず、システム側が「おそらくこうだろう」という仮定で設計を進めている |
| What it means | 本来は業務側がオーナーであるべき判断を、システム側が代行してしまっている。業務側はまだ最終判断をしていないため、後から仮定と異なる判断が下される可能性が残っている |
| What happens next | 業務側の最終判断がシステム側の仮定と異なっていた場合、設計・実装済みの部分がまるごと手戻りになる。しかも「システム側が勝手に決めた」という形になり、業務側との信頼関係にも影響する |
| What PgMO should ask | この判断のオーナーは誰か／システム側の仮定は業務側に共有・確認されているか／業務側の最終判断はいつ得られる見込みか／判断が仮定と異なった場合の設計への影響は評価済みか |

**例3：要件変更が設計・テストへ反映されていない**

| 段階 | 内容 |
|---|---|
| Fact | 要件変更が承認されたが、対応する設計書・テストケースがまだ更新されていない |
| What it means | 変更管理のプロセスが「要件の変更」で止まっており、下流の成果物（設計書・テストケース）への反映が別タスクとして追跡されていない |
| What happens next | 古い設計・古いテストケースのまま開発・テストが進み、変更が反映されていないままリリースされる。あるいはテストで気づかれても、どこまで手戻りが必要かの洗い出しに時間がかかる |
| What PgMO should ask | この要件変更は、どの設計書・テストケースに影響するか一覧化されているか／影響先の更新はいつまでに完了する予定か／更新が完了するまでの間、開発・テストは何を前提に進めているか |

### 3.2 早見表

| 兆候 | 疑うべきこと |
|---|---|
| 要件定義完了後もOpen Pointの件数が減らない | 「完了」がスケジュール上の区切りにすぎない |
| 業務判断待ちの論点をシステム側の仮定で埋めている | 判断のオーナーシップが業務側からシステム側に移ってしまっている |
| 要件変更が設計・テストに反映されていない | 変更管理が要件の変更だけで止まり、下流への波及が追跡されていない |

### 3.3 ②との接続

- Dependency Management／Chapter 6（Consistency）：Open Pointや要件変更の影響先は、②のDependency RegisterやConsistency Matrixに載せるべき項目そのものである
- Chapter 2.1（本Framework）：「完了」を主要指標だけで判断しないという原則の、要件・設計工程における具体形

## Chapter 4：開発・品質

開発工程の進捗報告は「量」の指標（完成本数、消化率等）に偏りやすい。しかし「量」が計画通りでも「質」が伴っていなければ、後工程（テスト以降）で問題が噴出する。

> これらの質問は、間への波及があるかを見るためであり、個別PJの品質管理を引き取るためではない。

### 4.1 Fact → What it means → What happens next → What PgMO should ask

**例1：進捗率は予定どおりだが、レビューが滞留している**

| 段階 | 内容 |
|---|---|
| Fact | 開発の進捗率（コーディング完了率）は計画どおりだが、コードレビューの完了件数が積み上がらず滞留している |
| What it means | 「進捗」が実装の完了だけを指しており、品質を担保するレビュー工程がボトルネックになっている |
| What happens next | レビュー未完了のコードがそのまま結合テストに入り、レビューで本来検出できたはずの不具合がテスト工程に持ち越される。滞留が続くほど、後からまとめてレビューする際の負荷も大きくなる |
| What PgMO should ask | レビュー待ちの件数と滞留期間はどれくらいか／レビュアーのキャパシティは足りているか／レビュー未完了のままテストに入る場合、どこまでのリスクを許容しているか |

**例2：完成量は計画どおり増えているが、後工程で発見される不具合の割合が増えている**

| 段階 | 内容 |
|---|---|
| Fact | 完成量（消化率）は計画どおり増えているが、単体テストではなく後工程（結合テスト以降）で発見される不具合の割合が増えている |
| What it means | 前工程で検出・除去すべき不具合が後工程へ流出しており、品質の作り込み、または前工程のレビュー／単体テストが十分に機能していない可能性がある |
| What happens next | 流出が続くほど、発見が遅い工程ほど1件あたりの修正コスト（原因調査・影響範囲確認・再テスト）が大きくなる。結合テスト以降のスケジュールが不具合対応に圧迫される |
| What PgMO should ask | 不具合はどの工程で作り込まれ、どの工程で発見されているか（作り込みと発見の工程差）／前工程のレビュー・単体テストは計画どおり実施されているか／流出が特定の機能・担当者に偏っていないか |

**例3：特定メンバーだけがタスクを大量に抱えている**

| 段階 | 内容 |
|---|---|
| Fact | 開発チームの中で、特定の1〜2名だけがタスク（担当機能・レビュー待ち・問い合わせ対応）を大量に抱えている |
| What it means | 属人化が進んでおり、そのメンバーが単一障害点（Single Point of Failure）になっている |
| What happens next | そのメンバーが離脱・体調不良・他タスクへの割り込み等で稼働できなくなった場合、担当していた範囲全体が一斉に遅延する。本人も抱え込みすぎて質が落ちている可能性がある |
| What PgMO should ask | そのメンバーが1〜2週間稼働できなくなった場合、代替できる人はいるか／タスクの偏りは是正する計画があるか／本人は残業・持ち帰り作業で帳尻を合わせていないか |

### 4.2 早見表

| 兆候 | 疑うべきこと |
|---|---|
| 進捗率は順調だがレビューが滞留 | 「進捗」が実装完了のみを指し、品質担保工程がボトルネック化 |
| 完成量は順調だが後工程での不具合発見割合が増えている | 前工程のレビュー・単体テストが機能しておらず、不具合が後工程へ流出している |
| 特定メンバーへのタスク集中 | 属人化による単一障害点化 |

### 4.3 ②との接続

- Chapter 7.6（先読み）：これらの兆候はいずれも「消化率」という表面指標だけでは見えない予兆であり、②の先読みの型がそのまま適用できる
- Risk／Issue Management：属人化やレビュー滞留は、顕在化前に気づけばRisk、既に遅延等が発生していればIssueとして扱う典型例

## Chapter 5（パイロット）：テスト（単体→結合→総合→UAT）で何を潰しているのか

> これらの質問は、間への波及があるかを見るためであり、個別PJの品質管理を引き取るためではない。

### 5.1 テストの主目的は「検証・可視化」であり、実施しただけで品質は上がらない

テストの主目的は、品質を検証し、可視化することである。テストを実施しただけでは品質は上がらない。

```text
Design／Build で品質を作り込む
        ↓
Test で不足（不具合）を検出する
        ↓
修正・再テストで品質を収束させる
```

テストの各段階は、それぞれ別の種類の不具合を検出するために存在する。段階の名前より、**どの段階がどの種類の不具合を検出するために存在するか**を押さえる方が重要である。

| 段階 | 検出しているもの |
|---|---|
| 単体テスト | プログラム内部のロジックの誤り |
| 結合テスト | システム・モジュール間のインターフェース不整合 |
| 総合テスト | 業務シナリオ全体を通した機能不備、性能・可用性等の非機能要件の未達 |
| UAT（受入テスト） | Business Requirement／Acceptance Criteriaを満たしているかを業務側が確認する場。あわせて、実運用に即した使い勝手や現場でしか気づけない業務ルールの見落としもここで検出される |

※呼称・切り分けは案件や開発方法論によって異なる。本表は典型例。

「結合テストの消化率が90%です」という報告は、原則として**予定していたテストケースの90%を実施した**という意味にすぎない。不具合がどれだけ残っているか、重大な不具合が収束しているか、重要なIFが十分に検証されたか（Open Pointが本当に潰れているか）は、消化率とは別に確認する必要がある。

### 5.2 Fact → What it means → What happens next → What PgMO should ask

**例1：結合テスト開始直前でもIF仕様が固まっていない**

| 段階 | 内容 |
|---|---|
| Fact | 結合テスト開始2週間前なのに、IF仕様にOpen Pointが複数残っている |
| What it means | 両システムが同じ前提でインターフェースを実装できていない可能性が高い |
| What happens next | テスト開始そのものが遅延する。または開始できても大量の不整合が検出され、後工程（総合テスト・移行）に手戻りが波及する |
| What PgMO should ask | 未確定のIFはいくつあるか／双方は現時点で何を仮置き（前提）として実装しているか／いつ・誰が確定させるか／確定が遅れた場合のテスト計画への影響は評価済みか |

**例2：消化率は計画通りだが、未修正の不具合件数が減らない**

| 段階 | 内容 |
|---|---|
| Fact | 結合テストの消化率は計画通りだが、検出した不具合のうち「未修正」件数が横ばいで減らない |
| What it means | 検出ペースに対して修正キャパシティが不足している。または根本原因が共通しており同種の不具合が繰り返し発生している |
| What happens next | 消化率という表面的な指標は健全に見えても、未解消の不具合が総合テスト以降に持ち越され、リリース判定の直前に大量の残存不具合で判断が詰む |
| What PgMO should ask | 未修正の不具合は原因別にどう分布しているか／同一原因の不具合が繰り返し出ていないか／修正のボトルネックはどこにあるか（人員／設計判断待ち／環境） |

**例3：総合テストの性能検証が縮小データで実施されている**

| 段階 | 内容 |
|---|---|
| Fact | 総合テストのスケジュールは維持されているが、性能テストが本番相当データ量ではなく縮小データセットで実施されている |
| What it means | 性能問題が本番データ量になって初めて顕在化するリスクが、検証されないまま残っている |
| What happens next | 稼働後に性能劣化・タイムアウト等が発生し、直前の対策では間に合わず、稼働延期または稼働後の緊急対応が必要になる |
| What PgMO should ask | 本番相当データでの性能検証はいつ実施予定か／縮小データの結果から本番相当の性能をどう見積もっているか／間に合わない場合の代替検証・リスク受容の判断は誰がするか |

**例4：UATで要件定義時に出てこなかった例外業務の指摘が多い**

| 段階 | 内容 |
|---|---|
| Fact | UATで、要件定義時には出てこなかった「現場の例外業務」に関する指摘が多数上がっている |
| What it means | 要件定義がシステム化対象の標準ケースに寄っていて、実運用で発生する例外パターンの洗い出しが不足していた |
| What happens next | 稼働直前にスコープ外の追加開発判断を迫られる。または例外業務を運用でカバーする代替手段を稼働までに合意する必要が生じ、移行スケジュールを圧迫する |
| What PgMO should ask | 指摘の件数と重大度の内訳はどうなっているか／どこまでシステム化し、どこから運用回避にするかの切り分け方針は誰がいつまでに決めるか／この判断が他PJのスコープや移行計画に影響しないか |

### 5.3 早見表（Chapter 9への布石）

| 兆候 | 疑うべきこと |
|---|---|
| 結合テスト直前でもIFにOpen Pointが残る | 両システムの実装前提の不一致 |
| 消化率は健全だが未修正件数が減らない | 修正キャパシティ不足／根本原因の共通化 |
| 性能テストが縮小データのみ | 本番相当の性能リスクが未検証 |
| UATで想定外の例外業務指摘が多い | 要件定義時の例外パターン洗い出し不足 |

### 5.4 ②との接続

- Chapter 3（Dependency）：例1のIF確定遅延は、②のDependency Registerに載る典型的なCritical Dependencyそのものである
- Chapter 5.4（ベンダー間責任分界）：例4の「システム化するか運用回避するか」の切り分けは、②のグレーゾーン判定の手順と直結する
- Chapter 7.6（先読み）：例2・例3はいずれも「消化率」という表面指標だけでは見えない予兆であり、②の先読みの型がそのまま適用できる

## Chapter 6：データ移行

データ移行は、他工程と違い「やり直しが効きにくい」特性を持つ。特にCutover（本番切替）は一定時間内に完了させなければならず、途中で止めて仕切り直すことが難しい。②Chapter 9演習のPJ-Dに対応する工程である。

> これらの質問は、間への波及があるかを見るためであり、個別PJの品質管理を引き取るためではない。

### 6.1 Fact → What it means → What happens next → What PgMO should ask

**例1：移行対象件数は把握しているが、データ品質は未評価**

| 段階 | 内容 |
|---|---|
| Fact | 移行対象データの件数は正確に把握されているが、データの品質（欠損・重複・不整合の有無）はまだ評価されていない |
| What it means | 「件数」という量的な指標は管理されているが、移行先システムで正しく使えるデータかどうかという質的な確認が抜けている |
| What happens next | 移行リハーサルや本番移行の段階で、品質問題（欠損・重複等）が原因のエラーが大量に発生し、想定していた移行時間内に収まらなくなる |
| What PgMO should ask | データ品質の評価はいつ実施する計画か／評価の結果クレンジングが必要と分かった場合、対応期間は移行スケジュールに織り込まれているか |

**例2：マッピングが未確定**

| 段階 | 内容 |
|---|---|
| Fact | 移行元と移行先のデータ項目の対応関係（マッピング）が、一部の項目についてまだ確定していない |
| What it means | 未確定の項目については、移行プログラムの開発自体が着手できないか、暫定的な対応（仮のマッピング）で進んでいる |
| What happens next | マッピングが後から変更されると、移行プログラムの作り直しが必要になる。確定が遅れるほど、移行リハーサルの実施自体が遅延する |
| What PgMO should ask | 未確定のマッピングは何件あるか／確定の障害は何か（業務側の判断待ちか、移行先システムの仕様待ちか）／いつまでに確定すれば移行リハーサルに間に合うか |

**例3：移行リハーサルは成功しているが、本番相当のデータ量ではない**

| 段階 | 内容 |
|---|---|
| Fact | 移行リハーサルは成功したと報告されているが、使用したデータ量は本番の一部（縮小データ）だった |
| What it means | リハーサルが検証したのは移行手順の正しさであって、本番データ量での処理時間・リソース消費までは検証されていない |
| What happens next | 本番移行（Cutover）で想定より処理時間がかかり、許容されている移行時間枠（システム停止時間）を超過するリスクがある。Cutoverは途中で止めにくいため、超過が判明した時点で選択肢が限られる |
| What PgMO should ask | 本番相当データ量でのリハーサルはいつ実施する計画か／縮小データの結果から本番の所要時間をどう見積もっているか／許容されている移行時間枠に対してどの程度の余裕があるか |

**例4：切り戻し（ロールバック）条件が曖昧**

| 段階 | 内容 |
|---|---|
| Fact | 移行手順書は用意されているが、移行を中断して切り戻す（ロールバックする）ための具体的な条件・手順が明記されていない |
| What it means | 「うまくいく前提」の手順書になっており、うまくいかなかった場合にどう判断し、どう戻すかが決まっていない |
| What happens next | 移行中に問題が発生した際、その場で「続行するか、戻すか」を即興で判断することになる。判断が遅れるほど、中途半端な状態でシステムが停止するリスクが高まる |
| What PgMO should ask | 切り戻しを判断する基準（どの事象が起きたら切り戻すか）は明文化されているか／切り戻しの実行手順とそれに要する時間は見積もられているか／その場の判断者は誰か |

### 6.2 早見表

| 兆候 | 疑うべきこと |
|---|---|
| 移行件数は把握しているがデータ品質が未評価 | 量的指標のみで質的な移行可否が未確認 |
| マッピングが未確定 | 移行プログラム開発の着手・確定スケジュールへの影響 |
| リハーサル成功だが本番相当量でない | 本番の処理時間・リソースが未検証 |
| 切り戻し条件が曖昧 | 移行中の異常時に判断基準がなく即興対応になるリスク |

### 6.3 ②との接続

- Chapter 5.4（ベンダー間責任分界）：データクレンジングは、②が明示的にグレーゾーンの例として挙げている論点である
- Chapter 8（RAID／Decision Log）：切り戻し条件の未整備は、事前に合意しておくべきDecisionが未決のまま残っている典型例

## Chapter 7：Interface／外部連携

> これらの質問は、間への波及があるかを見るためであり、個別PJの品質管理を引き取るためではない。

### 7.1 なぜIFはPJ間事故の温床になるのか

IFは、②の5領域のうち「Interface」そのものであり、複数のPJ・ベンダーが同時に触れる、プログラム全体で数少ない場所である。他の成果物（要件定義書・設計書等）は基本的に1つのPJの中で閉じているが、IF仕様だけは必ず2つ以上のPJが同じ理解で実装できていなければならない。

しかも、IFの合意が崩れていても、それぞれのPJ内では「自分たちの実装は正しく進んでいる」ように見え続ける。双方とも自分の仮定に沿って粛々と設計・実装を進めるため、問題は片方が気づいて指摘するまで表面化しない。この「双方が正常に見えたまま進行する」性質が、IF起因の事故を発見しにくくしている。

```text
仕様未確定（または解釈のズレ）
        ↓
両側が異なる仮定で設計
        ↓
実装が先行
        ↓
結合で不一致が発覚
        ↓
双方修正
        ↓
テスト再実施
        ↓
後続PJ・移行へ波及
```

この連鎖のどこで気づくかによって、影響範囲は大きく変わる。設計段階で気づけば片方の設計変更で済むが、実装が先行した後に気づけば、双方の手戻り・再テスト・スケジュール遅延に発展する。

### 7.2 Fact → What it means → What happens next → What PgMO should ask

**例1：IF仕様が未確定のまま、双方が実装に着手している**

| 段階 | 内容 |
|---|---|
| Fact | IF仕様のOpen Pointが複数残ったまま、双方のPJが実装に着手している |
| What it means | 双方が異なる仮定（暫定仕様）で実装を進めている可能性が高い。仮定を明示的に突き合わせないまま進むと、食い違いが結合テストまで顕在化しない可能性がある |
| What happens next | 結合テストで不整合が発覚し、双方が原因究明・修正・再テストを行うことになる。実装が進んでいるほど修正コストが大きく、結合テストのスケジュールそのものが遅延する |
| What PgMO should ask | 未確定のOpen Pointは何か／双方はそれぞれ何を仮定として実装しているか（仮定が食い違っていないか）／いつ・誰が確定させるか／確定した際、先行した実装のどこまでが手戻りになるか |

**例2：IF仕様書のバージョンが両PJで揃っていない**

| 段階 | 内容 |
|---|---|
| Fact | IF仕様書は「合意済み」とされているが、一方のPJが参照しているバージョンが、もう一方が最後に更新したバージョンより古い |
| What it means | 変更内容が両PJに同時に伝わっておらず、片方は既に無効になった仕様のまま実装を進めている |
| What happens next | 結合の直前まで気づかれず、結合テスト開始時に大量の不整合として一度に発覚する。原因調査に時間がかかり、どちらの実装が「正しい」かをめぐる対立にもなりやすい |
| What PgMO should ask | IF仕様書のバージョン管理・変更通知の方法はどうなっているか／双方が参照している版は最新か／直近の変更で、通知が届いていない相手はいないか |

**例3：正常系のIFは合意されているが、異常系（エラー処理）が合意されていない**

| 段階 | 内容 |
|---|---|
| Fact | IFの正常系（リクエスト・レスポンスの形式）は合意されているが、エラー発生時の挙動（エラーコード体系、タイムアウト時の扱い、リトライの要否等）は明文化されていない |
| What it means | 双方とも「正常に動く分には問題ない」と報告してくるため、正常系のテストが通れば「IF確定」と見なされやすいが、異常系の前提は依然として食い違っている |
| What happens next | 総合テストや移行リハーサルで異常系のシナリオを実行して初めて不整合が見つかる。発見が遅くなるほど、修正の影響範囲（両PJのエラーハンドリング設計）が広がる |
| What PgMO should ask | エラー処理・タイムアウト・リトライの仕様は合意済みか／正常系のテストが通ったことを「IF確定」として扱っていないか／異常系のテストはいつ実施する計画か |

**例4：1つのIFに複数PJが依存しているが、変更影響を把握しているのは1チームだけ**

| 段階 | 内容 |
|---|---|
| Fact | 認証基盤や共通マスタなど、複数PJが同じIFに依存している状態で、そのIFに変更が入ることになった |
| What it means | 変更を発意したPJは自分たちへの影響しか把握しておらず、他に依存している複数のPJへの影響範囲を誰も横断的に把握していない |
| What happens next | 変更後、依存している他PJの側で予期しない不具合が発生する。原因究明の際に「誰が影響範囲を確認すべきだったか」で責任の所在が曖昧になりやすい |
| What PgMO should ask | このIFに依存しているPJは他にいくつあるか／変更の影響範囲は誰が確認したか／変更のタイミングと周知先は決まっているか |

### 7.3 早見表

| 兆候 | 疑うべきこと |
|---|---|
| IF仕様にOpen Pointが残ったまま実装が進んでいる | 双方が異なる仮定で実装している可能性 |
| IF仕様書のバージョンが両者で食い違っている | 変更が片方に伝わっていない |
| 正常系だけで「IF確定」とされている | 異常系（エラー処理）の前提が未合意 |
| 1つのIFに複数PJが依存している | 変更の影響範囲が横断的に把握されていない |

### 7.4 ②との接続

- Chapter 3.6（IF設計レビューの手順）：本Chapterの例1〜4はいずれも、②のIF設計レビューで確認すべき観点と対応する
- Dependency Management：IF確定はそれ自体が典型的なCritical Dependencyであり、②のDependency Registerに載せるべき項目である

## Chapter 8：Environment／Infrastructure

環境・インフラは、要件定義や設計と異なり「見えにくい」成果物である。動いていることが当たり前とされ、問題が起きて初めて存在に気づかれる。②Chapter 9演習のテスト統括（PJ-E）が環境をいつ受け取るかという「抜けやすいポイント」と直結する。

> これらの質問は、間への波及があるかを見るためであり、個別PJの品質管理を引き取るためではない。

### 8.1 Fact → What it means → What happens next → What PgMO should ask

**例1：環境は完成したと報告されているが、設定差分がある**

| 段階 | 内容 |
|---|---|
| Fact | テスト環境は「構築完了」と報告されているが、実際に使い始めると、想定していた設定（ミドルウェアのバージョン、パラメータ等）と差分がある |
| What it means | 「環境構築完了」の判定基準がサーバーの起動確認どまりで、設計書との突き合わせによる設定内容の妥当性確認が行われていない |
| What happens next | 環境差分が原因の不具合が発生し、アプリケーション側の不具合と区別するための切り分けに時間がかかる。原因究明が長引くほどテストスケジュールが圧迫される |
| What PgMO should ask | 環境構築の完了判定基準に設計書との突き合わせは含まれているか／構築後の設定確認（差分チェック）はいつ・誰が行うか |

**例2：テスト環境と本番環境の構成に差がある**

| 段階 | 内容 |
|---|---|
| Fact | テスト環境と本番環境で、サーバースペック・ネットワーク構成・外部接続先等に既知の差異がある |
| What it means | テストで確認できるのは「テスト環境における」動作であり、本番環境固有の条件（性能・外部接続の遅延等）は未検証のまま残っている |
| What happens next | テストでは問題がなかった処理が、本番環境固有の条件下で性能劣化・接続エラー等を起こす。本番でしか再現しないため原因究明が難航しやすい |
| What PgMO should ask | テスト環境と本番環境の差異は一覧化されているか／その差異が影響しうる項目（性能・外部接続等）は、別途どのような方法で検証するか |

**例3：権限・ネットワーク開通待ちで作業が止まっている**

| 段階 | 内容 |
|---|---|
| Fact | 開発・テストに必要な権限付与やネットワーク開通の申請が、社内手続きの都合でまだ完了していない |
| What it means | システム開発上の課題ではなく、組織のプロセス（申請・承認フロー）がボトルネックになっている |
| What happens next | 開発・テスト要員が「作業をしたくてもできない」待機状態になり、後ろのスケジュールがそのまま後ろ倒しになる。手続きの遅延は現場の努力では短縮できないことが多い |
| What PgMO should ask | 申請から開通までの標準的なリードタイムはどれくらいか／どの承認プロセスで止まっているか／PgMOとして承認を早める働きかけができる相手はいるか |

**例4：性能試験用の環境が本番相当でない**

| 段階 | 内容 |
|---|---|
| Fact | 性能試験（負荷試験）を実施する環境のスペックが、本番環境と異なる（縮小されている、または共有環境で他の負荷と混在している） |
| What it means | 性能試験の結果が本番での性能をそのまま反映していない。良い結果が出ても悪い結果が出ても、本番での実際の性能は別に見積もる必要がある |
| What happens next | 縮小環境での良好な結果を鵜呑みにして稼働判定を行うと、本番稼働後に性能問題が発覚する。稼働後の対応は稼働前の対策よりコストが大きい |
| What PgMO should ask | 性能試験環境と本番環境の差分（スペック・専有か共有か）は何か／その差分を踏まえて本番での性能はどう見積もっているか／見積もりの確信度はどの程度か |

### 8.2 早見表

| 兆候 | 疑うべきこと |
|---|---|
| 環境完成の報告と実際の設定に差がある | 完了判定基準が起動確認どまりで、設定の妥当性確認が抜けている |
| テスト環境と本番環境に構成差がある | 本番固有の条件が未検証 |
| 権限・NW開通待ちで作業が止まっている | 技術課題ではなく組織プロセスがボトルネック |
| 性能試験環境が本番相当でない | 性能試験の結果が本番の性能を反映していない |

### 8.3 ②との接続

- Chapter 5.4（ベンダー間責任分界）：結合テスト環境構築は、②が明示的にグレーゾーンの例として挙げている論点である
- Chapter 5（テスト、本Framework）：例4は5.2例3（総合テストの性能検証が縮小データ）と対になる、環境側から見た同じリスクである

## Chapter 9：症状から引く早見表

Chapter 1〜8は工程順に学ぶための構成である。しかし実務では、報告を工程番号で聞くわけではない。「完了しました」「順調です」という一言が、実はChapter 2にも4にも5にも6にも8にも当てはまる、ということが普通に起きる。

本Chapterは、耳にした一言（症状）から、疑うべきこと・確認先へ直接ジャンプするための早見表である。Chapter番号を覚えている必要はない。

### 9.1 症状カテゴリ一覧

| # | 症状カテゴリ | こんな一言で気づく |
|---|---|---|
| A | 「完了」「順調」という報告全般 | 「完了しました」「順調です」「消化率◯％です」 |
| B | 未確定・Open Point・仮置きが残っている | 「別途調整」「暫定で」「今のところは」 |
| C | 縮小・簡易条件での検証を「検証済み」として報告 | 「リハーサルは成功しました」「テストは通りました」（条件を聞くと本番と違う） |
| D | バージョン・伝達のズレ | 「そう聞いていない」「その仕様はもう古いはず」 |
| E | 正常系のみ確認、異常系・例外が未確認 | 「普通に使う分には問題ない」 |
| F | 影響範囲・依存関係が横断的に把握されていない | 「うちへの影響はないです」（他への影響は？） |
| G | 人・体制のリスク | 「あの人に聞かないと分からない」「まだ手続き中で」 |
| H | 異常時・失敗時の対応が決まっていない | 「うまくいく前提で進めています」 |
| I | スケジュール上はつながっているが中身が違う（Consistency） | 「日程はそのとおりです」（でも指しているものが噛み合っていない） |

### 9.2 カテゴリ別：疑うべきこと・確認先

**A. 「完了」「順調」という報告全般**

| 具体的な兆候 | 疑うべきこと | 確認先 |
|---|---|---|
| 要件定義「完了」でもOpen Pointが残る | 「完了」がスケジュール上の区切りにすぎない | Ch3.1例1 |
| 基本設計「完了」でもPJ間部分が「別途調整」のまま | 自PJで閉じる部分だけが完了している | Ch2.2例 |
| 進捗率は順調だがレビューが滞留 | 「進捗」が実装完了のみを指す | Ch4.1例1 |
| 完成量は順調だが後工程での不具合発見割合が増えている | 前工程での検出・除去が機能していない | Ch4.1例2 |
| 結合テスト消化率は順調だが未修正不具合が減らない | 消化率＝実施率であり解消率ではない | Ch5.1、Ch5.2例2 |
| 移行件数は把握しているがデータ品質は未評価 | 量的指標のみで質的な移行可否が未確認 | Ch6.1例1 |
| 環境「完成」でも設定に差分がある | 完了判定が起動確認どまり | Ch8.1例1 |

**B. 未確定・Open Point・仮置きが残っている**

| 具体的な兆候 | 疑うべきこと | 確認先 |
|---|---|---|
| 非機能要件が定義書に記載されていない | 「完了」が機能要件のみを指す | Ch1.3例1 |
| 前工程レビュー未完了のまま次工程が並行着手（工程圧縮） | 手戻りリスクを内包したまま進行 | Ch1.3例2 |
| Open Pointをシステム側の仮定で埋めて設計している | 判断オーナーシップがシステム側に移っている | Ch3.1例2 |
| IF仕様のOpen Pointを残したまま双方が実装着手 | 双方が異なる仮定で実装している可能性 | Ch5.2例1、Ch7.2例1 |
| マッピングが未確定 | 移行プログラム開発の着手・確定への影響 | Ch6.1例2 |

**C. 縮小・簡易条件での検証を「検証済み」として報告**

| 具体的な兆候 | 疑うべきこと | 確認先 |
|---|---|---|
| 総合テストの性能検証が縮小データ | 本番相当の性能リスクが未検証 | Ch5.2例3 |
| 移行リハーサルが成功しているが縮小データ | 本番の処理時間・リソースが未検証 | Ch6.1例3 |
| テスト環境と本番環境に構成差がある | 本番固有の条件が未検証 | Ch8.1例2 |
| 性能試験環境が本番相当でない | 性能試験の結果が本番の性能を反映していない | Ch8.1例4 |

**D. バージョン・伝達のズレ**

| 具体的な兆候 | 疑うべきこと | 確認先 |
|---|---|---|
| IF仕様書のバージョンが両者で食い違っている | 変更が片方に伝わっていない | Ch7.2例2 |
| 要件変更が設計・テストに反映されていない | 変更管理が要件の変更だけで止まっている | Ch3.1例3 |

**E. 正常系のみ確認、異常系・例外が未確認**

| 具体的な兆候 | 疑うべきこと | 確認先 |
|---|---|---|
| 正常系だけで「IF確定」とされている | 異常系（エラー処理）の前提が未合意 | Ch7.2例3 |
| UATで想定外の例外業務指摘が多い | 要件定義時の例外パターン洗い出し不足 | Ch5.2例4 |

**F. 影響範囲・依存関係が横断的に把握されていない**

| 具体的な兆候 | 疑うべきこと | 確認先 |
|---|---|---|
| 1つのIFに複数PJが依存している | 変更の影響範囲が横断的に把握されていない | Ch7.2例4 |

**G. 人・体制のリスク**

| 具体的な兆候 | 疑うべきこと | 確認先 |
|---|---|---|
| 特定メンバーへのタスク集中 | 属人化による単一障害点化 | Ch4.1例3 |
| 権限・NW開通待ちで作業が止まっている | 技術課題ではなく組織プロセスがボトルネック | Ch8.1例3 |

**H. 異常時・失敗時の対応が決まっていない**

| 具体的な兆候 | 疑うべきこと | 確認先 |
|---|---|---|
| 切り戻し（ロールバック）条件が曖昧 | 「うまくいく前提」の手順になっている | Ch6.1例4 |

**I. スケジュール上はつながっているが中身が違う（Consistency）**

| 具体的な兆候 | 疑うべきこと | 確認先 |
|---|---|---|
| PJ間のマイルストーンの日付は揃っているが、それぞれが指す「完了」の定義・粒度・前提が異なる | 日付の一致は、成果物の中身の一致を意味しない | Ch2.1、Ch7.2例2 |

## Chapter 10：質問の目的別リファレンス

Chapter 1〜8の「What PgMO should ask」を、Chapter別ではなく質問の目的別に並べ替えたものである。個別の質問を暗記するのではなく、次の6つの型を体に入れることが最終ゴールである。

```text
何が未確定か？
        ↓
誰が決めるか？
        ↓
いつ決めるか？
        ↓
（それまでは）今は何を仮定して進めているか？
        ↓
変わったらどこまで影響するか？
        ↓
間に合わなければどうするか？
```

この6つの問いは、Chapter 1〜8のどの「Fact」に対しても、ほぼそのまま当てはめられる。

答えが集まった時点で、それはそのまま②のDependency RegisterやRAID（Risk／Assumption／Issue／Decision）の入力になる。この6問はPgMOの頭の中で終わらせる質問ではなく、②へ書き込むための素材を集める質問である。

### 10.1 前提を暴く（何が未確定か／今は何を仮定しているか）

| 質問 | 出所 |
|---|---|
| 未確定のOpen Pointは何件あり、それぞれ何か | Ch3.1例1、Ch5.2例1、Ch7.2例1 |
| 双方は現時点で何を仮定として実装・設計しているか | Ch1.3例1、Ch3.1例2、Ch5.2例1、Ch7.2例1 |
| 正常系のテストが通ったことを「確定」として扱っていないか | Ch7.2例3 |
| 縮小データ・簡易条件での結果を、本番相当の結果として扱っていないか | Ch5.2例3、Ch6.1例3、Ch8.1例2、Ch8.1例4 |

### 10.2 Ownerを特定する（誰が決めるか）

| 質問 | 出所 |
|---|---|
| この判断のオーナーは誰か（業務側かシステム側か） | Ch3.1例2 |
| 未確定事項は誰が確定させるか | Ch1.3例1、Ch3.1例1、Ch5.2例1 |
| その場の判断者（異常時・切り戻し時）は誰か | Ch6.1例4 |
| 変更の影響範囲は誰が確認したか | Ch7.2例4 |

### 10.3 期限を確認する（いつ決めるか）

| 質問 | 出所 |
|---|---|
| いつ・誰が確定させるか | Ch1.3例1、Ch5.2例1、Ch6.1例2 |
| 本番相当条件での検証はいつ実施する計画か | Ch5.2例3、Ch6.1例3 |
| 申請・承認プロセスのリードタイムはどれくらいか | Ch8.1例3 |

### 10.4 影響範囲を広げる（変わったらどこまで影響するか）

| 質問 | 出所 |
|---|---|
| これが確定・変更された場合、先行している部分のどこまでが手戻りになるか | Ch1.3例2、Ch2.2例、Ch3.1例3 |
| このIF・この項目に依存しているPJは他にいくつあるか | Ch7.2例4 |
| 不具合・指摘は原因別・重大度別にどう分布しているか | Ch4.1例2、Ch5.2例2、Ch5.2例4 |

### 10.5 代替策・Risk受容を確認する（間に合わなければどうするか）

| 質問 | 出所 |
|---|---|
| 確定が遅れた場合の代替（暫定仕様での継続等）は決まっているか | Ch3.1例1 |
| 間に合わない場合の代替検証・Risk受容の判断は誰がするか | Ch5.2例3 |
| どこまでシステム化し、どこから運用回避にするかの切り分け方針は誰がいつまでに決めるか | Ch5.2例4 |
| 切り戻しの実行手順とそれに要する時間は見積もられているか | Ch6.1例4 |

## Appendix：Capability Modelへの接続（案）

`frameworks/consultant-capability-skill-model.md` のCapability II（Delivery／Execution）のうち、②を教材としている次の4 Skillには、現時点でPrerequisite Knowledgeの節がない。

- Dependency Management（教材：② Ch3）
- Schedule Integration（教材：② Ch4）
- Scope／Responsibility（教材：② Ch5）
- Risk／Issue Management（教材：② Ch7〜8）

Risk／Issue ManagementはReview Round 1で追加した。SI経験がないと、「IF Open Pointが10件あります」「テスト消化率は順調です」といった報告を聞いても、それがRiskかIssueか、Severityがどの程度か、いつ上げるべきかを判断できない。SI Project LiteracyなしにRisk／Issue Managementの型だけを持っていても、RAG判定の入力そのものが作れない。

本Frameworkの到達目標を、Capability Modelの既存ルール（Prerequisite KnowledgeはLevel化せずPass／Not Yetの二値、§4）に合わせて次の5項目に集約する。Capability IVのようにSkillごとに異なる知識領域を挙げるのではなく、4 Skill共通のPrerequisite Knowledgeとして扱うことを想定している（SI Project Literacyは分割できる知識領域の集合ではなく、1つの一体的な解像度であるため）。

**Prerequisite Knowledge（Pass／Not Yet）**
- SIライフサイクル（要件→設計→開発→テスト→移行→稼働）の各工程が何を確認して次に進むかを説明できる
- 工程間の主要な受け渡し物（成果物）を挙げられる
- 兆候を1つ聞いて、後工程への典型的な波及を1つ以上挙げられる
- その兆候に対して、PgMOとして確認すべき質問を組み立てられる
- 未発生の不確実事象はRisk、既に発生している問題はIssueとして区別できる。Impact・Urgency、Riskの場合はLikelihoodも踏まえて、対応優先度／Severityを判断できる

Required Levelは、Strategy Consultant RoleではCapability II自体が対象外（L0基準）のため適用されない。PgMO Role側の`consultant-role-responsibility-model.md`相当の定義がまだないため、Required Levelの確定はそちらの整備を待つ。Skill本体へのPrerequisite Knowledge追加自体は、Role定義を待たずに反映できる。
