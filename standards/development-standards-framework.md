# Development Standards Framework

**Version:** v1.1  
**Status:** Active  
**Owner:** Kazuaki Tanaka  
**Origin:** 大規模基幹系更改案件の開発標準（2003/12）の位置づけ・構成を一般化。加えて金融機関等 IT 基準パックの**技術／運用／設備**三層（2002 案）を一般化。クライアント名・ベンダー名・固有情報なし。

---

## Purpose

エンタープライズシステム開発において、**発注側が示す方針（ガイドライン）**と**ベンダーが遵守するルール（規約）**を一体として設計・運用するためのフレームワークです。

目的は、品質・保守性・生産性を確保しつつ、プロジェクト特性に応じて**適用範囲を限定できる**ことです。

`standards/document-management-standard.md` が文書の管理・作成を定義するのに対し、本書は**開発標準全体の構成と責任分界**を定義します。

---

## When to Use

- 大規模更改・新規基幹系開発の**開発標準セット**を設計するとき
- RFP / 契約に「開発標準遵守」を盛り込むとき
- 発注側 PM とベンダー PM の**管理責任**をすり合わせるとき
- パッケージ（ERP等）とカスタム開発が混在するプログラムの**適用範囲**を決めるとき

## Core Concepts

### 開発標準とは

情報系・業務系を問わず、新規開発・更改に適用する**共通の品質基盤**です。小規模案件でも、標準を参照することでレビュー観点・成果物体系・引継ぎ品質を揃えます。

### 二層構成

| 層 | 読者（主） | 性質 | 例 |
|----|-----------|------|-----|
| **ガイドライン系** | 発注側担当者 | 開発方針・管理観点・手順の**指針** | 開発管理、環境、運用設計/引継 |
| **規約系** | 開発ベンダー | 遵守すべき**ルール** | 命名、コード、DB、UI、リリース |

**原則:** ガイドラインは「何を見るか・いつ判断するか」、規約は「どう作るか・どう命名するか」を担う。

### 三基準レイヤ（技術／運用／設備）

ガイドライン／規約とは**直交する軸**。規制業・重要インフラ・金融機関等で、安全対策を「システムが持つ機能」「人が回す手続」「物理プラント」に分けて要求するときの型。

| 層 | 問い | 大分類（一般化） | 主に接続する資産 |
|----|------|----------------|-----------------|
| **技術基準** | システム／基盤は何を備えなければならないか | 災害・障害対策、故意・過失対策（認証・権限・防護・不正防止等）、監査証跡機能 | 設計要件、アーキテクチャ、運用設計の監視／バックアップ |
| **運用基準** | 誰がどの手続で回し、記録するか | 管理体制、入退、運用（権限・オペ・入出力・ファイル・監視・CP 等）、開発・変更、設備管理、教育、外部委託、監査 | `operations-design-guide.md`, `operations-handover-guide.md`, 開発管理・リリース |
| **設備基準** | 建物・電空・回線は何を満たすか | 建物、電算室・保管室、電源／空調室、電源・空調・監視制御・回線設備 | インフラ／ファシリティ設計（開発標準本文の外でも可） |

**使い方:**

- RFP／社内基準では「準拠」と書く前に、**どの層のどの大分類を今回スコープにするか**を切る。  
- 開発プロジェクト単体では設備層を丸ごと持たないことが多い。その場合は設備を**除外理由付き**で適用表に残す。  
- 業界システム監査指針の統制クラスは、この三層＋本カタログのガイドライン／規約へ**投影**する（チェック行の転載はしない）。→ `knowledge/patterns/fis-system-audit-as-assurance.md`

**登録しないもの:** 各基準の項番本文、閾値、施設仕様の細部、監査チェックポイント集の行。

## Standard Catalog (Generalized)

以下は2003年当時の基幹系更改で用いた**標準カタログ**を一般化したものです。案件では名称・章立てを調整してよい。

### ガイドライン系

| 標準 | 主な内容 | 主な読者 |
|------|---------|---------|
| **開発管理ガイドライン（管理概要・管理本編）** | 進捗・仕様・品質・構成・コミュニケーション管理 | 発注側 PM、ベンダー PM |
| **開発管理ガイドライン（開発手順編）** | 工程別作業・成果物・レビューポイント（カスタム / パッケージ別） | 発注側レビュー担当、ベンダー設計リード |
| **開発環境／試験環境ガイドライン** | 共有環境の利用・管理・セキュリティ | ベンダー、インフラ担当 |
| **運用設計ガイドライン** | SL別の運用設計検討項目（監視・バックアップ等） | ベンダー、運用設計担当 |
| **運用引継ガイドライン** | 引継資料・手順・運用委託/AP維持管理との合意 | ベンダー、運用委託先 |
| **ドキュメント標準** | 文書管理規約・作成基準・文書区分 | 全関係者 |

### 規約系

| 標準 | 主な内容 | 備考 |
|------|---------|------|
| **システム命名規約** | システムID・業務ID・命名管理手順 | クライアント固有IDはリポジトリに登録しない |
| **コード体系規約** | 文字コード・外字 | 時代・地域に応じて更新 |
| **ライブラリ／リリース管理規約** | 原本管理、環境間リリース保証 | `release-management-guide.md` |
| **維持管理規約** | AP/共通モジュールの維持管理・変更方針 | |
| **カスタム開発技法規約** | 言語・フレームワーク別コーディング | **技術スタック依存**。原則として一般化のみ |
| **パッケージ開発技法規約** | ERP等パッケージ固有ルール | パッケージ採用時のみ |
| **データベース管理規約** | 設計・アクセス・SQL指針 | |
| **UI標準規約** | 画面・帳票の統一 | Web/GUI/パッケージ別 |
| **ユーザ管理規約** | ID申請・管理手順 | IAM連携はクライアント固有 |

## Applicability by Domain

パッケージとカスタムが混在するプログラムでは、**領域別に適用セットを分ける**。

| 領域（例） | 追加で強く適用する標準 |
|-----------|----------------------|
| **取引・カスタム中心** | カスタム開発技法規約、カスタム開発手順編、リッチGUI UI |
| **会計・ERP中心** | パッケージ開発技法規約、パッケージ開発手順編、パッケージ UI |
| **人事・HRパッケージ** | パッケージ別開発手順編（SAP-HR等） |
| **全領域共通** | 管理本編、環境、運用設計/引継、ドキュメント標準、命名・リリース・DB・帳票UI・ユーザ管理 |

**発注側の役割:** 領域ごとの適用表をプログラム定義時に合意し、RFP / 契約別添に載せる。

## Roles and Responsibilities

| 関係者 | ガイドライン | 規約 |
|--------|-------------|------|
| **発注側 PM / 開発担当** | 管理本編の観点で進捗・仕様・品質・構成・会議を監督。ベンダー独自手法があっても**レビュー基準**として使う | 遵守状況をレビュー・受入判定に反映 |
| **開発ベンダー** | 実施要領（進捗管理実施要領等）を必要に応じて作成。運用設計・引継では設計書に保守性向上の仕組みを盛り込む | 命名・コーディング・リリース等を遵守 |
| **運用委託先** | 引継ガイドラインに沿った受入・合意 | リリース・ユーザ管理の運用側手順を遵守 |

## Management Domains (Development Management Guide)

`development-management-guide.md` で詳細化する**5管理領域**：

| 領域 | 発注側が見るポイント（概要） |
|------|---------------------------|
| **進捗管理** | 管理単位、週次報告、遅れの可視化、問題管理、工程終了判定 |
| **仕様管理** | 仕様確定、変更フロー（設計連絡→確認→変更管理） |
| **品質管理** | レビュー、試験、問題・障害の重要度分類 |
| **構成管理** | 成果物版管理、ベースライン、チェックポイント |
| **コミュニケーション管理** | 工程会議、進捗会議、議事録、使用ツール |

ベンダーはこれを受けて**プロジェクト実施要領**を作成する（標準の写しではなく、プロジェクト向けに具体化）。

## Lifecycle Placement

| フェーズ | 主に参照する標準 |
|---------|-----------------|
| 契約 / キックオフ | 本フレームワーク、適用範囲表、ドキュメント標準 |
| 要件〜設計 | 開発手順編、ドキュメント標準、技法/UI/DB規約 |
| 製造〜試験 | 環境ガイドライン、品質/構成管理、リリース規約 |
| 移行〜Go-live | 運用設計、運用引継、リリース規約 |
| 運用 | 維持管理、ユーザ管理、ドキュメント改訂 |

`frameworks/program-phases-investigation-to-requirements.md` は調査〜要件（Phase 100–500）を扱う。`frameworks/sap-implementation-phase-model.md` は ERP パッケージ導入の Phase 0–6（評価〜維持）を扱う。本フレームワークは**設計以降（Build / Run）**の標準体系です。

## Exceptions and Tailoring

標準は TCO 削減のため**解釈・見直しを許容**する。以下は適用限定の典型例：

| 条件 | 対応 |
|------|------|
| 既存アーキテクチャを継承 | 該当規約・手順を限定適用 |
| 試行サービス等、保守性より速度優先 | ガイドラインの一部を除外 |
| 特殊パッケージで標準適用が困難 | パッケージベンダー標準で代替し、差分を文書化 |
| 不適切・時代遅れの条項 | プログラム合意の上で改訂または除外 |

**必須:** 例外は口頭にせず、**適用範囲表 + 改訂履歴**に残す。

## Relationship to PMO

| 観点 | PMO（`standards/pmo-operating-guide.md`） | 開発標準（本書） |
|------|----------------------------------------|-----------------|
| スコープ | プログラム横串・ポートフォリオ・変革 | 単一/複数開発プロジェクトの実行品質 |
| 進捗 | SteerComm、Benefit、統合ロードマップ | WBS/工程表、週次進捗、問題管理表 |
| 成果物 | プログラム定義、統合 SCN 等 | 設計書、試験計画、運用引継資料 |

両者は競合ではなく、**PgMO が「何をいつ決めるか」、開発標準が「どう作って渡すか」**を分担する。

## Review Checklist

- [ ] ガイドラインと規約の境界が関係者に説明されているか
- [ ] 領域別（カスタム / パッケージ）の適用表が合意されているか
- [ ] 技術／運用／設備の三基準のうち、今回スコープと除外が適用表にあるか（該当業態のみ）
- [ ] 例外・限定適用が文書化されているか
- [ ] ドキュメント標準（文書区分・番号・承認）と整合しているか
- [ ] 運用引継・リリースの責任分界が運用委託契約と一致しているか
- [ ] クライアント固有ID・ベンダー名・実様式がリポジトリ用コピーに含まれていないか
