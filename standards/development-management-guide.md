# Development Management Guide

**Version:** v1.0  
**Status:** Active  
**Owner:** Kazuaki Tanaka  
**Origin:** 大規模基幹系更改案件の開発管理ガイドライン管理本編（2003/12）を一般化。クライアント名・ベンダー名・固有情報なし。

---

## Purpose

発注側開発担当者が、ベンダー実行プロジェクトを**進捗・仕様・品質・構成・コミュニケーション**の5領域で監督するための標準です。

`standards/development-standards-framework.md` が開発標準全体の構成を定義するのに対し、本書は**管理本編**（実行ガバナンスの中核）に特化します。

ベンダーは本書の観点を受けて**プロジェクト実施要領**（進捗管理実施要領等）を作成する。

---

## When to Use

- 大規模開発・更改プロジェクトの**発注側 PM / 開発担当**の日常管理
- 進捗会議・仕様調整会議・工程終了判定の設計
- ベンダー WBS / 進捗表 / 問題管理表の**レビュー基準**
- RFP / 契約別添の「開発管理遵守」条項の具体化

---

## Overview

管理本編は以下5章で構成される：

| 章 | 領域 | 発注側の主な役割 |
|----|------|-----------------|
| 2 | 進捗管理 | 計画妥当性確認、進捗会議、アクション、工程終了確認 |
| 3 | 仕様管理 | 要件/仕様確定、仕様変更の可否判断 |
| 4 | 品質管理 | レビュー・試験の監督、品質目標・工程終了判定 |
| 5 | 構成管理 | 変更のトレーサビリティ、受入・版確定 |
| 6 | コミュニケーション管理 | 会議体系、様式・ツールの運用 |

ベンダー提案の「プロジェクト管理方針」章との境界は、本書末尾の **Project Management Policy Layer**（`project-management-policy-layer.md`）を参照。

## Roles and Reporting Lines

### 階層構造（典型）

```
プロジェクトマネージャ（PM）
  └ プロジェクトリーダ（PL）×システム/領域
       └ グループリーダ（GL）×業務グループ
```

| 役割 | 責任 |
|------|------|
| **PM** | 全体概要計画、進捗会議主催（レベル1）、横断調整 |
| **PL** | 詳細計画、レベル2/3進捗、工程終了判定、ベンダー側窓口 |
| **GL** | グループ内 WBS・実績、問題の一次対応 |

**報告ルート（ベンダー内部）:** GL → PL → PM  
**発注側との窓口:** 進捗管理レベルに応じ PL または PM

PM と PL は規模により同一人物でもよい。

## 1. Schedule Management (進捗管理)

### 1.1 Purpose

1. 遅れの早期発見と**大幅スケジュール遅延**の防止（経験差による遅れを含む）  
2. 計画作業項目の漏れ・重複の確認  
3. 問題・課題への対策と計画見直しの確認  

### 1.2 Three Progress Levels

| レベル | 種類 | 管理者 | 管理周期 | スケジュール幅 |
|--------|------|--------|---------|---------------|
| **1** | 全体（複数システム） | PM | 月 | 月/週 |
| **2** | システム（業務グループ集約） | PL | 1–2週 | 日 |
| **3** | グループ内（WBS タスク/WP） | GL | 1–2週 | 日 |

**規模別の目安:**

| プロジェクト形態 | 使用レベル |
|-----------------|-----------|
| 複数システム | 1 + 2 + 3 |
| 単一システム | 2 + 3 |
| 単一システム・単一業務グループ | 1–3 を統合管理可 |

### 1.3 Progress Flow

```
概要計画（発注側PM → ベンダーPM）
  → 詳細計画（ベンダーPL：体制・管理指標・WBS）
  → 計画公開（関係者全体）
  → 計画妥当性確認（発注側）
  → [工程ループ] 進捗会議 → 問題/課題対策 → 対策結果確認 → 工程終了判定
```

### 1.4 WBS and Control Unit

**WBS 階層:** プロジェクト → 工程 → アクティビティ → タスク → **ワークパッケージ**

- 管理単位は原則**ワークパッケージ**
- タスク成果物の作成作業を WP として分解
- 担当者の作業状況が判定できる粒度まで分割

### 1.5 Management Metrics (Examples)

工程ごとに定量指標を設定。検討タスク等で定量困難な場合は**完成率**で管理。

| 例 |
|----|
| ドキュメント記述項目数 / ページ数 |
| プログラムモジュール数 |
| 試験項目数 |
| バグ消化数 |
| マイルストン消化率 |

### 1.6 Delay Visibility (−0.5W notation)

進捗管理表では、予定 vs 実績の差を**週単位**で可視化する（例: `−0.5W`, `−1W`, `+1W`）。

- 小さな遅れ（0.5週）も早期に表面化させる
- 遅延タスクについては**要因・後続影響・リカバリ策・リカバリ時期**を進捗会議で確認

### 1.7 Meetings and Minutes

- **進捗会議:** 定期開催。実績・問題・工程終了を報告受領
- **議事録:** ベンダー作成 → 次回確認 → 主催者・責任者承認 → 原本ベンダー保管、コピー発注側保管

### 1.8 Issue Management (Progress Context)

- 問題・課題は**問題管理表**で一元管理
- GL/PL で解決不能な場合は**速やかに上位報告**
- 緊急案件は**アクション会議**を開催

### 1.9 Phase Exit Criteria

各工程開始前に、発注側 PL とベンダー PL が**工程終了判定基準**を設定（品質管理章と連動）。

### 1.10 Client Checkpoints (Schedule)

| タスク | チェック |
|--------|---------|
| 計画妥当性 | 工程開始前にスケジュール作成、無理のない設定、適切な管理レベル、管理周期に合った BD、管理単位統一 |
| 管理指標 | 工程ごとに指標設定、全タスクに成果物・実行責任者・マイルストン |
| 進捗会議 | 遅延時の要因/影響/リカバリ、前回議事録・宿題、問題の重要度/影響/担当/期限 |
| 対策確認 | 処置適切・期限内完了、緊急時のアクション会議計画と実施 |
| 工程終了 | 判定者明確、判定基準は品質管理章参照 |

## 2. Specification Management (仕様管理)

### 2.1 Purpose

要件定義書 / 詳細設計書とソフトウェアの対応関係を取りまとめ、機能・性能・信頼性を確実に実現する。仕様変更時は他グループ・他システムへの調整が必要。

### 2.2 Governance Structure

1. 仕様管理**キーマン**（決定権者）を発注側内で任命  
2. **ユーザ部門**を体制に組み込む  
3. グループごとに仕様管理**窓口**を設ける  
4. 要件追加/変更・仕様変更の**決定者**を明確化  

### 2.3 Two Tracks

| トラック | タイミング | 内容 |
|---------|-----------|------|
| **仕様検討管理** | 仕様確定前 | 要件検討 + 仕様検討 |
| **仕様変更管理** | 詳細設計承認（仕様確定）後 | 合意された変更のみ |

**境界ルール:**

- 仕様確定後の設計書変更は原則**障害**として管理（ベンダー/AP維持に過失がなければ仕様変更扱いの例外あり）
- **要件スコープが変わる**追加/変更は、仕様確定後でも**仕様変更**として扱う

### 2.4 Specification Review Flow (Pre-FIX)

| Step | 内容 |
|------|------|
| ① 要件提示 | 発注側 → ベンダー窓口 |
| ② 要件調整 | レビュー・問題記述票で確認。**ユーザ部門参画必須** |
| ③ 要定承認 | 全要件事項確認 → **要件スコープ確定**（証跡必須） |
| ④ 仕様調整 | 詳細設計レビュー・問題記述票。**ユーザ部門参画必須** |
| ⑤ 詳設承認 | 全仕様確認 → **仕様確定**（仕様確認書等で証跡） |

口頭・電話の問合せも**必ず文書化**する。

### 2.5 Change Flow (Post-FIX)

```
① 問題発生（障害 vs 仕様問題を切り分け）
  → ② 仕様調整（設計連絡票で影響調査）
  → ③ 仕様変更依頼（内容・理由・緊急度/重要度・影響範囲・変更方法）
  → ④ 変更内容検討
  → ⑤ 仕様調整会議（実施/延期/再検討/中止、リリース時期）
  → ⑥ 履歴管理
  → ⑦ 変更作業実施・確認
```

**変更可否の判断観点（発注側）:**

1. 計画・契約変更が容認できるか  
2. 開発コスト増が容認できるか  
3. 工期延長が容認できるか  
4. 他システムへの影響がないか  

計画/契約変更が必要な場合は、先に計画・契約見直しを実施。

## 3. Quality Management (品質管理)

### 3.1 Definition

品質 = システム利用者の**満足度**。本標準は設計・プログラム品質を左右する**機能性**を重視。

### 3.2 Verification by Phase (Custom Development)

| フェーズ | 検証対象 | 妥当性確認（発注側） | 検証（ベンダー） |
|---------|---------|---------------------|-----------------|
| 要件定義/分析 | 要件定義書 | レビュー | レビュー |
| 設計/製造 | 詳細設計書、プログラム | — | 結合試験 |
| 試験 | システム全体 | 総合運転試験 | 総合試験 |

パッケージ開発（ERP等）では分析/プロトタイピング/FIT-GAP を追加（原本参照）。

### 3.3 Quality Metrics

特定の数値は案件で設定。以下を**目標値 + 許容上限/下限**で定義：

| 指標 | 計算式（例） |
|------|-------------|
| **試験密度** | 試験項目数 ÷ 開発規模 |
| **障害検出密度** | 検出障害数 ÷ 開発規模 |

開発規模 = ステップ数 or ファンクションポイント（ベンダー標準に合わせる）。  
総合運転試験の品質目標は**発注側**が設定。

### 3.4 Review Flow (Summary)

```
要件ヒアリング → レビュー体制確立 → 設計（内部レビュー）
  → レビュー準備（事前送付・事前コメント）
  → レビュー実施 → 問題記述票 → 修正 → 回答 → 再レビュー判定
  → 品質判定（レビュー結果報告書）→ 設計承認 → 工程終了判定 → 進捗会議で報告
```

**要点:**

- レビュー時に議事録は作らず、**問題記述票**に設計エラー以外も記録
- **部分レビュー + 通しレビュー**で網羅性・整合性を確認
- 問題記述票の重要度（大/中/小）に偏りがないか確認

### 3.5 Test Flow (Summary)

**結合/総合試験（ベンダー主体）:** 品質目標 → 試験計画 → 計画確認 → 試験 → 障害管理（障害処理票）→ 途中経過確認（進捗会議）→ 品質判定 → 工程終了

**総合運転試験（発注側主体）:** 試験グループ/委託先が実施。発注側 PL が計画確認・品質判定・工程終了。ベンダーは障害修正依頼に応答。

**工程終了時の確認例:** 障害レベル偏りなし、業務影響障害残存なし、障害発生率収束、ペンディングの引継先/内容/期限明確（総合試験は原則ペンディング持ち込み不可）。

## 4. Configuration Management (構成管理)

### 4.1 Purpose

ソフトウェア・ハードウェア・ドキュメントの変更について**トレーサビリティ**を保証し、システム損傷を防止。

### 4.2 Basic Policy

1. 作業目的を明確化し、作業計画を作成  
2. 役割分担を明確化し、責任者承認を得る  
3. 作業履歴を記録  
4. 完了報告と責任者確認  
5. 確認結果を**最新状態**として管理  

### 4.3 Control Start Timing

| 対象 | 管理開始（遅くとも） |
|------|---------------------|
| ソフトウェア | 総合運転試験開始時 |
| ハードウェア | 総合運転試験開始時 |
| ドキュメント | 承認・版数付与時 |

ドキュメント管理手順は `standards/document-management-standard.md` に従う。

### 4.4 Change Flow

```
変更要望 → 受入れ → 変更内容確認 → 作業計画 → 承認
  → SW貸出 / HW変更許可 / ドキュメント提供
  → 変更作業 → 変更後確認 → 納品 → 受入れ → 変更確定（ライブラリ最新化・版番号）
```

### 4.5 Client Checkpoints (Configuration)

| タスク | チェック |
|--------|---------|
| 変更要望 | 承認責任者、変更理由、変更前バージョン/状態 |
| 承認 | 責任者、対象、影響範囲、作業日/期間/内容/量、手順遵守 |
| 受入れ | 媒体ウイルス検査、保護、必要時暗号化 |
| 変更確定 | 変更後バージョン/状態、ライブラリ最新化 |

## 5. Communication Management (コミュニケーション管理)

### 5.1 Purpose

発注側とベンダー間の**公式情報**を敏速かつ適切に伝達する。

### 5.2 Basic Principles

1. **体制・役割の明確化** — 情報経路を定義  
2. **情報伝達の確認** — 合意・承認の証跡を残す  
3. **情報ライフサイクル** — 発生→収集→配布→蓄積→廃棄  

### 5.3 Meeting Types

| 会議 | 目的 |
|------|------|
| **進捗会議** | 進捗/品質報告、工程終了確認、問題抽出、スケジュール変更審議 |
| **アクション会議** | 緊急・重要問題の早期解決 |
| **仕様調整会議** | 仕様確認・調整・変更の決定 |

## Issue Severity (A–D)

問題管理表（AIOS-REC-04）の重要度：

| レベル | 定義 |
|--------|------|
| **A** | プロジェクト全体に影響。一部作業が滞っている |
| **B** | 複数領域に影響。解決策が未確定 |
| **C** | 複数領域に影響。解決策は確定 |
| **D** | 自領域で解決可能 |

**工程会議への提示ルール:** 重要度 **B 以上**、または意志決定が遅れている案件（内部調整不能な費用増、マイルストン変更、サービス品質への重大影響等）。

レビュー問題記述票（AIOS-REC-10）の重要度は **大 / 中 / 小**（設計指摘用）。

## Project Management Policy Layer (方針章との境界)

ベンダー提案やキックオフの「プロジェクト管理方針」は、本書の5領域監督と**同じ平面ではない**。方針章が固定すべきは、進捗の測り方・会議の事実確認と決定の分離・課題／リスク／ToDo・変更とベースライン（QCD）・次工程阻害要因の品質追跡である。判断の型は `knowledge/patterns/project-management-policy-layer.md`。

| 本書の章 | 方針章で追加確認すること |
|---------|-------------------------|
| 進捗 | 件数％ではなく作業量差異で遅延規模が見えるか |
| 仕様／構成の変更 | 変更票の状態遷移と、要求・契約・WBS ベースラインへの QCD 条件 |
| 品質 | 工程目標に加え、次工程の阻害要因を早期に消しているか |
| コミュニケーション | 上位報告前の事実確認場があるか（決定の場と混同していないか） |
| 問題管理（A–D） | 損失×不確実性で Risk / Issue / ToDo が切り分けられているか |

プログラム層のステコミ／横断／検査は `playbooks/program-governance-cadence.md`。

## Review Checklist (Engagement Lead)

- [ ] 3レベル進捗管理が規模に適合しているか

- [ ] 会議体系（進捗/アクション/仕様調整）が機能しているか
