## Purpose

新規システムの**運用設計**において、業務運用とシステム運用の検討項目を整理し、統合監視環境への準拠を通じて**高いサービスレベルを低い運用コスト**で実現する標準です。

ベンダーは設計書（運用設計書・運設）に保守性向上の仕組みを盛り込み、発注側は運用委託との整合を確認します。

`standards/deliverable-archetypes.md` Archetype G の「運用設計書」と接続します。

## When to Use

- 要件定義以降の**運用要件**定義・詳細化
- 運用設計書（運設）の作成・レビュー
- 運用委託 RFP / SLA 設計の入力
- Go-live 前の監視・バックアップ・ジョブ設計の合意

---

## Scope and Roles

### 対象

- 新規導入の業務系・情報系システム（基盤ガイドライン準拠を前提）

### 三者役割

| 関係者 | 役割 |
|--------|------|
| **発注側** | 方針決定、統合監視との整合、承認 |
| **開発ベンダー** | 運用設計書作成、運用要件の具体化 |
| **運用委託先** | 統合監視サービス、運用実施、監視方式への準拠 |

---

## Basic Policy

1. 発生事象と**重要度**を整理し、適切な**監視項目・監視方法**を設計する  
2. システム特性と**費用対効果**に基づく監視・管理（過剰監視を避ける）  
3. **統合運用監視**を前提に、稼働・障害を一元管理  

---

## Design Timing

運用設計は業務設計スケジュールと**完全同期しない**。

| ルール | 内容 |
|--------|------|
| 要件定義 | **すべての検討項目**について運用要件を定義（必須） |
| 詳細設計以降 | 要件整理の結果、必要と判断した項目の**仕様を確定** |

工程記号（参考）: BD=要件/分析, DD=詳細設計, M=製造, SI=結合, PT=総合試験

## Business Operations Checklist

業務運用（業務要件側）の検討項目：

| 項目 | 検討内容 | 必須 | 仕様確定目安 |
|------|---------|------|-------------|
| **稼働スケジュール** | オンライン/バッチのサービス曜日・時間、延長時の夜間バッチ影響 | ○ | BD–DD |
| **運用基本サイクル** | 日次/週次/月次/期末処理一覧、重複時の影響 | ○ | BD–DD |
| **ジョブスケジュール** | 起動連携、エラー時リトライ/停止/スキップ、性能、オペレータ操作 | バッチあり | DD–M |
| **業務日付** | 日付またがり処理の管理方法 | 該当時 | DD |
| **データ移行** | 通常業務での移行方式・手順 | 該当時 | DD–M |
| **ソフトウェア配布** | 配布・リリース手段 | ○ | M–SI |

## System Operations Checklist

システム運用（技術側）の検討項目：

| 項目 | 検討内容 | 必須 | 仕様確定目安 |
|------|---------|------|-------------|
| **保守（起動/停止）** | 通常/縮退運転時の HW/SW/MW/AP 起停手順 | ○ | DD–SI |
| **リブート** | サーバ/ NW 機器のリブート要否・タイミング | ○ | DD–SI |
| **計画停止** | メンテナンス用計画停止 | ○ | DD–SI |
| **障害対応** | 想定障害時の運用対処・復旧方法 | ○ | M–PT |
| **キャパシティ** | ファイルローテーション、DB表領域クリーンアップ、資源分析ツール | ○ | M–PT |
| **時刻同期** | サーバ/NW 機器の時刻同期 | ○ | M–PT |
| **セキュリティ** | 組織セキュリティガイドライン準拠 | ○ | DD–SI |
| **バックアップ** | 業務/システムバックアップ（後述） | ○ | BD–DD |
| **監視** | 死活/ログ/プロセス/キャパシティ（後述） | ○ | DD–PT |

## Backup Design

### 2種類

| 種別 | 目的 |
|------|------|
| **業務バックアップ** | 業務不整合からの復旧 |
| **システムバックアップ** | 機器障害等からの復旧 |

### 業務バックアップの検討軸

| 軸 | 選択肢・要点 |
|----|-------------|
| **タイミング** | 夜間バッチ前 / 前後両方 / ログ等の個別タイミング |
| **対象** | データファイル、ログファイル（最低限） |
| **方式** | ①全データ ②差分 ③更新分のみ |
| **周期・世代** | 日次/週次、世代管理、媒体保管 |

## Monitoring Design

### ログ監視

| ログ種別 | 要点 |
|---------|------|
| **オンライン AP** | 経過ログ・エラーログ（必須: DD 以降） |
| **バッチ AP** | 経過ログ・エラーログ（必須: DD 以降） |
| **OS / パッケージ** | システムログ、製品ログ |
| **キーワード** | AP ログに監視ツール判別用キーワードを埋込可 |

### その他監視

| 種別 | 内容 |
|------|------|
| **死活監視** | PING によるサーバ/NW 機器 |
| **キャパシティ** | CPU/メモリ/ディスク等の閾値監視 |
| **プロセス監視** | 常駐プロセス数の下限通知 |
| **NW 障害通知** | ルータ/FW/LB 等の障害トラップ |

### 統合運用監視

- 全システムの監視を**一元管理**（運用委託の統合監視サービスに準拠）
- 監視方式・項目は運用委託側の標準サービス定義に従う
- 設計段階で監視サーバ（運用監視/NW監視等）との連携を確認

## Service Level Consideration

| 観点 | 設計への反映 |
|------|-------------|
| 重要度 | 監視項目・通知先・エスカレーション |
| 可用性 | 冗長、縮退運転、計画停止窗口 |
| 性能 | バッチ完了時刻、オンライン延長限界 |
| 運用コスト | 監視粒度、自動化 vs 手作業 |

## Review Checklist (Client)

- [ ] 要件定義で運用要件が定義されているか  
- [ ] 必須項目（稼働、サイクル、配布、起停、障害、バックアップ、監視）が漏れていないか  
- [ ] ジョブ/バッチとオンラインの時間整合が取れているか  
- [ ] バックアップのタイミング・対象・世代が明確か  
- [ ] 統合監視環境のサービス範囲と一致しているか  
- [ ] 運用設計書（運設）が方式設計書・詳設と整合しているか
