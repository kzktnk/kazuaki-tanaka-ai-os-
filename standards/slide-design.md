# Slide Design Standard

**Version:** v0.1（試行版）  
**Status:** Draft  
**Owner:** Kazuaki Tanaka  
**Document role:** 1枚のスライドの中身（タイトル・配置・表）を作るときの品質基準

---

## Purpose

1枚のスライドを、**タイトルだけで主張が伝わり、左から右へ読むと根拠から帰結へ進み、表が判断に必要な軸だけで組まれている**状態にする。

資料全体の構成（何枚・何順）は `standards/deliverable-archetypes.md`、トーンと削る原則は `core/author-voice.md`、判断の質のレビューは `standards/consulting-review.md` が担う。本書はそのどれにもない**1枚の中の作り方**だけを扱う。同じ規則を他のファイルに重ねて書かない。

## When to Use

- クライアント向けスライドの作成・編集（AIに下書きさせる場合を含む）
- 他者のスライドのレビュー
- AIにスライドを作らせる前に、本書を読ませる

## 適用範囲

- **扱う**：タイトルの書き方（§1）、左右の配置（§2）、表の組み方（§3）
- **扱わない**：フォント・色・罫線の太さ・角丸などの見た目の具体値。IBMのテンプレートとブランドガイドに従う
- **本書の番号**：試行中に指摘を足すときは、既存の番号を変えずに各節の末尾へ追記する（§6）

## 1. タイトル

### 1.1 結論を、切り出しても読める文で書く

タイトルにはそのページの結論を書く。判定は**タイトルだけを切り出して、本文を見ていない人が読んで意味が取れるか**で行う。

- 主語と述語のある文にする。「〜は、…する」が基本
- タイトルは常体で書き、「です」「ます」で終えない
- 1行に収めるために主語・対象・固有名詞を落とさない。長ければ意味の切れ目で2行にする。文字を小さくして1行に詰めない
- 「この」「前述の」で他ページを参照しない。1枚で自立させる

| 避ける | 直す |
|---|---|
| 運用移行の課題 | 運用移行は、監視閾値が未合意のままでは本番切替の判断ができない |
| 連携強化による効率化 | 本社と発電所が同じKPIを見ることで、月次の差異説明が不要になる |

### 1.2 見出しラベルを前置きしない

「現状と課題：〜」「推進体制：〜」のように、タイトルの頭に話題名とコロンを付けない。付けると、タイトルを並べて読んだときに目次にしか見えなくなる。ページの話題はヘッダーのタグやセクション名が担い、タイトルは主張文だけにする。コロンの後ろに主張が書けているなら、前のラベルを消せばそのまま使える。

### 1.3 ページ内の個数をタイトルに入れない。入れたら中身と一致させる

「3つの理由」「5段階で進める」のような**要素の個数は主張ではない**。個数を言いたくなったら、個数の代わりに中身の構造か結論を書く。

- 避ける：「移行は5段階で進める」
- 直す：「移行は、Warrantyの範囲を先に合意してから段階的に切り替える」

数を書いてよいのは、その数自体が伝えたい内容のとき（「保守費は5年で1.8倍になる」「未合意のIFが全体の4割を占める」）。数を書いたら、本文の項目数・段階数と必ず一致させる。「3段階」と書いたページに矢羽が4本ある食い違いは、読み手が最初に気づく破綻である。

### 1.4 タイトルだけを通し読みする

提出前にタイトルだけを抜き出して上から読み、1本のストーリーになっているかを確かめる。話が飛ぶ・戻る・同じことを二度言う箇所があれば、そのページの位置か主張を直す。`core/author-voice.md` §6「キーメッセージだけでストーリーが通るか」を確かめる手順がこれである。

### 1.5 主張の広さを根拠に合わせる

タイトルの言い切りは、そのページの根拠で裏付く範囲までにする。

- 提案先・自社に関わる主張ほど控えめにする（「A社だけが対応できる」→「現時点で対応に着手しているのはA社とB社」）
- 逆に、根拠が広いのに例示を狭く書きすぎない
- 留保は文末をぼかして表すのではなく、「IBM仮説」の明示と主張の範囲で表す（§5）

## 2. 配置

### 2.1 左に前提・事実、右に帰結・意味合い

2カラムでは、**より上流（前提・定義・事実・図表）を左、帰結・意味合い・示唆を右**に置く。読み手は左から右へ「なぜ→何が→だからどうする」の順に読む。

- 図表のあるページは、左に図表・右に読み取りとしてのコメントにする。図の下にコメントを敷かない
- ただし、図が一目で読め、タイトルで意味合いを言い切れているなら、右のコメントを置かず図を全幅にしてよい
- 表より上流にある前提・定義の文章があるときは、その文章を左、表を右にする。迷ったら「どちらが上流か」で決める
- 左右に強い因果（前提→帰結）があるときだけ、間に右向きの三角を1つ置く。単なる表と補足には置かない
- 左右のカラムには、それぞれ単独で意味が通る見出しを付ける（「現行の保守体制」／「移行後に変わる責任分界」）。「だから〜」のように左と続けて読まないと意味が取れない見出しにしない
- 左右の下端を揃える

### 2.2 下部の結論帯と浮いた箱を置かない

- ページ下部に「POINT」「KEY」「まとめ」などの結論帯を作らない。結論はタイトルに、意味合いは右カラムに置く
- 表・カラム・図の構造に属さない小さな箱・ラベル・吹き出しを版面に浮かせて置かない。分類ラベルなら表の行見出しか列見出しに入れる
- `core/author-voice.md` §3.2 の「『IBMの主張：』の独立スライド＋青箱」と同じ理由で避ける。構造に属さない要素は、AIが作ったように見えやすい

## 3. 表

### 3.1 カードを並べるより、軸のある表にする

同じ観点で比べられる内容は、カードやボックスを並べず、**行＝項目・列＝観点**の表にする。

- A案の箱とB案の箱を左右に置いて見比べさせない。行＝評価観点、列＝案の表にする
- 左端の行見出しは、意味のある粒度で大分類に束ねてよい
- `core/author-voice.md` §4.1「表は判断に必要な行だけ」と両立させる。表にするのは、比較の軸が本当にあるときだけにする

### 3.2 行は軸の定義に従い、列は主張に必要なものだけにする

- **行**：左端の軸が定義する集合の要素だけを並べる。軸が「移行対象システム」なら、行はシステムだけにする。マクロな事実、自社の主張、結論の行を混ぜない。提出前に各行を軸ラベルに当てはめて読み上げ、当てはまらない行は外す
- **結論行**：表の最終行に、他の行と粒度の違う「以上より〜」の結論行を足さない。結論はタイトルへ
- **列**：主張に効かない列は置かない。役割分担の表に「過去実績」列があると、読み手は担当の話ではなく実績の比較を始める
- **列見出し**：「事実」「ポイント」のような抽象語にしない。そのセルに何が書いてあるかを名指しする名詞にする（「現行の保守範囲」「移行後の担当」）
- **非該当**：該当しないセルは空欄にせず「—」にする

Archetype D の問題抽出表（`standards/deliverable-archetypes.md`）のように列が決まっている表でも、行と列見出しにはこの節を当てる。

## 4. 提出前チェック

- [ ] タイトルを切り出して読んで、結論が伝わるか（§1.1）
- [ ] タイトルの頭に「〜：」のラベルがないか（§1.2）
- [ ] タイトルに要素の個数を書いていないか。書いた数が本文と一致しているか（§1.3）
- [ ] タイトルだけの通し読みで、1本のストーリーになっているか（§1.4）
- [ ] 言い切りが、そのページの根拠の範囲に収まっているか（§1.5）
- [ ] 左が前提・事実、右が帰結・意味合いの順になっているか（§2.1）
- [ ] 下部の結論帯、構造に属さない浮いた箱がないか（§2.2）
- [ ] 比較できる内容が、カードではなく軸のある表になっているか（§3.1）
- [ ] 表の各行が軸の定義に当てはまり、主張に効かない列がないか（§3.2）

言葉の癖（空虚な強調、カタカナ盛り、定型の締め）は `standards/writing.md` §De-AI Writing Pass、判断の質は `standards/consulting-review.md` で別に確認する。

## 5. 既存ルールとの関係

| 論点 | 既存の記述 | 本書での扱い |
|---|---|---|
| 体言止め | `standards/writing.md` De-AI Pass §5：意図しない体言止めを避ける | 散文は既存どおり。スライドのタイトル・ブレットは、同じ階層で語尾を揃えることを条件に体言止めを許す |
| So what | `core/author-voice.md` §3.2：「So What」「Key Insight」の見出しを乱用しない | 意味合いの**中身**は必ず載せるが、**ラベル**は使わない。意味合いはタイトルか、右カラムの名詞句の見出しに載せる（§2.1） |
| 留保 | `core/author-voice.md` §3.1：「仮説」「案」「〜と考えている」を使う | 留保は「IBM仮説」「案」の明示と主張の広さ（§1.5）で表す。タイトルの文末は言い切る。「〜と考えられます」を並べると、かえってAIっぽく見える |
| 1スライド1メッセージ | `standards/writing.md` Slide Writing、`core/author-voice.md` §4.1 | 本書はその実装方法。原則は既存ファイルに置いたままにする |

## 6. 試行の進め方とメンテナンス

- **試行**：実案件のデッキ1本（10枚前後）で本書を使う。AIに下書きさせる場合は、作らせる前に本書を読ませる。レビューで受けた指摘のうち本書で防げなかったものを記録する
- **Activeへ上げる条件**：試行1本を通して、§4のチェックで拾えなかった指摘が本書に追記済みであること。上げるかどうかはOwnerが判断する
- **追記**：レビューで同じ指摘を2回以上受けたら、該当する節の末尾に1行で足す。既存の番号は変えない（`knowledge/patterns/standard-as-learned-memory.md`：1回の指摘ではなく、繰り返された指摘を標準に戻す）
- **足さないもの**：見た目の具体値、特定クライアントのブランド規則、ピッチ（登壇）用の作法
