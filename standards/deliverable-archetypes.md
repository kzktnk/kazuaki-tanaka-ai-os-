# Deliverable Archetypes — Slide & Document Structure

**Version:** v1.1  
**Status:** Active  
**Owner:** Kazuaki Tanaka  
**Origin:** レガシー成果物アーキタイプの**最小構成**テンプレ。クライアント名・固有情報なし。

---

## Purpose

資料種別ごとの**最小スライド/文書構成**を定義します。

`knowledge/lessons/author-voice-archetypes-legacy.md` が「何を作るか」を説明するのに対し、本書は**何枚・何順で書くか**の実務テンプレです。

`core/author-voice.md` の原則（1スライド1メッセージ、10枚前後、削る勇気）に従って設計しています。

---

## How to Use

1. アーキタイプを選ぶ（legacy または task type）
2. 本書の**最小構成**を骨格にする
3. 詳細は Appendix または次フェーズへ
4. 提出前に `core/author-voice.md` §6 チェックリスト

## Archetype A: 提案書（RFP応答 / Phase提案）

**目安枚数:** 12–18枚（Appendix除く）  
**読者:** 選定委員会、プロジェクトオーナー

| # | スライド | キーメッセージ（例） |
|---|---------|---------------------|
| 1 | 表紙 | — |
| 2 | 背景・課題 | クライアントFactから入る。なぜ今か |
| 3 | 目的・ゴール | 本提案が達成すること |
| 4 | 提案の全体像 | 方式・アーキの1枚サマリー |
| 5–6 | 方式詳細（必要最小） | 選定理由に直結する部分のみ |
| 7 | 実現性：前提・スケジュール | 実現可能である根拠 |
| 8 | 体制 | 誰がどう回すか |
| 9 | 付加価値 | 要件外の妥当提案、盲点への気づき |
| 10 | リスクと対応 | 主要リスク2–3点 |
| 11 | 次ステップ | 合意・依頼事項 |

**Appendix（任意）:** 詳細アーキ、WBS、参考事例

**避ける:** 全章Equal深度、エグゼクティブサマリー先行（本編未確定時）

## Archetype B: ベンダー評価結果報告

**目安枚数:** 8–12枚  
**読者:** 選定会議、SteerComm

| # | スライド | 内容 |
|---|---------|------|
| 1 | 評価の目的・方法 | 評価軸、段階、評価者 |
| 2 | 評価サマリー | 論点別の差分（点数表だけにしない） |
| 3–5 | 領域別ハイライト | 基盤、業務領域A、業務領域B 等 |
| 6 | 付加価値の比較 | 要件外提案・盲点への対応 |
| 7 | 懸念・リスク | 選定に影響する論点 |
| 8 | 推奨と根拠 | 留保付き推奨 |
| 9 | 次ステップ | 二次評価、追加確認、決定依頼 |

**表の原則:** 評価Pointごとに**1行コメント**（なぜその点数か）

**参照:** `standards/vendor-proposal-evaluation.md`

**目安枚数:** 12–18枚  
**読者:** アーキレビュー、PMO、発注側技術担当

| # | スライド | 内容 |
|---|---------|------|

| 3–5 | 各案概要 | 案A/B/C — 1案1–2枚 |

## Archetype G: カスタム開発成果物体系（Build Phase）

**適用:** ウォーターフォール型のカスタム開発（要件定義 → 設計/製造 → 試験）  
**読者:** 発注側レビュー担当、ベンダー設計リード、QA  
**参照:** `standards/development-management-guide.md`, `standards/document-management-standard.md`, `frameworks/sap-implementation-phase-model.md`（試験体系 UT/IT/UAT 等）

大規模案件をモデルとした**成果物カタログ**です。プロジェクトごとに作成単位・様式は調整可。実様式テンプレートはリポジトリに登録しない（ID と用途のみ）。

### Phase Overview

| フェーズ | 目的 | 発注側の焦点 |
|---------|------|-------------|
| **要件定義** | 業務要件洗い出し → 要定/方概 | スコープ確定、概要レベル（詳細は設計へ） |
| **設計/製造** | 仕様確定 → 実装 | 仕様FIX、UI/データ/方式、プログラム |
| **試験** | 結合/総合/総合運転 | 計画妥当性、品質目標、受入 |

**原則:** 要件定義で十分にまとめないと設計で手戻り、仕様確定が遅れると製造で品質低下。

### Minimum Deliverables (MIN)

規模に関わらず**最低限**必要（様式目次 ○ 付き）：

| フェーズ | MIN 成果物 |
|---------|-----------|
| 要件定義 | 機能一覧(C101)、アクティビティ図(C111)、ビジネスルール(C102) |
| 設計/製造 | 機能一覧、画面一覧/遷移/レイアウト、帳票一覧/レイアウト、外部IF一覧、外部IF定義(C243)、ファイル一覧、コード/エンティティ定義、論理ER |
| 試験 | 総合試験項目表(C301)、シナリオ(C302)、成績書、運用引継説明書 |

### Review Checkpoints by Deliverable Group

#### 要件定義

| 成果物群 | レビューポイント（要約） |
|---------|------------------------|
| UC/Activity/BR/機能一覧 | システム化範囲明確、業務フロー洗出、機能要件網羅、ユーザ要件との差異に理由/代案 |
| 画面 | 発注側イメージと一致、対象画面の網羅 |
| 帳票 | 発注側イメージと一致、対象帳票の網羅 |
| 外部I/F | 連携先・I/Fの網羅 |
| ファイル | 対象ファイルの網羅 |
| 概念データ | 業務フロー整合、コード妥当、移行考慮、画面/帳票との突合 |
| 方概 | 基盤/セキュリティガイドライン準拠、個別非機能要件 |

#### 設計/製造

| 成果物群 | レビューポイント（要約） |
|---------|------------------------|
| UC/共通/機能 | ユーザ要件実現、BR整合、機能連携、共通化、開発規約準拠 |
| 画面 | ユーザ承認レイアウト、UI標準、デザイン妥当性 |
| メッセージ | 可読性、通知/警告/エラー区分、エラー時の対処 |
| 帳票 | ロール権限対応 |
| 外部I/F・ファイル | 入出力仕様明確 |
| ステート | 業務フローと状態遷移の矛盾なし |
| バッチ | 機能網羅、リカバリ策 |
| 論理データ | ユーザ承認コード、第1正規化 |
| 方式/運用 | 基盤/セキュリティ/運用ガイドライン準拠、環境構築定義 |
| プログラム | 共通部品利用、開発規約準拠 |
| 移行 | 移行対象・方法明確 |

#### 試験

| 成果物 | レビューポイント（要約） |
|--------|------------------------|
| 総合試験計画 | 無理のない日程、消化件数/日、外部連動調整、正常/異常/性能/連動計画、品質目標値 |
| シナリオ/項目 | Go-live起点、実運用想定、観点→項目の漏れなし、目標項目数 |
| 成績書 | 計画通り完了、未達時の理由/対策 |
| 総合運転 | 実運用シナリオ、業務要件確認、品質/性能充足 |
| 運用マニュアル | 通常/異常運用の記述 |

### Usage Notes

- `standards/document-management-standard.md` の文書区分（要定/方概/詳設…）と表紙・改定履歴に準拠
- 代替資料で代用可（例: シーケンス図で処理定義書を代替）— プロジェクトで合意し記録
- 様式使用: 印刷レイアウト確認、不要シート削除
