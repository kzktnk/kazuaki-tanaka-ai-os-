# Deliverable Archetypes — Slide & Document Structure

**Version:** v1.0  
**Status:** Active  
**Owner:** Kazuaki Tanaka  
**Origin:** レガシー成果物アーキタイプの**最小構成**テンプレ。クライアント名・固有情報なし。

---

## Purpose

資料種別ごとの**最小スライド/文書構成**を定義します。

`knowledge/lessons/author-voice-archetypes-legacy.md` が「何を作るか」を説明するのに対し、本書は**何枚・何順で書くか**の実務テンプレです。

`core/author-voice.md` の原則（1スライド1メッセージ、10枚前後、削る勇気）に従って設計しています。

---

## How to Use

1. アーキタイプを選ぶ（legacy または task type）
2. 本書の**最小構成**を骨格にする
3. 詳細は Appendix または次フェーズへ
4. 提出前に `core/author-voice.md` §6 チェックリスト

## Archetype A: 提案書（RFP応答 / Phase提案）

**目安枚数:** 12–18枚（Appendix除く）  
**読者:** 選定委員会、プロジェクトオーナー

| # | スライド | キーメッセージ（例） |
|---|---------|---------------------|
| 1 | 表紙 | — |
| 2 | 背景・課題 | クライアントFactから入る。なぜ今か |
| 3 | 目的・ゴール | 本提案が達成すること |
| 4 | 提案の全体像 | 方式・アーキの1枚サマリー |
| 5–6 | 方式詳細（必要最小） | 選定理由に直結する部分のみ |
| 7 | 実現性：前提・スケジュール | 実現可能である根拠 |
| 8 | 体制 | 誰がどう回すか |
| 9 | 付加価値 | 要件外の妥当提案、盲点への気づき |
| 10 | リスクと対応 | 主要リスク2–3点 |
| 11 | 次ステップ | 合意・依頼事項 |

**Appendix（任意）:** 詳細アーキ、WBS、参考事例

**避ける:** 全章Equal深度、エグゼクティブサマリー先行（本編未確定時）

## Archetype B: ベンダー評価結果報告

**目安枚数:** 8–12枚  
**読者:** 選定会議、SteerComm

| # | スライド | 内容 |
|---|---------|------|
| 1 | 評価の目的・方法 | 評価軸、段階、評価者 |
| 2 | 評価サマリー | 論点別の差分（点数表だけにしない） |
| 3–5 | 領域別ハイライト | 基盤、業務領域A、業務領域B 等 |
| 6 | 付加価値の比較 | 要件外提案・盲点への対応 |
| 7 | 懸念・リスク | 選定に影響する論点 |
| 8 | 推奨と根拠 | 留保付き推奨 |
| 9 | 次ステップ | 二次評価、追加確認、決定依頼 |

**表の原則:** 評価Pointごとに**1行コメント**（なぜその点数か）

**参照:** `standards/vendor-proposal-evaluation.md`

## Archetype C: SteerComm / 経営層進捗

**目安枚数:** 6–10枚  
**読者:** ステアリングコミッtee、経営層

| # | スライド | 内容 |
|---|---------|------|
| 1 | 前回決定事項の進捗 | 完了/未完了を明示 |
| 2 | 今回の論点（2–3点） | 優先順位付き |
| 3–4 | 論点ごとの推奨と根拠 | 1論点1枚 |
| 5 | リスク・トレードオフ | 省略しない |
| 6 | 依頼する決定 | 何を、いつまでに |
| 7 | ToDo・次回 | 担当・期限 |

**避ける:** 30枚の進捗羅列、決定前の網羅報告

## Archetype D: 課題抽出・改善案（Phase 300）

**目安枚数:** 10–15枚  
**読者:** PMO、ステークホルダー、方式検討チーム

| # | スライド | 内容 |
|---|---------|------|
| 1 | As-Isの要点 | Fact（200の要約） |
| 2 | Gapの構造 | なぜ今つまずくか |
| 3–5 | 主要課題（3–5点） | 1課題1メッセージ |
| 6 | 改善方向 | To-Beの方向性（詳細方式は410へ） |
| 7 | 優先度・影響 | 何から手を付けるか |
| 8 | 換装・移行時期の論点 | 判断材料（FIXは410/420） |
| 9 | 次フェーズへの入力 | 400で検討すること |

**表（問題抽出表）の最小列:**

| 列 | 内容 |
|----|------|
| ID | 通番 |
| 現象 | 観測された事実 |
| 原因（仮説） | 構造的原因 |
| 影響 | 業務・コスト・リスク |
| 優先度 | 高/中/低 |

## Archetype E: 方式比較・各案評価（Phase 410）

**目安枚数:** 12–18枚  
**読者:** アーキレビュー、PMO、発注側技術担当

| # | スライド | 内容 |
|---|---------|------|
| 1 | 検討の目的・評価軸 | 何をもって選ぶか |
| 2 | 現行方式（As-Is） | 出発点 |
| 3–5 | 各案概要 | 案A/B/C — 1案1–2枚 |
| 6 | 各案評価シート | 評価軸 × 案（表） |
| 7 | 推奨案 | IBM/コンサル仮説（留保付き） |
| 8 | 推奨理由 | トレードオフ明示 |
| 9 | 詳細（フロー/構成） | 必要最小 |
| 10 | 次ステップ | 420要件定義への引継ぎ |

**評価シートの最小軸（例・OA/基盤刷新）:**

- セキュリティ・ガバナンス適合
- 運用コスト・保守性
- 拡張性・変化への耐性
- 移行実現性
- 既存資産との整合

## Archetype F: 調査研究報告会（Phase 500）

**目安枚数:** 15–20枚（100–400の圧縮）  
**読者:** ステークホルダー、スポンサー

| # | スライド | 内容 |
|---|---------|------|
| 1 | 背景・目的 | Phase 100 |
| 2–3 | 現状の要点 | Phase 200 |
| 4–6 | 主要課題と改善方向 | Phase 300 |
| 7–10 | 推奨方式と要件概要 | Phase 400 |
| 11 | 全体スケジュール | 次プログラム |
| 12 | 依頼事項・決定事項 | 報告会のゴール |

**原則:** 500だけ独立ストーリーを作らない。本体成果物の**要約**であること。

## Archetype G: 定義・仮説デック（JERA型）

**目安枚数:** 8–12枚  
**読者:** PO、作成者、経営層（本編確定後にサマリー）

| # | スライド | 内容 |
|---|---------|------|
| 1 | 位置づけ（1行） | メタ長文禁止 |
| 2 | Fact | 確認できたこと |
| 3 | Issue | なぜ今 |
| 4 | IBM仮説 | 自分の定義・答え |
| 5–6 | To-Be | あるべき姿 |
| 7–8 | Approach | 方策と順序 |
| 9 | 論点・次アクション | 決定依頼は定義後 |

**参照:** `knowledge/lessons/client-deliverable-voice-jera-2026-08.md`
