# Release Management Guide

**Version:** v1.0  
**Status:** Active  
**Owner:** Kazuaki Tanaka  
**Origin:** 大規模基幹系更改案件のライブラリ／リリース管理規約（2003/12）を一般化。クライアント名・ベンダー名・固有情報なし。

---

## Purpose

構成管理の一環として、ソフトウェア変更作業を**正確かつスムーズ**に行い、**トレーサビリティ**を確保する標準です。

総合試験工程以降の**ライブラリ管理**と **PT → RT → 本番** のリリースを前提とします。

`standards/development-management-guide.md` §Configuration Management と接続します。

---

## When to Use

- 結合試験以降のソース・設定・実行形式の版管理
- 変更開発・障害修正のリリースフロー設計
- 開発ベンダー / AP維持 / 運用委託のリリース責任分界
- RFP・契約のリリース管理条項

---

## Roles

| 関係者 | 責任 |
|--------|------|
| **発注側** | 変更決定、各種承認、受入試験 |
| **開発ベンダー / AP維持** | 資源貸出依頼、修正、PT/RT 試験、リリース申請 |
| **運用委託** | 資源貸出実施、環境へのリリース実施、台帳管理 |

各社は必要に応じ**ライブラリ管理者**（窓口）を設置。

---

## Basic Policy

1. すべての作業は**発注側の監督**のもとで実施  
2. リリース順序: **PT → RT → 本番**。各段階で正しく動作確認してから次へ  
3. パッケージ製品は本規約に準拠しつつ、製品固有手順を併用可  

---

## Management Scope

### ライブラリ管理対象（代表）

| カテゴリ | 例 |
|---------|-----|
| **ソース** | 各種言語ソース、スクリプト |
| **ビルド** | ビルド/DDL/環境構築スクリプト |
| **設定** | OS、Web/AP、DB、AP、運用設定 |
| **実行形式** | クラス、jar/war/ear、バイナリ、帳票定義 |
| **パッケージ生成物** | リポジトリ export 等 |

### 管理項目

| 項目 | 内容 |
|------|------|
| 世代・差分 | 変更履歴 |
| 属性 | システム名、言語、資源区分（ディレクトリ構成） |
| 状態 | PT試験中 / RT試験中 / 本番リリース済 |
| リリース情報 | 日付、事由（仕様変更番号等） |
| 有効性 | 論理削除の識別 |

### 二重管理（長期変更）

制度変更等で本番リリースまで長期間かかる場合、**変更対象を別管理**する。試験環境は新規環境または既存流用を検討。

## Release Targets by Environment

| 環境 | 役割 |
|------|------|
| **PT** | 開発ベンダー主体の総合試験 |
| **RT** | 発注側受入・総合運転試験 |
| **本番** | サービス提供 |

## Release Flow

```
(1) 変更指示（発注側）
  → (2) 資源貸出依頼（ベンダー/AP維持）
  → (3) 貸出承認（発注側）
  → (4) 貸出実施（運用委託）+ 台帳記録
  → (5) 資源修正（ベンダー/AP維持）
  → (6) PT環境リリース + 試験
  → (7) RT環境リリース・返却依頼（基準充足時）
  → (8) RTリリース・返却（運用委託）+ 発注側受入試験
  → (9) 本番リリース承認（発注側）
  → (10) 本番リリース（運用委託）
```

**新規開発**で既存資源修正が不要な場合は (2)–(4) を省略し (5) へ。

**RT 不具合時:** (2) から再実施。

## Release Criteria (Generalized)

リリース承認時の確認（※原本の品質基準を一般化）：

| 確認項目 | 内容 |
|--------|------|
| 品質 | 当該環境の試験・受入基準を満たす |
| 完備性 | リリース対象物が揃っている |
| 文書 | 申請書・資源一覧・管理台帳に不備がない |
| トレース | 変更事由（仕様変更番号等）が記録されている |

**緊急時:** 承認者不在・夜間の手順は事前に別途定義。

## Build Timing

| ケース | 対象 | 条件 |
|--------|------|------|
| **A** | Java/C 等ビルド必要 | 各環境のビルド環境（JDK 等）が同一であること |
| **B** | DB 登録型（ストアド等） | 環境ごとに登録 |
| **C** | スクリプト等ビルド不要 | 直接リリース |
| **リポジトリ系** | ERP 等 export | 製品手順に従う |

ビルドは原則 **PT 環境**で実施。

## Library Directory Structure (Pattern)

### 環境設定系（3層）

| 層 | 内容 |
|----|------|
| L1 | サーバまたは論理区画 |
| L2 | サービス（DB, Web/AP 等） |
| L3 | ファイル種別（起動系、cron 等） |

### 業務 AP 系（3層）

| 層 | 内容 |
|----|------|
| L1 | システム |
| L2 | 業務 |
| L3 | アプリケーション（必要に応じ deeper） |

**変更時:** 実行環境のツリーとライブラリツリーを一致させ、変更は関係者へ速やかに通知。リポジトリは定期バックアップ。

## Review Checklist

- [ ] PT→RT→本番の順序が守られているか  
- [ ] 貸出〜返却〜本番まで台帳が連続しているか  
- [ ] リリースログ・作業履歴が取得されているか  
- [ ] 本番リリース前に RT 受入が完了しているか  
- [ ] 長期変更の二重管理が必要な場合、別管理されているか  
- [ ] 緊急リリース手順が定義されているか
